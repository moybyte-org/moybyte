## 0. The goal, and the one test

People use Moybyte like an OS. Someone who wants LoRaWAN, sensors, motors,
MIDI, a synth, internet radio or a terminal tool writes a Moybyte **app**, in
the tier they choose (Python, Lua, wasm, C), instead of flashing a
single-purpose firmware over the console. The OS serves what the app needs:
**hardware, timing, background running and isolation**, and keeps the shell,
the store and OTA underneath.

Every proposal is judged by one question: **does it move a capability from
"flash your own firmware" to "an app asks the OS for it"?**

The frame: the OS is native code below the app verb table and Python is an
app runtime (owner, 2026-10-05; `native/moy_kernel/README.md`). #224 put the
spine, the store, input, audio, the glass, the frame loop, the radios, the
cart path, the app ABI's grants and the toolkit core in C; Lua and wasm carts
run with no Python call. The window managers, `console.py`, the Python cart
path and every shipped app stay Python (owner, 2026-09-27 and 2026-11-01:
sprint 7 is cancelled). This document builds on that line.

## 1. The principles

**Real-OS behaviour (owner, 2026-11-03): do what is closest to real on every
OS component.** The terminal is its first case (`system.md` §1).

**Each tier speaks its own community's standard (owner, 2026-11-03)**: POSIX
for C (`tiers.md` §1), WASI for wasm (`tiers.md` §3), MicroPython's `machine`
and `asyncio` for Python (`hardware.md` §1, `processes.md` §3), Lua's
`io`/`os` (`tiers.md` §2), so people bring existing code. Moybyte's own APIs
(`moybyte.*`) cover only what has no standard: the device APIs, events,
notifications, the picker and intents, the wake sources, the terminal's size,
and the log for Lua and wasm. After the plan, the owner's words: "a mostly
complete OS".

**Trust is consent per app, at install (owner, 2026-11-02).** The install
prompt says plainly what the app can reach: each permission by name, and for
`native` or a raw lease the one line **"full access to the console"**. The
user decides app by app. There is no device-wide developer mode and no
Unknown-sources switch as a gate; the wasm tier's switch
(`native/moy_wasm/README.md`, "Unknown sources") becomes this prompt for an
unsigned module. A store cart may be Lua, wasm or Python: a Python app
is listed as a **trusted app**, its prompt saying so. **A cart the user
writes in the Editor never prompts** (owner, 2026-11-03): their own code is
trusted, and PLAY grants what its manifest lists. The manifest, the
permission table and install are `processes.md` §2; the ladder is §4.

**Rules dropped (owner, 2026-11-01).** "One cart at a time", "no native apps"
and "no tier has a feature the others lack". The third was about moy-spec's
verb table, which still agrees verbatim across Python, Lua and wasm
(`docs/moy_cart_api.md`); what a tier may lack is an **OS** capability
(§4), and the OS says so instead of pretending.

**The memory rule every part of this design answers to.** THE SHARES
(`native/moy_play/moy_play.h`): a cart's PSRAM floor and largest block,
the kernel's internal-SRAM cap while the VM runs and nothing net while it is
stopped. The heap grows by
areas (on the S3s at most 512 KB a growth, `MOYBYTE_GC_GROW_MAX`; a P4's
doubles) and keeps an area while one object lives in it (#248). A second heap, a media buffer,
ELF text, a lane stack or a ring is a line in the shares or it does not exist:
THE SHARES' ROWS (the same header) give each console board a PROCS, MEDIA,
RINGS, ELF and LANES row, and the fit check refuses a take from a row that
is absent or full.

## 2. What stands from the 2026-07 plan

**Positioning (plan §2, DECIDED 2026-07-01, kept).** "Learn to make", not
"learn to use": a creative computer whose desktop, tools, games and lessons
are editable cartridges. The OS direction extends it: the person who outgrows
the cart API keeps the console and writes an app for it. "Not an app-store
device" reads as "not a device whose point is consuming apps"; the store
(#122–#125) is the funnel's far end.

**The canvas contract (plan §4, DECIDED).** A fixed 320×240 indexed canvas
for games on every tier; system UI at native resolution. The contract is
`.claude/rules/rendering.md` and `device/device_canvas.py`; presentation is
`docs/surface_model_v1.md`. Nothing here touches it.

**Safety (plan §13).** Local-first, no accounts for local use, no open
internet in child mode; a cart that wants more says so in its manifest. Plan
§13.2's two-level list is replaced by the permissions of `processes.md` §2,
each consented to per app at install (§1). Received carts are not run
until accepted. Child-mode policy covers every OS service acting for an app
(`hardware.md` §3). The AI helper is not part of the OS (#8, closed 2026-11-01).

The rest of the plan is shipped and described by its own authority
(`runtime/README.md`, the board READMEs, `docs/netplay_v1.md`,
`docs/engine3d_2026-10.md`) or history.

## 3. The process model in brief

Everything the OS runs is a process: an app (a window), a wallpaper, a
command (the terminal's), a service (no window, running whatever is on
screen) or an OS service, each a row of a C process table with a pid, a
state and an exit code. The shell is process 1, and every Python app runs
inside its one MicroPython VM, stepped cooperatively; Lua, wasm and ELF
processes run on kernel-owned tasks. Several apps, games included, run at
once: focus is the window manager's, running the process table's, and the
user sees in the task manager what each costs. A background process never
gets a per-frame tick; it sleeps on timers and events fed from C rings. The
design is `processes.md` §1 (kinds, states, the tick model) and §3 (the
Python VM).

## 4. The trust ladder

**Decision (owner, 2026-11-01): the more powerful the tier, the less sealed it
is and the more trust it needs.** Trust is consented per app (§1).

| tier | sealed by | may hold | store lists it | the prompt says |
|---|---|---|---|---|
| **Lua** | the safe stdlib and libmoy's verb table at runtime (`native/moycore`) | roles, device APIs, events (`hardware.md` §2); `pins` (`hardware.md` §1) | yes | its permissions |
| **wasm** | bounded linear memory; imports the only surface (`native/moy_wasm/README.md`) | the same, plus bus leases and timed lanes (`hardware.md` §2) | yes, compiled and signed by the store | its permissions; "full access" for a raw lease |
| **Python** | nothing (`processes.md` §2) | the same as Lua, plus bus leases as `machine` objects (`hardware.md` §1) | yes, as a trusted app | its permissions, and that it is trusted; "full access" for a raw lease |
| **C (ELF)** | on the P4 boards, U-mode and PMP, the table the only surface; on the S3s nothing, the kernel's own trust level (`os_2026-11/tiers.md` §1) | every table row; leases | no | "full access to the console"; one build per chip |
| *deferred (owner, 2026-11-02)*: server-compiled safe Rust → signed ELF | the compiler, against bugs not malice (rustc soundness holes such as `cve-rs`; `unsafe` in dependencies; panics and stack overflow still need the OS) | as C | would | as C |

**Signing is the default, not a lock** (owner, 2026-09-29): a present
signature must verify, whatever the user consented to; an absent one is what
the prompt covers. An unsigned ELF installs on consent, with no signing gate
(owner, 2026-11-02); a store that compiles C signs module, manifest and id
together.

**Hardening is a later step**, taken if adoption warrants it (owner,
2026-11-02: "we can always harden it later"). What it would add, in order:
a separate MicroPython instance for the foreground Python app on the P4s
(#246's variant A, at the GC cost #246 records: every instance's collection
lands in the foreground frame), with a module allowlist, if leaks or crashes
from Python apps become a problem (`processes.md` §3); the ELF signature
covering manifest and id, with revocation and key rotation over OTA; and a
consent gate above the per-app prompt for the powerful rungs (`native`, raw
leases), such as a parent's. None of it changes an app's manifest or the
permission table.

## 7. The order of work

**Six phases (owner, 2026-11-03): ship an early version as fast as
possible, Python first, then the hardware, the local system, remote access,
the other tiers and the OS between apps.** Phase 1 makes Python apps real OS
processes on every board and depends on nothing in phases 2–6; where a
phase-1 piece touches a later phase's mechanism it takes only the slice it
needs, named below. Phase 1 shipping Python-only is consistent with the
dropped "no tier lacks a feature" rule (§1): a Python app's background
process, notifications and task-manager row reach Lua and wasm in phase 5,
and the "same app in every tier" test is phase 5's.

Each step lands on its own; #246 tracks which have. The bar for any step
that touches a frame is the owner's: about 1.5 ms per frame over dev on #66's
rows (Brick Siege, a Lua cart, a compiled cart), measured with PERF `--diag`
and the LOOP line on the T-Deck and a P4, with `heapcaps` internal low-water
read with WiFi and BLE up. The bar measures the OS's own overhead; what the
user's chosen apps cost is shown in the task manager, not budgeted. Numbers
go to #66, #58, #158 or #246.

### Phase 1 — the early version: Python apps as processes

The VM-abort spike runs first (P1.1). The phase's slices of later phases:
from the shares (P2.1) only the rows a Python app's admission counts; from
the permission table only the rows Python apps hold; from clock and events
only the sources a Python app wakes on in this phase (input, timers;
`on("lora")` arrives with the LoRa row in P2.3). The dev channel and the
strike ledger cover debugging and recovery until phase 3.

1. **The VM-abort spike** (`processes.md` §3): whether a timer-driven
   `mp_sched_vm_abort` stops a runaway Python callback while the shell
   survives, on the T-Deck and a P4. *Verify:* a spinning callback aborted
   and the shell painting its next frame; the shell's GC pause (PERF `gc=`)
   and heap growth (`tools/mem_census.py` after) with two background Python
   apps alive, recorded in #246; whether the abort reaches a `_thread` that
   is not the main one, and a close held by a thread ignoring the stop
   ending once it does.
2. **The cheap fixes**: apply the saved brightness at boot and on
   change; read the battery (#130); declare the GPS on UART0 in the T-Deck's
   README (whose USB section calls U0RXD a header pin with nothing attached)
   and board file. *Verify:* host tests for the settings path; a T-Deck
   board pass (`tools/board.py pass tdeck`).
3. **The system log** (`processes.md` §9), with "this app crashed: details"
   and the crash notification once P1.8 and P1.9 exist. *Verify:* host tests
   of the ring (levels, process ids, wrap); a golden of the viewer; a board
   pass reading `log` over the dev channel.
4. **Clock and events, the Python half**: the record, rings and provenance
   (`hardware.md` §2) in `native/moy_input` for the sources Python apps use
   here; `time.ticks_us`, `moybyte.events(into)`, `moybyte.on/every/after`.
   *Verify:* `tests/test_frame_alloc.py` green; a PERF/LOOP A/B against dev
   on #66's rows on the T-Deck and a P4; internal low-water; scripted taps
   and a ring overflow on a P4's touch source (no P4 touch path uses an ISR,
   so its records are POLL).
5. **The permission table and the install prompt, as far as Python needs
   them** (`processes.md` §2, §1 here): the one table for the rows Python
   holds (roles, `notifications`, `autostart`, the device APIs of this
   phase), the prompt built from it, consent recorded with the grant,
   install-time and launch-time checks, all-or-nothing install, revocation
   per permission, no prompt for an Editor cart. *Verify:*
   `tests/test_roles.py` and `tests/test_user_apps.py` held to it; host
   tests of a denied install leaving nothing, a revoked permission absent
   (`None`) and a revoked `required` one refusing the launch; a prompt
   golden.
6. **The cooperative scheduler** (`processes.md` §1, §3, §4, §5): background
   Python apps on wake sources, the per-callback slice with warning →
   strike → suspend, the abort, the guaranteed slice (`MOY_BG_SLICE_*`),
   stop and restart across a VM stop; start and stop, TERM then
   KILL after `MOY_SERVICE_STOP_MS`, autostart at boot for an app holding
   `autostart`, log lines per service. *Verify:* host tests of each overrun
   rung, of TERM then KILL and of autostart; a PERF row of an unpaced game
   with the slice on, against dev; a board pass on an S3 and a P4.
7. **Several apps at once** (`processes.md` §1, §6): the window states, the
   game template pausing itself on minimise, the throttle rule with the
   freeze path unchanged, admission over the running set, the fifth audio
   source refused. *Verify:* `tests/test_wm_content_freeze.py` extended with
   a throttled window; goldens of a desk with a focused and a throttled game
   and of the refusal; host tests on each S3's shares (two big games
   refused); a P4 PERF run with two games open, each game's fps and both
   rates in #66.
8. **The task manager** (`processes.md` §6): per-process timing of `update`,
   `draw` and callbacks; Python's approximate memory; the system app with
   Close. Lua and wasm rows arrive in phase 5. *Verify:* host tests of the
   accounting against a cart of known cost; pixel goldens on every tier; the
   same two-game P4 run.
9. **Notifications** (`processes.md` §7). *Verify:* host tests of post, act
   (the game throttled on the desk, minimised on a handheld) and dismiss (it
   keeps playing); goldens of the banner on every tier; a board pass.
10. **Achievements as the first background process** (`processes.md` §8).
    *Verify:* `tests/test_roles.py` on the moved rows; host tests of an
    `achieve()` from a cart reaching the store and posting; goldens of
    Settings' Achievements page unchanged; a PERF row of the `achieve()`
    hop's frame cost against dev; a board pass on every board.

### Phase 5 — the other tiers

Spike: `elf_loader` on the S3.

1. **The Lua role binding** over the same source as the wasm adapter, and
   Lua's `io`/`os` over the files tree under the app's permissions
   (`tiers.md` §2). The public UI API already has its Lua face
   (`native/moycore/moycore_ui.h`, `native/moy_ui/README.md`), so no UI
   binding is new here. *Verify:* the roles trace in
   `tests/test_semantic_traces.py` for a Lua app.
2. **Wasm per-process grant binding**, replacing the adapter's one global
   grant (`tiers.md` §3). *Verify:* `tests/test_roles.py`; two compiled
   apps' grants distinct in a host test.
3. **Lua and wasm process tables, services and multi-session** (`tiers.md`
   §2, §3, `processes.md` §6): the runs as rows, services on their own tasks
   on P4 core 0, the task manager's exact heap rows, the crash record's
   process id. With the table in C, the device ownership the Python faces
   decide today (the WiFi hold, and one holder each for the mic, LoRa, BLE
   scan and media, `runtime/system/dev_*.py`) becomes lease kinds in
   `moy_lease`, the faces thin over them, and the shell's device commands
   are served in C over the same leases (owner, 2026-11-05: no second copy).
   *Verify:* two Lua processes in a host test; a service
   surviving an app switch; PERF `--diag` rows unchanged, the S3s included
   for OS services; an ELF or wasm process and the shell refused the mic
   while a Python app holds it, and the reverse.
4. **The ELF tier and its POSIX subset** (`tiers.md` §1): the ordinal
   source, the loader after its S3 spike, per-chip builds, the "full access"
   prompt; the file, socket, time and pthread rows; the lane exports on the
   P4s (`hardware.md` §2); the cross SDK. *Verify:* hello on each chip; a
   newer-table module refused; the internal-SRAM net cost and stall of a
   load; the sweep of its handles and its pthreads on a normal stop and on a
   crash; an unmodified small C program (a `cat`, an `nc`) built with the
   SDK and run on a board pass; a deliberate crash's core dump read with
   gdb, and the partition's cost against `headroom_floor_kib`.
5. **WASI for the wasm tier** (`tiers.md` §3), unless the WASI spike brought
   the commands forward in phase 3. *Verify:* a wasi-sdk `cat` and a Rust
   `wasm32-wasip1` hello run as commands unchanged on a board pass;
   `tests/test_roles.py` unchanged (WASI adds no ordinal rows).

**The tier-conformance test.** Once a tier has the verbs, porting the
achievements process to it (wasm, Lua) is the test that the same app behaves
the same in every tier: the same events in, the same store, the same
notifications out, pinned by the host test of P1.10 run per tier
(`tests/test_achievements_proc.py`; the Lua port and the wasm tier's gap are
`tiers.md` §2).
