# The 3D engine — a second engine under one console (2026-10)

**Status: DRAFT rev 3, 2026-10-04.** Rev 1 went through an architecture pass
(**REWORK**) and a performance and hardware pass (the perf case did not stand);
rev 2 folded every finding in. Rev 3 takes the owner's design decisions of the
same day (§2): the engine owns the 3D world's actors, the cart reaches them
through events, simple beats fast. It re-bases the speed case on ESP 88, the
closest measured scene to a racing game (§4). §13 is the ledger. Nothing here
is scheduled until the owner accepts it, and the plan puts the work after the
native kernel's transition (§7).
**Tracks:** #228 (3D for carts; this doc re-scopes it) · #224 (the kernel) ·
#158 (the compiled tier, the Jet and ESP 88 measurements) · #66 (frame and
per-verb numbers) · #85 (scenes, and the decision §2 reopens) · #227 (native
carts).
**Claims carry the kernel doc's four labels** (MEASURED, SOURCE, ESTIMATED,
PREDICTED; `docs/native_kernel_2026-09.md`'s header defines them). The numbers
quoted are the ones an argument turns on; their home is the issue cited.

## 0. The thesis

**What makes a 3D editor easy is its loop: model a thing, place it on a map,
give it behaviour.** The Blocks tier offers that loop in 2D: the Scene panel
places actors, the actor world moves and removes them, `draw_scene()` draws
them, and the Actors blocks compile onto those calls (`docs/moy_cart_api.md`,
"The actor world"). This doc adds the same loop in three dimensions: a Jet-like
renderer under a stripped-down Unity, with the blocks a kid already knows.

**It is a second engine, and is planned as one.** Godot is the model for living
with two: separate 2D and 3D node families and physics servers over one shared
core. Here the shared core is the console (§1).

**The engine owns the 3D world, and the cart talks to it in events.** Actors
live in C. Each frame the engine moves them, resolves their collisions and
draws them; a cart's code runs when something happens to an actor (a handler
per kind) and once a frame (its own `_update` and `_draw`). This is the native
entity world #85 declined for 2D and #44 declined as an engine that owns the
loop; the 3D world reopens it on purpose (2026-10-04), and the 2D world is
untouched.

**A cart that does not declare the world is untouched.** PICO-8 imports, every
2D cart, and code carts that draw 3D themselves with the pass verbs run exactly
as today; the engine never owns their frame.

**Simple beats fast, and fast means wasm.** There is no behaviour library, no
behaviour bytecode and no behaviour store. A game whose logic outgrows script
is a compiled cart drawing with the pass verbs, as the Jet carts draw with
`blit565`. A game bound by drawing gets faster from a lighter scene, not from
wasm (§4).

**Jet is not the console's engine.** The Jet carts stay compiled carts that
carry their own renderer (`ports/jet/README.md`): the console's route to Phong
shading and direct colour, and #227's case for native speed. The console's
raster may adapt Jet's integer span loops (§3.1); Jet's API, materials and
lights stay out of the spec.

The 2D actor world stays as it is: Python for Python carts
(`runtime/widgets.py`), a Lua mirror at zero upcalls a frame for Lua carts
(`runtime/lua_ext.py`). Nothing a 2D cart sees changes (§11).

## 2. Decisions this doc rests on

**The owner's, 2026-10-04:**

- **A stripped-down Unity, Blocks-first.** Kinds instead of prefabs, a flat
  list of actors, one camera, one sun.
- **A second engine, said plainly**, beside the 2D one.
- **Built after the kernel transition** (§7).
- **The engine owns the 3D world's actors**, reopening #85's Variant A and
  #44's line for the 3D world only. The cart keeps `_update` and `_draw`; the
  engine adds a step, its events and the world's draw around them (§3.3).
- **Simple over fast.** Per-kind event handlers and `frame` handlers, no
  behaviour library; wasm is the fast path.

**This doc's, open to §9:**

- **Immediate API, deferred execution, retained data.** A 3D pass records its
  calls into a frame list that its end renders, because banding the raster
  across cores needs the frame's triangles first. Models, the prepared level
  and the actors are kept between frames. A software renderer re-transforms
  every vertex and redraws every pixel each frame whatever the API, so nothing
  is saved by retaining the scene.
- **Three layers** (§3): a raster; pass verbs for code carts, Raylib-shaped;
  the event world for Blocks, Godot-shaped.
- **Whole-number maths in all three layers.** Conformance holds every host to
  identical pixels, and netplay sends inputs only; netplay already found what
  float width does across chips (`docs/netplay_v1.md` §5).
- **One call per object, never per triangle.** Geometry lives in assets
  addressed by name, as `map()` addresses the tilemap (SPEC.md §6.1: batching
  is the host's duty).
- **No new invalidation mechanism.** A pass redraws its viewport every frame;
  `docs/surface_model_v1.md` §8 stays closed.
- **One renderer for the game and the editor**, so what a kid places is what
  Play shows.
- **An optional extension, declared.** The 3D chapter is optional in the spec,
  as the WebAssembly binding is (SPEC.md §16). A cart declares it in its
  manifest; a host without it refuses at launch with a notice (SPEC.md §3.1)
  and stays conforming.
- **Allocate at launch, never grow.** The tier sizes its buffers from caps the
  cart declares, and the fit notice judges them at launch (§5).

## 3. The shape

### 3.1 Layer 1 — the raster (C, libmoy)

- **Into the console's canvas.** On the boards it holds RGB565 words, with the
  palette folded into one store table (`store[i] = wire[spal[pal[i]]]`,
  SOURCE: `native/moy_gfx/libmoy/moy_canvas.c`). A pass renders into the canvas
  current when it began, inside the clip rect current then: its viewport.
- **Colour order.** A shaded pixel is `wire[spal[ramp[pal[base]][step]]]`: the
  draw palette recolours the base colour, the ramp shades it, the screen
  palette and the wire follow. Each recorded call carries the `pal` and `palt`
  current when it was called, so one model in a pass can be recoloured. Per
  face this is a short table of the ramp's steps, looked up once a pixel.
- **Shading by palette ramps.** Each colour has a ramp of darker and lighter
  indices, a table with a MOY64 default that a cart may replace. Flat shading
  picks a step per face; Gouraud interpolates the step and dithers between
  steps with a screen-anchored 4×4 matrix, as `fillp` is anchored; fog walks
  the ramp towards a fog colour. (Proposal: colour is §9's first decision.)
- **Textures from the sprite sheet**, affine, addressed in sheet pixels as
  `sspr` addresses them. A sprite actor draws as a camera-facing cut-out.
- **Jet's span loops, adapted.** Jet's triangle and texture span code is
  integer (SOURCE: `ports/jet/jet/src/TriangleSpans.hpp`,
  `ports/jet/jet/src/TextureSpans.hpp`), but its per-triangle setup takes float
  reciprocals for speed on the LX7 (SOURCE: `ports/jet/jet/src/Renderer.cpp`,
  the edge and UV setup). The adaptation replaces those with fixed point and
  int64 intermediates, at a cost phase 0 measures; it is C99, palette-shaded,
  under Jet's MIT notice. Holding IEEE single precision bit-identical across
  the four tiers (no contraction, no fast-math) is a lever phase 0 may try,
  accepted only through the four-tier gate (§8).
- **A 16-bit depth buffer**, split per band (§5). The depth test and the tie
  rule are part of the spec, and opaque objects draw front to back in a sorted
  order the spec fixes, ties broken by call order, so early rejection works
  and pixels stay exact.
- **Two cart-chosen modes**, never a board's choice, because a board-chosen
  mode would change pixels:
  - **half width**, Jet's cheaper mode: the raster draws every other column
    and widens;
  - **interlaced**, ESP 88's mode and the largest single lever (§4): a pass
    draws one field of rows a frame and the other field keeps last frame's
    rows. The pass then owns its viewport, sky included: a 2D verb drawn under
    the viewport before the pass is lost on the field it draws. Fast sideways
    motion can comb, which is why the game chooses.
- **Bands across cores.** The pass's end transforms and culls on the cart's
  core, then rasterizes horizontal bands on the lanes the board gives, each
  band into its own rows and its own slice of the depth buffer. Bands match a
  single pass byte for byte, as the Jet carts' do (`tests/test_jet_cart.py`).
  A board with no lanes renders the bands in order, to the same pixels. The
  lanes are a new seam (§7).

### 3.2 Layer 2 — the pass verbs (immediate, Raylib-shaped)

Names are illustrative; the spec settles them. "The 3D verbs" stays the name
of `tri`, `trib`, `sspr` and `tline` until phase 2 renames that section.

```lua
function _draw()
  begin3d(px, py - 24, 16,  px, py, 4) -- eye, target: the pass begins
  map3d()                              -- the tilemap through its tile shapes
  model("ship", px, py, pz, turn)      -- an asset by name, one call
  bill(12, cx, cy, cz)                 -- sheet tile 12 as a cut-out
  end3d()                              -- the frame list renders here
  print("score "..score, 4, 4, 7)      -- the HUD, in the 2D verbs
end
```

- **World units are the 2D world's.** A map cell is 8 units, `x` and `y` lie on
  the map's plane as a 2D scene's rows do, `z` is height. A scene authored in 2D
  places its actors at the same spots in 3D.
- **`ray(...)` here tests the level only**: the first solid cell or tile shape
  along a ray. A ray that also hits actors is the world's (§3.3).
- **Numbers at the boundary.** A verb takes plain numbers and converts each to
  fixed point by one rule the spec states. `tline` asks for 16.16 integers; a
  kid's verb must not. Angles are integers in a fixed number of steps a turn,
  over a lookup table.
- **The pass rule.** Inside an open pass:
  - a 2D draw verb or a pixel read is refused with a message naming the rule;
  - `pal` and `palt` may change, and bind per recorded call;
  - a layer swap (`make_layer`'s canvas) is refused;
  - a pass still open at the end of `_draw` is ended by the console;
  - an error drops the pass with its frame.
- **The prepared level follows the map.** `mset` marks its cell, and the next
  pass re-prepares that cell's faces and its neighbours' before drawing.

### 3.3 Layer 3 — the event world (Godot-shaped)

**Declared.** A cart that declares the world in its manifest gets `actors`,
`touching`, `move_actor`, `remove_actor` and `scene` bound to it; a cart that
does not is a 2D cart, unchanged. Today those names are fixed by the Lua prelude
(`NOT_REGISTRABLE`, SOURCE: `runtime/lua_ext.py`); the binding chooses by the
declaration.

**The frame**, in an order the spec fixes:

1. the input snapshot, as today;
2. the cart's `_update`, which may be empty or absent;
3. the engine's step, in C: velocities, gravity, slides, contacts, timers;
4. the queued events, each to the handler of the actor's kind;
5. the engine draws the world;
6. the cart's `_draw`, the HUD, which may be empty or absent.

`pause_world()` stops steps 3 and 4; `step_world()` while paused runs one step,
which gives a code cart menus, cutscenes and turn-based play. The world steps on
the cart's tick; a `"fps": "free"` cart steps on real time and so cannot hold a
netplay match.

**Kinds, groups and bodies.** A kind is a tag, as in Blocks' per-kind scripts
(`docs/studio_2026-09.md` §5.5), and names its model or sprite, its body, its
box (the model's bounds unless set), whether gravity applies, and the groups it
belongs to ("enemy" holds slime, bat and ghost). Three bodies:
- **static**: the level's solid cells;
- **character**: moves by its velocity, slides along walls and floors, knows
  whether it stands on one, rides what it stands on, and pushes and is pushed
  by other characters (karts bump);
- **area**: a trigger.

No rigid bodies.

**Actors.** Each is a handle into the engine's table (index and generation,
`docs/native_kernel_2026-09.md` §4.3), seen by a handler as `self`: the engine's
fields (`x`, `y`, `z`, `vx`, `vy`, `vz`, `turn`, `kind`) and the cart's own
(`self.hp`), which live on the script side and never reach C. **The engine's
fields sync once a frame each way** — the script's writes before the step, the
engine's results after it — never one crossing per field read, so a handler
reads `self.x` at the cost of a script field, as the 2D Lua mirror does today. A
removed actor's handle is a no-op, as removing in 2D is harmless today; a handle
from another run is refused (proposal, §9).

**Handlers.** `on(kind or group, event, fn)` registers one: a decorator in
Python, a call in Lua, both the language's own prelude, like `on_net`. The
function never crosses into C: the engine queues each event as numbers (kind,
event, handles), and a dispatcher in the cart's runtime drains the queue and
calls the handlers, the events-not-callbacks shape of the kernel's ABI
(`docs/native_kernel_2026-09.md` §2.1). Blocks compiles each kind's event hats
to these registrations; `stage` names the cart itself, for messages.

```lua
on("coin", "touch", function(self, other)
  if other.kind ~= "player" then return end
  remove_actor(self)
  score = score + 1
end)

on("player", "frame", function(self)          -- counted: one call a frame
  self.vx = (btn("right") and 2 or 0) - (btn("left") and 2 or 0)
  if btnp("a") and on_floor(self) then self.vz = 6 end
end)
```

| event | when |
|---|---|
| `start` | the actor enters the world (scene load or spawn) |
| `touch`, `untouch` | a contact begins or ends; both actors' kinds hear it |
| `land`, `bump` | a character lands on a floor, or hits a wall |
| `timer` | `after(self, 2, "explode")`, `every(self, 1, "shoot")` |
| `receive` | `send("hurt")`, to every kind, group and the stage that listen |
| `press` | a button is pressed, for kinds that ask |
| `frame` | every frame, per actor: **counted** against the scene budget (§3.5) |

**Verbs over the world**, all C: `spawn(kind, x, y, z, fields)`,
`remove_actor`, `send`, `after`, `every`, `nearest(self, kind, r)`,
`within(self, r, kind)`, `count(kind)`, `ray(...)` against the level and the
actors, `on_floor`, a follow camera, `pause_world`, `step_world`; `move_actor`
and `touching` keep their names in 3D.

**Rules the spec fixes.** Events are delivered after the step in handle order,
the lower handle's kind first for a touch. A removed actor gets no further
events and its queued ones are dropped. A spawned actor exists at once, gets
`start` before the next step and has no part in this frame's contacts. A touch
handler registered with a kind filter ("when touched by player") queues only
those contacts. A handler error is the crash panel at the handler's line, as an
`_update` error is. The step fixes the slide axis order, the update order
(handle order), the order freed slots are reused, int64 intermediates for
products and squared lengths (a 16.16 square overflows int32 past 181 units),
and a speed cap or substeps so a body cannot cross a cell in one step.

**What it costs a cart.** A `frame` handler is one script call per actor per
frame: the same work a PICO-8 cart's `for e in enemies` loop does, and the same
ceiling (#85: tens of moving actors fine in Python, two hundred not; Lua about
twice that). Motion, gravity and collision run in C, where a PICO-8 cart writes
them in script. Events cost only when something happens.

### 3.5 The editors

- **The Model panel** (new) shares the Sprites panel's layout: tools in a
  column, the model's view, its own sheet strip for textures (Studio S11). At
  the T-Deck's 320×222 (Studio S5) it shows one view at a time: a voxel slice
  with a layer slider, or the 3D preview, toggled. Voxel grids are capped,
  meshed at load and flat-shaded.
- **Bake to sprites** renders a model from chosen angles into sheet tiles for
  any 2D cart: the first step `moybyte_console_plan_2026-07.md` §10.2 decided.
  It needs layer 1 where the baking happens, not on the board that plays the
  result: in the Studio on a board that keeps the raster, in the browser
  Studio, or in moy-spec's CLI.
- **The Scene panel's 3D view.** Placement stays top-down, which works with a
  trackball and on touch, with a height field in the props row. The fullscreen
  tier never splits (Studio §7), so on a T-Deck or Guition S3 the 3D preview is
  a toggle; on the P4 desk it sits beside placement.
- **The props row** gains model, body, box, gravity and groups for a kind. It
  is the row the Scene panel has, not the custom-field inspector Studio §11 cut.
- **The floor board's verdict.** The Studio shows whether the cart's scene fits
  the floor board's budget — triangles, covered pixels, and actors with a
  `frame` handler — so a cart authored on a P4 does not ship a scene the S3s
  cannot hold.
- **Blocks' 3D category**: an event hat per event ("when touched by", "when I
  land", "when I receive", "every 2 seconds", "every frame", the last one
  counted), and blocks for velocity, jump, turn, spawn, send, the queries and
  the follow camera.

The Studio stays a Python app (`docs/studio_2026-09.md` §9). Its 3D views draw
through the engine against a canvas handle (`docs/native_kernel_2026-09.md`
§2.1), with the app's memory, not a cart's (§5).

## 4. Speed

**The draw dominates; the logic costs what a PICO-8 cart's would.** A 3D frame
on these boards is bound by the raster and the fixed frame, and the event model
moves no draw cost either way. Going native puts the S3 and P4 families in the
same class.

**The reference scene is ESP 88**, the Jet film the compiled tier ships
(`ports/jet/README.md`): four of its twelve cuts are a racing game's scenes.
As the wasm cart plays them today — two cores, half width, interlaced, 320×198,
with a Phong car, rain, glows and reflections:

| cut | Guition S3 | Waveshare P4 | Guition P4 |
|---|---|---|---|
| 02 THE COURIER: a car on a scrolling street | 21.4 fps | 34.8 | 32.3 |
| 03 REAR VIEW: the camera low behind the car | 15.7 | 24.4 | 23.8 |
| 06 BOULEVARD: a skid turn, 6 traffic cars, 2 police | 16.3 | 26.3 | 25.3 |
| 07 PURSUIT: the chase | 16.7 | 28.6 | 27.0 |

(MEASURED, #158: the Guition S3 on 2026-09-29, the P4s on 2026-10-01.)

**From that to the console's renderer** (ESTIMATED; the S3, cut 07 and cut 03):

| step | cut 07 | cut 03 | source |
|---|---|---|---|
| native Jet, one core, PSRAM, 320×198, interlaced | 25.9 ms | 30.1 ms | MEASURED, #158, 2026-09-29 (native rung, headless) |
| a second core, ×1.25–1.6 | 16–21 | 19–24 | native Jet gained 1.48–1.69× headless; wasm's lanes 1.08–1.29× on glass beside the panel (#158, 2026-09-29) |
| progressive instead of interlaced, ×1.54 | 25–32 | 29–37 | Jet's native teapot at half width: 24.2 ms progressive, 15.7 interlaced (#158, 2026-09-29) |
| console, clears, widening and the cart's logic | +about 10 | +about 10 | the Guition S3's console in play, 6–7 ms (#158, 2026-09-27); `cls` 3.1 ms (#66); logic below |

| a racer as heavy as ESP 88 | S3 boards | P4 boards |
|---|---|---|
| progressive | ~21–29 fps | ~23–34 |
| interlaced | ~29–38 | ~31–43 |
| a lighter racer (flat ramps, fog, no rain or reflections; a raster two thirds of ESP 88's), progressive | ~30–35 | ~35–40 |

The P4 column runs the same steps from its own native rung (cut 07 19.6 ms,
cut 03 26.7 ms, #158, 2026-09-29), with about 11 ms outside the raster: the
Waveshare's fenced PPA scale is about 4.7 ms and `present_frame` about 1.5
(#158, 2026-10-01); the P4's shell cost is not measured.

**PREDICTED:** a lighter racer holds 30 fps progressive on the Guition S3, and
an ESP 88-weight one holds 30 interlaced. Phase 0 settles it (§8).

**The logic.** A Python verb call costs about 5–7 µs on the Guition S3
(MEASURED, #202, 2026-08-18) and a C verb from Lua about a microsecond (#66,
2026-09-09). Six karts' `frame` handlers, lap checkpoints and the field sync
are about 1–2 ms in Python: a few percent of the frame. The one design point
that could break that is per-field crossings, which the once-a-frame sync rules
out (§3.3).

**The fixed frame on the Guition S3**, beside the raster: the shell's share
of a drawn frame, about 6 ms (#66 body, 2026-09-11, diag on); `cls`, 3.1 ms;
a depth clear at half width, about half a `cls` (ESTIMATED from its 76,800
bytes against 153,600); and the panel's band pump on core 0, 7.3 ms a frame,
which the lanes share (#66 body, Guition S3 section). The S3 is fill-bound
(#66 and #167, 2026-07-28: "on the S3, paint fewer pixels"): half width cut
Jet's native Flat render by 19%, not 50% (#158, 2026-09-29), because the canvas
stays 320 wide in PSRAM.

**What wasm buys, and what it does not.** A compiled cart's logic runs near
native, so a game bound by logic — hundreds of actors, heavy AI — goes to wasm.
A racer is bound by drawing, and the draw is native C either way; its levers
are the scene's: fog and a short view, half width, interlacing, flat shading, a
HUD strip that shrinks the viewport (320×200 is 17% less fill), cut-out trees,
karts of sixty triangles or fewer.

**Not yet measured, and what decides the rest:** native Jet on two cores, on
glass, at 320×198, where the second core shares core 0 with the panel; and the
triangles each ESP 88 cut rasterizes, which the cart already writes to pmem
slot 2 (SOURCE: `ports/jet/esp88.moy/src/main.cpp`, `PM_TRIS`) and nobody has
read.

## 5. Memory

- **Two cases.** A Lua cart may run with the Python VM stopped (kernel sprint
  4); a Blocks or Python cart never does (§1). The S3 budget is judged for the
  second.
- **Every buffer is sized at launch from declared caps** and never grows.
  Jet's own queues keep the capacity of the busiest frame (`ports/jet/README.md`,
  "Memory"), and the S3s fail on fragmentation, not totals (#158,
  2026-10-01), so the tier asks once and the fit notice judges it then.
- **ESTIMATED, the items and their largest block:**

| item | size | largest block |
|---|---|---|
| depth buffer | 320 × 240 × 2 = 153,600 B; half width 76,800 B; interlaced, one field's rows | one band's rows: a quarter at four bands |
| frame list | about 40 B a transformed triangle × the cart's cap (1,024 → 40 KB) | the list |
| models | about 6 B a vertex and 10 B a face; a voxel model meshes to its surface, under the grid's cap | the largest model |
| prepared level | faces between solid and empty cells, under a cap on the map's size | the level |
| world | about 64 B an actor × the cart's cap (256 → 16 KB), the event queue at its cap | the table |
| the script side | each actor's mirror object and the cart's own fields, in the VM's heap | — |

- **Internal SRAM.** Native Jet keeps hot buffers there (#227); the T-Deck's
  low-water with radios up is a few KB (kernel §4.6), so no band buffer goes
  there on the T-Deck, and elsewhere only under the kernel's gate.
- **The editor's memory is the app's.** The Studio's 3D views hold their own
  depth buffer and frame list from the app's share, costed in phase 5.
- **Flash.** The raster, the pass verbs and the world are native text in every
  image that takes them, and again in the web bundle every image carries
  (kernel §5, item 4). The build prints each image's headroom; the P4 images
  have the least (#158). Every phase gates on the per-board floor kernel sprint
  0 sets.

**What each kind of cart gets.** A Lua or Python cart: all three layers. A
compiled cart: layers 1–2 through its import table, the world only once it is
promoted. The browser: everything, compiled by emscripten. moy-spec's own
players: layers 1–2.

## 7. Relation to the kernel transition

**The engine's work starts after the transition ends** (sprint 7; 2026-10-04).
Phase 0a is measurement only and touches nothing the kernel moves, so it can
run any time. The table says what each later phase builds on, so a phase that
could move earlier is visible; moving one is the owner's call.

| phase (§8) | builds on |
|---|---|
| 0a — ESP 88 measured | nothing: the shipped cart and a native build of its code |
| 0b — prototype | sprint 0's meters; the kernel's image, so the fixed frame it measures is the one that ships |
| 1 — spec | nothing in the kernel; moy-spec's own schedule |
| 2 — libmoy, tiers, lanes | sprint 3 (canvas ownership, present), sprint 4 (the cart path, moycore's glue), sprint 0's headroom floors |
| 3 — Model panel, bake | sprint 5 (canvas handles for apps), sprint 6 (the toolkit) |
| 4 — the event world | sprint 2 (handle tables), sprint 4 (the Lua superset rulings, the cart path), sprint 0's cart-available PSRAM threshold |
| 5 — Scene 3D view, props, verdict | sprints 5–7; the Studio's own order of work |

**The lanes are a new item no sprint holds.** Today they exist only inside a
wasm session (SOURCE: `native/moy_wasm/README.md`; the seam is
`native/moycore/libmoy/moy_wasm.h`'s `lane_go`/`lane_wait`), and an interpreted
or a Lua or Python session has none. Phase 2 lifts that seam into libmoy's
raster interface for every runtime, with the kernel's cart path as its moybyte
owner.

What the kernel gives the engine: PSRAM for Lua carts, one native loop on
every tier, handle tables, events instead of callbacks, a recovery floor for a
native crash, and one toolkit for the editors' chrome.

## 9. Decision points, all the owner's

1. **Colour.** Palette ramps with dithered Gouraud (proposed: `pal()`, fades
   and #44's indexed canvas hold; the look is a dithered PS1), or a
   direct-colour surface (the teapot's look; reopens #44 and the console plan's
   §10.1).
2. **Depth.** A banded depth buffer (proposed, if phase 0b shows it fits), or a
   back-to-front sort that costs no memory and gets some overlaps wrong. One
   rule for every host either way.
3. **Modelling.** Voxels (proposed: a slice editor works with a trackball, and
   it is the console plan's direction) or picoCAD-style faces, which need a
   pointer. Importers for both.
4. **Physics depth.** Boxes, the grid, gravity, sliding, riding and pushing
   (proposed), or slopes and capsules too.
5. **A removed actor's handle**: a no-op (proposed, as in 2D) or a loud error.
6. **Per-kind code's shape**: `on(...)` registrations in the cart's scripts
   (proposed: one namespace, so Python's globals work), or a file per kind,
   which Blocks' per-kind scripts already look like.
7. **A "while touching" event**, which fires every frame and would be counted
   like `frame`, or `touch` and `untouch` alone (proposed).
8. **The bar.** The drawn rate a 3D game must hold on the Guition S3 for the
   reference racer and platformer; phase 0b sizes the scene budget against it.
9. **Where 3D is authored.** At T-Deck size (proposed, Studio S5), or on the
   desk only, as #228 put it.
10. **Every board, or the P4s first.** §4 puts the two families in one class;
    phase 0 decides.

## 10. What can kill it

- **The floor board.** No scene budget worth having holds the bar on the
  Guition S3, even interlaced. Then the S3 boards deny the tier, and bake to
  sprites is what they get.
- **Memory with the VM up.** A Blocks 3D game's buffers do not fit beside the
  Python heap on the S3s.
- **The lanes.** The band pump leaves core 0 too little for the bands to pay.
- **The field sync.** A once-a-frame sync that costs more in Python than the
  handlers it serves.
- **Flash headroom** on the P4 images.
- **The editor.** A Model panel unusable at 320×222 with a trackball. Then 3D
  authoring is a desk feature, which Studio S5 forbids without a decision.
- **Determinism's price.** Fixed-point setup slower than Jet's floats by more
  than the budget allows.
- **Spec permanence.** A format that turns out wrong after carts use it.

## 11. Non-goals

- Jet's API, materials, lights or Phong shading in the spec.
- A behaviour library, behaviour bytecode or a behaviour store: simple over
  fast (§2). Nothing here rules one out later, as built-in handlers.
- The engine owning the frame of a cart that did not declare the world.
- Rigid bodies, joints, a transform hierarchy deeper than one attachment, an
  animation system, skeletal meshes, shaders, multiple lights, shadows,
  terrain sculpting.
- Loading glTF or OBJ on a console: one format of our own, with importers.
- A new invalidation mechanism, or caching any part of a 3D frame.
- Changing the 2D verbs, the 2D actor world, or anything a 2D cart sees.
- Blocks compiling to Lua (declined, `docs/moycore_direction.md` §3).
