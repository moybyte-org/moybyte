## 0. The thesis

**What makes a 3D editor easy is its loop: model a thing, place it on a map,
give it behaviour.** The Blocks tier offers that loop in 2D: the Scene panel
places actors, the actor world moves and removes them, `draw_scene()` draws
them, and the Actors blocks compile onto those calls (`docs/moy_cart_api.md`,
"The actor world"). This doc adds the same loop in three dimensions: a Jet-like
renderer under a stripped-down Unity, with the blocks a kid already knows.

**It is a second engine, and is planned as one.** Godot is the model for living
with two: separate 2D and 3D node families and physics servers over one shared
core. Here the shared core is the console (§1).

**The engine owns the 3D world, and the cart talks to it in events.** Actors
live in C. Each tick the engine moves them and resolves their collisions; a
cart's code runs when something happens to an actor (a handler per kind) and
in its own `_update` and `_draw`, which draws the world with `draw_scene()` as
a 2D cart does. This is the native entity world #85 declined for 2D and #44
declined as an engine that owns the loop; the 3D world reopens it on purpose
(2026-10-04), and the 2D world is untouched.

**A cart that does not declare the world is untouched.** PICO-8 imports, every
2D cart, and code carts that draw 3D themselves with the pass verbs run exactly
as today; no world name exists in their namespace.

**Simple beats fast, and fast means wasm.** There is no behaviour library, no
behaviour bytecode and no behaviour store. A game whose logic outgrows script
is a compiled cart drawing with the pass verbs, as the Jet carts draw with
`blit565`. A game bound by drawing gets faster from a lighter scene, not from
wasm (§4).

**Jet is not the console's engine.** The Jet carts stay compiled carts that
carry their own renderer (`ports/jet/README.md`): the console's route to Phong
shading and direct colour, and #227's case for native speed. The console's
raster may adapt Jet's integer span loops (§3.1); Jet's API, materials and
lights stay out of the spec.

**Blocks compiles to Python, and stays Python.** Blocks→Lua is declined
(`docs/moycore_direction.md` §3), so a Blocks 3D game runs with the Python VM
up, wherever the kernel can stop it for a Lua cart. Every budget below is
costed for that case (§4, §5).

The 2D actor world stays as it is: Python objects for Python carts
(`runtime/widgets.py`); for Lua carts a Lua-authoritative mirror whose actor
verbs run in Lua with no upcall, while `draw_scene()` crosses into Python and
pushes down what changed (`runtime/lua_ext.py`). Nothing a 2D cart sees
changes (§11).

## 2. Decisions this doc rests on

**The owner's, 2026-10-04:**

- **A stripped-down Unity, Blocks-first.** Kinds instead of prefabs, a flat
  list of actors, one camera, one sun.
- **A second engine, said plainly**, beside the 2D one.
- **Built after the kernel transition** (§7).
- **The engine owns the 3D world's actors**, reopening #85's Variant A and
  #44's loop line for the 3D world only. The cart keeps `_update` and `_draw`;
  the engine adds its step and its events to each tick (§3.3).
- **Simple over fast.** Per-kind event handlers and `frame` handlers, no
  behaviour library; wasm is the fast path.

**This doc's, open to §9:**

- **Immediate API, deferred execution, retained data.** A 3D pass records its
  calls into a frame list that its end renders, because banding the raster
  across cores needs the frame's triangles first. Models, the prepared level
  and the actors are kept between frames. A software renderer re-transforms
  every vertex and redraws every pixel each frame whatever the API, so nothing
  is saved by retaining the scene.
- **Three layers** (§3): a raster; pass verbs for code carts, Raylib-shaped;
  the event world for Blocks, Godot-shaped.
- **Whole-number maths in all three layers.** Conformance holds every host to
  identical pixels, and netplay sends inputs only; netplay already found what
  float width does across chips (`docs/netplay_v1.md` §5).
- **One call per object, never per triangle.** Geometry lives in assets
  addressed by name, as `map()` addresses the tilemap (SPEC.md §6.1: batching
  is the host's duty).
- **No new invalidation mechanism.** A pass redraws its viewport every frame;
  `docs/surface_model_v1.md` §8 stays closed.
- **One renderer for the game and the editor**, so what a kid places is what
  Play shows. The engine is a context with no statics, so the Studio's 3D view
  and a docked playtest each hold one.
- **Two declarations, both at launch.** The 3D extension (layers 1–2) is
  optional in the spec, as the WebAssembly binding is (SPEC.md §16). The world
  (layer 3) is moybyte's, its name reserved in SPEC.md so another host refuses
  a world cart at launch with a notice (SPEC.md §3.1) rather than at its first
  call.
- **Allocate at launch, never grow.** The tier sizes its buffers from caps and
  modes the cart declares, and the fit notice judges them at launch (§5).

## 3. The shape

### 3.1 Layer 1 — the raster (C, libmoy)

- **Into the console's canvas.** On the boards it holds RGB565 words, with the
  palette folded into one store table (`store[i] = wire[spal[pal[i]]]`,
  SOURCE: `native/moy_gfx/libmoy/moy_canvas.c`). A pass renders into the canvas
  current when it began, inside the clip rect current then: its viewport.
- **Colour order.** A shaded pixel is `wire[spal[ramp[pal[base]][step]]]`: the
  draw palette recolours the base colour, the ramp shades it, the screen
  palette and the wire follow. Each recorded call carries the `pal` and `palt`
  current when it was called, so one model in a pass can be recoloured. Per
  face this is a short table of the ramp's steps, looked up once a pixel.
- **Shading by palette ramps.** Each colour has a ramp of darker and lighter
  indices, a table with a MOY64 default that a cart may replace. Flat shading
  picks a step per face; Gouraud interpolates the step and dithers between
  steps with a screen-anchored 4×4 matrix, as `fillp` is anchored; fog walks
  the ramp towards a fog colour. (Proposal: colour is §9's first decision.)
- **Textures from the sprite sheet**, affine, addressed in sheet pixels as
  `sspr` addresses them. A sprite actor draws as a camera-facing cut-out.
- **Jet's span loops, adapted.** Jet's triangle and texture span code is
  integer (SOURCE: `ports/jet/jet/src/TriangleSpans.hpp`,
  `ports/jet/jet/src/TextureSpans.hpp`), but its per-triangle setup takes float
  reciprocals for speed on the LX7 (SOURCE: `ports/jet/jet/src/Renderer.cpp`,
  the edge and UV setup). The adaptation replaces those with fixed point and
  int64 intermediates, at a cost phase 0b measures; it is C99, palette-shaded,
  under Jet's MIT notice. Holding IEEE single precision bit-identical across
  the four tiers (no contraction, no fast-math) is a lever phase 0b may try,
  accepted only through the four-tier gate (§8).
- **A 16-bit depth buffer**, split per band (§5). The depth test and the tie
  rule are part of the spec, and opaque objects draw front to back in a sorted
  order the spec fixes, ties broken by call order, so early rejection works
  and pixels stay exact. ESP 88 draws by painter's order with no depth buffer
  (SOURCE: `ports/jet/examples/esp32-neon-film/main/firmware/JetConfig.hpp`),
  so no measurement yet covers this buffer's per-pixel cost (§4).
- **Two cart-declared modes**, never a board's choice, because a board-chosen
  mode would change pixels; declared at launch, because they size the buffers:
  - **half width**, Jet's cheaper mode: the raster draws every other column
    and widens;
  - **interlaced**, ESP 88's mode and the largest single lever (§4): a pass
    draws one field of rows a frame and the other field keeps last frame's
    rows. The pass then owns its viewport, sky included: a cart's declared
    background (#63) is not restored over the viewport, and a 2D verb drawn
    under it before the pass is lost on the field it draws. Fast sideways
    motion can comb, which is why the game chooses.
- **Bands across cores.** The pass's end transforms and culls on the cart's
  core, then rasterizes horizontal bands on the lanes the board gives, each
  band into its own rows and its own slice of the depth buffer, split by the
  pass's own row load rather than at a fixed height. Bands match a single pass
  byte for byte, as the Jet carts' do (`tests/test_jet_cart.py`). A board with
  no lanes renders the bands in order, to the same pixels. The lanes are a new
  seam (§7).

### 3.2 Layer 2 — the pass verbs (immediate, Raylib-shaped)

Names are illustrative; the spec settles them. "The 3D verbs" stays the name
of `tri`, `trib`, `sspr` and `tline` until phase 2 renames that section.

```lua
function _draw()
  begin3d(px, py - 24, 16,  px, py, 4) -- eye, target: the pass begins
  map3d()                              -- the tilemap through its tile shapes
  model("ship", px, py, pz, turn)      -- an asset by name, one call
  bill(12, cx, cy, cz)                 -- sheet tile 12 as a cut-out
  end3d()                              -- the frame list renders here
  print("score "..score, 4, 4, 7)      -- the HUD, in the 2D verbs
end
```

- **World units are the 2D world's.** A map cell is 8 units, `x` and `y` lie on
  the map's plane as a 2D scene's rows do, `z` is height. A scene authored in 2D
  places its actors at the same spots in 3D.
- **`ray(...)` tests the level only**: the first solid cell or tile shape along
  a ray. The world's own ray, which also hits actors, is a different name
  (§3.3), so a moybyte declaration never redefines a spec verb.
- **Numbers at the boundary.** A verb takes plain numbers and converts each to
  fixed point by one rule the spec states. `tline` asks for 16.16 integers; a
  kid's verb must not. Angles are integers in a fixed number of steps a turn,
  over a lookup table.
- **The pass rule.** Inside an open pass:
  - a 2D draw verb or a pixel read is refused with a message naming the rule;
  - `pal` and `palt` may change, and bind per recorded call;
  - a layer swap (`make_layer`'s canvas) is refused;
  - a pass still open at the end of `_draw` is ended by the console;
  - an error drops the pass with its frame.
- **The prepared level follows the map.** `mset` marks its cell, and the next
  pass re-prepares that cell's faces and its neighbours' before drawing.

### 3.3 Layer 3 — the event world (Godot-shaped)

**Declared, and bound only when declared.** A cart that declares the world
gets every world name — `on`, `spawn`, `send`, `after`, `every`, `count`,
`nearest`, `within`, `cast`, `on_floor`, `turn`, `forward`, `follow`,
`pause_world`, `step_world` — and `actors`, `touching`, `move_actor`,
`remove_actor` and `scene` bound to the world. A cart that does not gets none
of them: PICO-8's own `count` and a cart's global named `spawn`
(`system_carts/moybyte.hop_quest.moy`) are untouched. The world's names live in their
own list, not in `CART_VERBS`, so they become reserved Blocks names only in a
world cart. Today the actor names are fixed by the Lua prelude
(`NOT_REGISTRABLE`, SOURCE: `runtime/lua_ext.py`); the binding chooses by the
declaration.

**The frame.** The world runs inside the tick model (#217,
`runtime/tick_model.py`), which runs logic at the declared rate and draws on an
integer divisor of it. A world cart always declares a paced rate, 30 or 60
ticks a second; `"fps": "free"` is refused, because velocities are per tick.
**Per tick**, as many as the loop frame runs:

1. the input snapshot, and `net.pump`, as today;
2. the cart's `_update`, which may be empty or absent;
3. the engine's step, in C: velocities, gravity, slides, contacts, timers;
4. the queued events, each to its handlers.

**Per drawn frame**: the declared background's restore, outside an interlaced
viewport (§3.1), then the cart's `_draw`, which draws the world with
`draw_scene()` — a 3D pass from the world's camera — and the HUD after it,
exactly the "clear, draw scene, write score" order the 2D Actors blocks use.
The step and the events are logic: the scheduler's tick cost, and PERF's
`frame_split`, count them with `_update`. Under moycore's fused tick the four
steps run inside it, before `_draw` (SOURCE: `runtime/player.py`, `draw_next`);
after the kernel, in the kernel's native loop. `pause_world()` stops steps 3
and 4; `step_world()` while paused runs one step, which gives a code cart
menus, cutscenes and turn-based play.

**Kinds, groups and bodies.** A kind is a tag, as in the 2D rows' `.tag` and
Blocks' per-kind scripts (`docs/studio_2026-09.md` §5.5). It names its model or
sprite, its body, its box (the model's bounds unless set), whether gravity
applies, and the groups it belongs to ("enemy" holds slime, bat and ghost).
Three bodies:
- **static**: the level's solid cells;
- **character**: moves by its velocity, slides along walls and floors, knows
  whether it stands on one, rides what it stands on, and pushes and is pushed
  by other characters (karts bump);
- **area**: a trigger.

No rigid bodies.

**Actors have one owner: the engine.** Each actor is a handle into the
engine's table, seen by a handler as `self`. Its engine fields (`x`, `y`, `z`,
`vx`, `vy`, `vz`, `turn`, `tag`) are read and written through the handle, so a
read always sees the last write and a C verb's effect at once, and there is no
second copy to reconcile. Each access is a crossing (§4). A cart's own fields
(`self.hp`) live in a script-side table keyed by the handle and never reach C.
The proxy a handler receives is made once, at spawn, and reused, so the
dispatcher allocates nothing per event. The world is a per-run table, wiped at
each run's start, and a handle carries the run it belongs to: a removed
actor's handle is a no-op, as removing in 2D is harmless today; a handle from
another run is refused. These are the world's handles, a cart-level space,
not the kernel's (`docs/native_kernel_2026-09.md` §4.3).

**Motion verbs in C.** `turn(self, steps)`, `forward(self, n)` and
`face(self, other)` work in integer angles over a lookup table, and Blocks'
3D category compiles to them. The 2D helpers' float trig (SOURCE:
`runtime/blocks.py`, `_movesteps`) never runs in a world cart, so the step stays
bit-identical across hosts.

**Handlers.** `on(kind or group, event, [filter,] fn)` registers one: a
decorator in Python (`@on("coin", "touch", "player")`), a call in Lua. The
function never crosses into C: the engine queues each event as numbers (kind,
event, handles, an argument), and a dispatcher in the cart's runtime drains the
queue and calls the handlers. That is the events-not-callbacks shape the
kernel gives its app ABI (`docs/native_kernel_2026-09.md` §2.1), applied here
by this doc. A filter ("when touched by player") makes the engine queue only
matching contacts. Blocks compiles each kind's event hats to these
registrations; `stage` names the cart itself.

```lua
on("coin", "touch", "player", function(self, other)
  remove_actor(self)
  score = score + 1
end)

on("player", "frame", function(self)          -- counted: one call a tick
  self.vx = (btn("right") and 2 or 0) - (btn("left") and 2 or 0)
  if btnp("a") and on_floor(self) then self.vz = 6 end
end)
```

**The events, in the order the spec fixes.** After each step, classes are
delivered in this order; within a class by handle order, a touch to the lower
handle's kind first; for one actor, its kind's handler before its groups',
and the stage's last.

| order | event | when |
|---|---|---|
| 1 | `start` | the actor entered the world on the previous tick (scene load or spawn) |
| 2 | `timer` | `after(self, 2, "explode")` or `every(self, 1, "shoot")` came due, counted in ticks |
| 3 | `land`, `bump` | a character landed on a floor, or hit a wall |
| 4 | `touch`, `untouch` | a contact began or ended; both actors' kinds hear it |
| 5 | `press` | a button was pressed, with the player's index (`btn(name, p)`), for kinds that ask |
| 6 | `receive` | a `send("hurt")` from the previous tick, to every kind, group and the stage that listen |
| 7 | `frame` | every tick, per actor: **counted** against the scene budget (§3.5) |

`send` and `spawn` inside a handler take effect on the next tick, the same
one-tick hop the 2D broadcast mailbox uses (SOURCE: `runtime/blocks.py`), so no
drain feeds itself. A removed actor gets no further events and its queued ones
are dropped. A handler error is the crash panel at the handler's line, as an
`_update` error is. The event queue has a cap the cart declares; past it the
step stops queuing for that tick and the overflow is reported, the same way on
every host.

**The step's own rules.** The spec fixes the slide axis order, the update
order (handle order), the order freed slots are reused, int64 intermediates for
products and squared lengths (a 16.16 square overflows int32 past 181 units),
and a speed cap or substeps so a body cannot cross a cell in one step.

**Verbs over the world**, all C: `spawn(kind, x, y, z, fields)`,
`remove_actor`, `send`, `after`, `every`, `count(kind)`, `nearest(self, kind,
r)`, `within(self, r, kind)`, `cast(...)` (a ray against the level and the
actors), `on_floor`, `follow(actor, back, up)` for the camera, `pause_world`,
`step_world`; `move_actor` and `touching` keep their names in 3D.

**Blocks' existing hats map onto it.** "Every frame" is `_update` on the Stage
and `frame` on a kind; "when I hear" with `broadcast` is `receive` with `send`,
with the same one-tick hop; "when key pressed" is `press`.

**What it costs a cart.** A `frame` handler is one script call per actor per
tick, the shape of a PICO-8 cart's `for e in enemies` loop, and the same
ceiling (#85: tens of moving actors fine in Python, two hundred not; Lua about
twice that). Its field accesses cross into C where a PICO-8 cart reads its own
table, so a field costs more; motion, gravity and collision cost less, because
they run in C where a PICO-8 cart writes them in script. Events cost only when
something happens.

### 3.4 The data

All text, diffable, beside today's cart files. Names are placeholders: each
format is a spec decision and permanent.

| file | what | Godot's |
|---|---|---|
| a model per file | voxels or faces (§9), in the palette, textured from the sheet | a mesh resource |

| kinds | per tag: model, body, box, gravity, groups | a saved scene used as a prefab |

### 3.5 The editors

- **The Model panel** (new) shares the Sprites panel's layout: tools in a
  column, the model's view, its own sheet strip for textures (Studio S11). At
  the T-Deck's 320×222 (Studio S5) it shows one view at a time: a voxel slice
  with a layer slider, or the 3D preview, toggled. Voxel grids are capped,
  meshed at load and flat-shaded.
- **Bake to sprites** renders a model from chosen angles into sheet tiles for
  any 2D cart: the first step `moybyte_console_plan_2026-07.md` §10.2 decided.
  It needs layer 1 where the baking happens, not on the board that plays the
  result: in the Studio on a board that keeps the raster, in the browser
  Studio, or in moy-spec's CLI.
- **The Scene panel's 3D view.** Placement stays top-down, which works with a
  trackball and on touch, with a height field in the props row. The fullscreen
  tier never splits (Studio §7), so on a T-Deck or Guition S3 the 3D preview is
  a toggle; on the P4 desk it sits beside placement.
- **The props row** gains model, body, box, gravity and groups for a kind. It
  is the row the Scene panel has, not the custom-field inspector Studio §11 cut.
- **The floor board's verdict.** The Studio shows whether the cart's scene fits
  the floor board's budget — triangles submitted, covered pixels, the declared
  modes, and actors with a `frame` handler — so a cart authored on a P4 does
  not ship a scene the S3s cannot hold.
- **Blocks' 3D category**: an event hat per event ("when touched by", "when I
  land", "when I receive", "every 2 seconds", "every frame", the last counted),
  and blocks for velocity, jump, turn, forward, spawn, send, the queries and the
  follow camera.

The Studio stays a Python app (`docs/studio_2026-09.md` §9). Its 3D views draw
through their own engine context against a canvas handle
(`docs/native_kernel_2026-09.md` §2.1), with the app's memory, not a cart's
(§5).

## 4. Speed

**The draw dominates; the logic costs about what a PICO-8 cart's would.** A 3D
frame is bound by the raster and the console's fixed frame. **And the tick
model sets what "fast enough" means**: a 30-tick cart draws at 30, 15 or 10
frames a second, a 60-tick cart at 60, 30, 20 or 15 (`runtime/tick_model.py`).
So the budget is milliseconds per drawn frame, D, against a line: about 28 ms
to hold 30 drawn with margin, and for 20 drawn at a 60-tick rate, D plus the
two tick-only frames in its cycle within about 47 ms (a tick-only frame is
about 3 ms of the shell's loop stages, #66 body, 2026-09-11, plus the step and
the handlers).

**The reference scene is ESP 88**, the Jet film the compiled tier ships: its
COURIER, REAR VIEW, BOULEVARD and PURSUIT shots (#158's cuts 03, 04, 07 and 08)
are a racing game's scenes, measured on every board as the wasm cart plays
them (#158). The estimate starts from the same shots' **native** one-core
rungs: Jet as ESP 88 builds it, in PSRAM, 320×198, half width, interlaced,
headless.

| term | S3 boards | P4 boards | source |
|---|---|---|---|
| native one-core rung, PURSUIT / REAR VIEW | 25.9 / 30.1 ms | 19.6 / 26.7 ms | MEASURED, #158, 2026-09-29 |
| progressive instead of interlaced | ×1.5–1.8 | ×1.4–1.6 | Jet's native teapot, progressive over interlaced, across its shadings (#158, 2026-09-29) |
| a second core, on glass | ÷1.1–1.35 | ÷1.2–1.5 | ESP 88's racing shots gained 1.10–1.21 on the Guition S3 and 1.10–1.25 on the Guition P4 through lanes beside the panel; native Jet headless gained 1.48–1.69 (#158, 2026-09-29) |
| outside the raster: console, scan-out and widening, clears | +11–16 ms interlaced, +12–17 progressive | +14–18 ms | ESP 88's gap between frame and render, 17–24 ms on the Guition S3 (#158, 2026-09-29); the Guition P4's shell about 6 ms (#66 body, 2026-09-11); busy less render 14 ms on both P4s (#158, 2026-10-01) |
| not included | the depth buffer's per-pixel read, compare and write; full width (×1.24–1.53); 240 rows instead of 198 (+21%) | | §3.1; #158, 2026-09-29 |

**ESTIMATED, D per drawn frame**, the two shots' extremes; "lighter" is a
scenario, a racer whose raster is two thirds of ESP 88's, not a measured scene:

| scene | S3 boards | drawn | P4 boards | drawn |
|---|---|---|---|---|
| ESP 88's weight, interlaced | 30–43 ms | 20 at a 60 tick, else 15 | 27–40 ms | 30 at the light end, else 20 |
| ESP 88's weight, progressive | 41–66 ms | 15 | 32–54 ms | 20 or 15 |
| lighter, interlaced | 24–34 ms | 30 at the light end, else 20 | 23–33 ms | 30, else 20 at the heavy end |
| lighter, progressive | 31–50 ms | 20 or 15 | 26–42 ms | 30 at the light end, else 20 |

So a 3D racer is a 20-frame game on the S3 boards unless it is light and
interlaced, and a 30-frame game on the P4s when it is light or interlaced. The
P4 lead is smaller than the wasm cart shows, because the sandbox costs the S3
more.

**The reference racer phase 0b builds**, fixed before it is measured: half
width, a 320×198 viewport under a HUD strip, the depth buffer on, a 30- and a
60-tick build, six karts and a follow camera, and a triangle count two thirds
of PURSUIT's, which phase 0a counts.

**PREDICTED, for that racer:** on the Guition S3, interlaced, it draws 20 at a
60-tick rate (D + 2 tick-only frames ≤ 47 ms), and progressive draws 15 at a
30-tick rate; on a P4, interlaced, it holds 30 drawn (D ≤ 28 ms). Phase 0b's
perf guard confirms or refutes each line.

**The logic.** A crossing costs 1.5–3.6 µs from Lua on the S3 (#66,
2026-09-01) and 5–7 µs from Python at the cheapest verb (`pix`; `spr` 15.5,
`rect` 21.9; #202, 2026-08-18). Field access through the handle (§3.3) makes
each read or write one crossing: six karts' `frame` handlers at about a dozen
accesses each are under a millisecond in Python. At the 256-actor cap with
four accesses an actor a tick, it is about 1.5–3.7 ms in Lua and 5–7 ms in
Python, a tick: the ceiling a handler-heavy world pays, which phase 0b measures
at 30 and 60 ticks. A dispatcher that allocated per event would bring the
collector into the frame (a collection on the S3 has measured about
190–200 ms, #158, 2026-09-30); the dispatcher allocates nothing, and
`tests/test_frame_alloc.py` holds a world cart to it.

**The S3 is fill-bound** (#66 and #167, 2026-07-28: "on the S3, paint fewer
pixels"): half width cut Jet's native Flat render by 19%, not 50% (#158,
2026-09-29), because the canvas stays 320 wide in PSRAM, and the panel's band
pump takes 7.3 ms of core 0 a frame on the Guition S3 (#66 body, Guition S3
section), which the lanes share.

**What wasm buys, and what it does not.** A compiled cart's logic runs near
native, so a game bound by logic — hundreds of actors, heavy AI — goes to wasm.
A racer is bound by drawing, and the draw is native C either way; its levers
are the scene's: interlacing, half width, fog and a short view, flat shading, a
HUD strip that shrinks the viewport (320×200 is 17% less fill), cut-out trees,
karts of sixty triangles or fewer.

## 5. Memory

- **Two cases.** A Lua cart may run with the Python VM stopped (kernel sprint
  4); a Blocks or Python cart never does (§1). The S3 budget is judged for the
  second.
- **Every buffer is sized at launch from declared caps and modes** and never
  grows. Jet's own queues keep the capacity of the busiest frame
  (`ports/jet/README.md`, "Memory"), and the S3s fail on fragmentation, not
  totals (#158, 2026-10-01), so the tier asks once and the fit notice judges it
  then.
- **ESTIMATED, the items and their largest block:**

| item | size | largest block |
|---|---|---|
| depth buffer | 320 × 240 × 2 = 153,600 B; half width 76,800 B; one field's rows when interlacing is declared | one band's rows: a quarter at four bands |
| frame list | about 40 B a transformed triangle, plus each call's `pal`/`palt` state, × the cart's cap (1,024 → about 40 KB) | the list |
| models | about 6 B a vertex and 10 B a face; a voxel model meshes to its surface, under the grid's cap | the largest model |
| prepared level | faces between solid and empty cells, under a cap on the map's size | the level |
| world | about 64 B an actor × the cart's cap (256 → 16 KB); the event queue at its cap | the table |
| the script side | each actor's proxy and the cart's own fields, about 150–300 B an actor, in the VM's heap | — |

- **Internal SRAM.** Native Jet keeps hot buffers there (#227); the T-Deck's
  low-water with radios up is a few KB (kernel §4.6), so no band buffer goes
  there on the T-Deck, and elsewhere only under the kernel's gate.
- **The editor's memory is the app's.** The Studio's 3D views hold their own
  engine context, depth buffer and frame list from the app's share, costed in
  phase 5.
- **Flash.** The raster, the pass verbs and the world are native text in every
  image that takes them, and again in the web bundle every image carries
  (kernel §5, item 4). The build prints each image's headroom; every phase
  gates on the per-board floor kernel sprint 0 sets.

## 9. Decision points, all the owner's

1. **Colour.** Palette ramps with dithered Gouraud (proposed: `pal()`, fades
   and #44's indexed canvas hold; the look is a dithered PS1), or a
   direct-colour surface (the teapot's look; reopens #44 and the console plan's
   §10.1).
2. **Depth.** A banded depth buffer (proposed, if phase 0b shows its per-pixel
   cost fits), or a back-to-front sort that costs no memory and gets some
   overlaps wrong. One rule for every host either way.
3. **Modelling.** Voxels (proposed: a slice editor works with a trackball, and
   it is the console plan's direction) or picoCAD-style faces, which need a
   pointer. Importers for both.
4. **Physics depth.** Boxes, the grid, gravity, sliding, riding and pushing
   (proposed), or slopes and capsules too.
5. **A removed actor's handle**: a no-op (proposed, as in 2D) or a loud error.
6. **Per-kind code's shape**: `on(...)` registrations in the cart's scripts
   (proposed: one namespace, so Python's globals work), or a file per kind,
   which Blocks' per-kind scripts already look like.
7. **A "while touching" event**, which fires every tick and would be counted
   like `frame`, or `touch` and `untouch` alone (proposed).
8. **The bar.** The drawn rate a 3D game must hold, per board family; §4
   predicts 20 on the S3s and 30 on the P4s for the reference racer.
9. **Where 3D is authored.** At T-Deck size (proposed, Studio S5), or on the
   desk only, as #228 put it.
10. **Every board, or the P4s first**, decided from phase 0b against the bar.

## 10. What can kill it

- **The floor board.** Phase 0b's reference racer misses even 15 drawn on the
  Guition S3 interlaced, or the owner's bar is 30 there. Then the S3 boards
  deny the tier, and bake to sprites is what they get.
- **The depth buffer.** Its per-pixel cost on a fill-bound S3, which no
  measurement covers yet, pushes the scene budget below a useful racer.
- **Memory with the VM up.** A Blocks 3D game's buffers do not fit beside the
  Python heap on the S3s.
- **The lanes.** The band pump leaves core 0 too little for the bands to pay.
- **Field crossings.** A handler-heavy world in Python costs more than the
  frame can hold, at the counts kids actually use.
- **Flash headroom** on any image that takes the tier.
- **The editor.** A Model panel unusable at 320×222 with a trackball. Then 3D
  authoring is a desk feature, which Studio S5 forbids without a decision.
- **Determinism's price.** Fixed-point setup slower than Jet's floats by more
  than the budget allows.
- **Spec permanence.** A format that turns out wrong after carts use it.

## 11. Non-goals

- Jet's API, materials, lights or Phong shading in the spec.
- A behaviour library, behaviour bytecode or a behaviour store: simple over
  fast (§2). Nothing here rules one out later, as built-in handlers.
- Any world name in the namespace of a cart that did not declare the world.
- A world cart at `"fps": "free"`.
- Rigid bodies, joints, a transform hierarchy deeper than one attachment, an
  animation system, skeletal meshes, shaders, multiple lights, shadows,
  terrain sculpting.
- Loading glTF or OBJ on a console: one format of our own, with importers.
- A new invalidation mechanism, or caching any part of a 3D frame.
- Changing the 2D verbs, the 2D actor world, or anything a 2D cart sees.
- Blocks compiling to Lua (declined, `docs/moycore_direction.md` §3).
