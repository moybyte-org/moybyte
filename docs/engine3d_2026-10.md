# The 3D engine — a second engine under one console (2026-10)

**Status: DRAFT rev 1, 2026-10-04.** Nothing here is scheduled. The work starts
after the native kernel's transition (`docs/native_kernel_2026-09.md`), and §7
names, phase by phase, which of its sprints each piece waits on.
**Tracks:** #228 (3D for carts; this doc re-scopes it) · #224 (the kernel) ·
#158 (the compiled tier and the Jet measurements) · #66 (frame and per-verb
numbers) · #227 (native carts, Jet's own route to native speed).
**Claims carry the kernel doc's four labels** (MEASURED, SOURCE, ESTIMATED,
PREDICTED; its header defines them). The few numbers quoted are the ones an
argument turns on; their home is the issue cited.

---

## 0. The thesis

**What makes a 3D editor easy is its loop: model a thing, place it on a map,
give it behaviour.** The Blocks tier already offers that loop in 2D. The Scene
panel places actors, the actor world moves and removes them, `draw_scene()`
draws them, and the Actors blocks compile onto exactly those calls
(`docs/moy_cart_api.md`, "The actor world"). This doc adds the same loop in
three dimensions: a Jet-like renderer under a stripped-down Unity, with the
blocks a kid already knows.

**It is a second engine, and is planned as one** (2026-10-04). Godot is the
model for living with two: its 2D and 3D are separate node families with
separate physics servers, over one core that both share. Here the shared core
is the console. What 3D adds is its own renderer, world, formats, editor views
and spec chapter (§1).

**Jet is not the console's engine.** The Jet carts stay what
`ports/jet/README.md` says they are: compiled carts that carry their own
renderer, the console's route to Phong shading and direct colour, and #227's
case for native speed. The console's renderer may adapt Jet's integer span
loops as its inner loop (§3.1); Jet's API, materials and lights stay out of the
spec.

**PICO-8-style 3D stays possible and is not the answer.** `tri`, `tline` and
`sspr` (SPEC.md §6.1, §7.1) let a code cart write its own renderer, and picoCAD
is built that way. It is hard to write, and its per-frame loops run in script,
which is what made the raycaster slow (§4).

## 1. What is shared, and what is new

| shared with the 2D console | new for 3D |
|---|---|
| the `.moy` format, the `_init`/`_update`/`_draw` loop, input, audio, `pmem`, netplay's transport | a renderer in C (layer 1), tuned per board |
| the 2D verbs, which draw the HUD over the 3D frame | the 3D verbs (layer 2) |
| the palette, the sprite sheet, tile flags, the tilemap | a world simulation in C (layer 3): bodies, sliding, gravity, raycasts, touch events |
| the Studio, Blocks' editor, the Files panel | a model format and per-tile shapes, both permanent once in the spec |
| the store, OTA, signing, the board ports, the browser player | the Model panel and the Scene panel's 3D view |
| the Player, the tick model, the fit notice | a spec chapter, conformance goldens, and a perf pass per board |

The 2D actor world is about a hundred lines of Python (SOURCE:
`runtime/widgets.py`, `touching` and its overlap test). The 3D world is new
native code, not an extension of it.

## 2. Decisions this doc rests on

Taken in the design conversation of 2026-10-04 unless marked as a proposal;
§9 lists what is still the owner's to decide.

- **A stripped-down Unity, Blocks-first.** Kinds instead of prefabs, a flat
  list of actors instead of a node tree, one camera, one sun. Every Blocks
  concept keeps its meaning: an actor, a kind (its tag), a per-kind script, a
  scene, touching.
- **Immediate API, deferred execution, retained data.** A cart says each frame
  what to draw, as every moy verb does. The calls inside a 3D pass record into
  a frame list that the pass's close renders, because splitting the raster
  across cores needs the whole frame's triangles first (§3.1). Models, the
  level and the world's actors are loaded once and kept. In a software renderer
  every vertex is re-transformed and every pixel redrawn each frame whatever the
  API, so a retained scene would save nothing: the camera moves.
- **Three layers** (§3). A raster (Godot's rendering server, Raylib's `rlgl`);
  3D verbs, Raylib-shaped, for code carts; a world, Godot-shaped, for Blocks.
- **Whole-number maths in all three layers.** Conformance holds every host to
  identical pixels, and netplay sends inputs only, so two boards must compute
  the same world bit for bit. Netplay already found what float width does to
  that (`docs/netplay_v1.md` §5); a fixed-point world cannot drift.
- **One call per object, never per triangle.** Geometry lives in assets
  addressed by name, as `map()` addresses the tilemap. The Lua bridge passes
  numbers, not lists, and SPEC.md §6.1 already says batching is the host's
  duty (`docs/moy_cart_api.md`, "The batch verbs are gone").
- **No new invalidation mechanism.** A 3D pass redraws the frame, as a game's
  frame is redrawn today; `docs/surface_model_v1.md` §8 stays closed.
- **One renderer for the game and the editor.** The Studio's 3D views draw
  through the engine, so what a kid places is what Play shows.
- **A board takes or denies the tier** in its `board.toml`, with a reason, as it
  does the compiled tier's module. A cart that needs it on a board without it
  is refused with a notice, never a crash (SPEC.md §3.1's clean refusal).

## 3. The shape

### 3.1 Layer 1 — the raster (C, libmoy)

- **Triangles into the console's canvas.** On the boards that canvas holds
  RGB565 words with the palette resolved as each pixel is drawn (SOURCE:
  `native/moy_gfx/micropython.cmake`, `native/moy_gfx/libmoy/moy_canvas.c`).
  The 3D raster writes the same words through the same store table, so
  `pal()`, the screen palette and the 2D verbs compose with it unchanged.
- **Jet's span loops as the inner loop, adapted.** Jet's triangle and texture
  span code is integer-only (SOURCE: `ports/jet/jet/src/TriangleSpans.hpp`,
  `ports/jet/jet/src/TextureSpans.hpp`; its floats are in the camera and object
  setup). Adapted to C99 and to palette shading, under Jet's MIT notice.
- **Shading by palette ramps.** Each colour has a ramp of darker and lighter
  indices, a table with a default for MOY64 that a cart may replace. Flat
  shading picks one step per face. Gouraud interpolates the step across a span
  and dithers between steps with a screen-anchored 4×4 matrix, as `fillp`'s
  pattern is anchored. Distance fog is the same ramp walked towards a fog
  colour. All of it is a table lookup per pixel and lands in the palette, so
  it is exact on every host. (Proposal: the colour decision is §9's first.)
- **Textures from the sprite sheet**, affine, addressed in sheet pixels as
  `sspr` addresses them. A sprite actor draws as a camera-facing cut-out.
- **A 16-bit depth buffer** (Jet's teapot uses one: SOURCE,
  `ports/jet/README.md`, "Memory"). A cart may ask for half width, Jet's
  cheapest mode, which halves the buffer and the fill; that is a cart's
  choice, never a board's, because a board-chosen mode would change pixels.
- **Bands across the cores.** The pass's close transforms and culls on the
  cart's core, then rasterizes horizontal bands on as many lanes as the board
  gives, each band into its own rows. The compiled tier already runs a cart's
  `par` items this way, on lanes that take only what the display leaves
  (SOURCE: `native/moy_wasm/README.md`, "A cart's `par` items run on the
  session's lanes"), and the Jet carts hold their banded frame byte for byte to
  a single pass (`tests/test_jet_cart.py`). The renderer uses the same lanes; a
  board with none renders the bands in order on one core, to the same pixels.

### 3.2 Layer 2 — the 3D verbs (immediate, Raylib-shaped)

A pass opens with a camera and closes with the 2D camera's return; the HUD
follows in the 2D verbs. Names are illustrative; the spec settles them.

```lua
function _draw()
  cls(1)
  cam3d(px, py - 24, 16,  px, py, 4)  -- eye, target: opens the 3D pass
  map3d()                             -- the tilemap, extruded through its tile shapes
  model("ship", px, py, pz, turn)     -- an asset by name, one call
  bill(12, cx, cy, cz)                -- sheet tile 12 as a camera-facing cut-out
  cam3d()                             -- closes the pass: the frame renders here
  print("score "..score, 4, 4, 7)     -- the HUD, in the 2D verbs
end
```

- **World units are the 2D world's.** A map cell is 8 units, `x` and `y` lie
  on the map's plane exactly as a 2D scene's rows do, and `z` is height. A
  scene authored in 2D places its actors at the same spots in 3D.
- **Collision as plain functions over data**: `ray(...)` returns the first wall
  or actor along a ray; a box test answers overlap. They test the level and
  the world, never pixels.
- **The pass rule.** Inside a pass nothing has been drawn yet: a 2D verb
  called there is refused or deferred to after the pass (the spec picks one),
  and `pix()` reads only after the close. This is the one new rule the
  deferral adds.
- **Numbers at the boundary.** A verb takes plain numbers and converts each to
  fixed point by one rule the spec states. `tline` asks the cart for 16.16
  integers; a kid's verb must not.

### 3.3 Layer 3 — the world (Godot-shaped)

- **Actors live in C, held by handle.** A handle is an index plus a
  generation, refused when stale (`docs/native_kernel_2026-09.md` §4.3). A
  script holds integers; the world's data never crosses into a VM.
- **Kinds are the prefabs.** A kind names its model or sprite, its body, its
  box (from the model's bounds unless set), and whether gravity applies. Blocks
  already keeps a script per kind (`docs/studio_2026-09.md` §5.5).
- **Three bodies.** Static: the level's solid cells. Character: moves by
  sliding along walls and floors and reports whether it stands on one, the
  call most Godot games are built on. Area: a trigger, reporting what touches
  it. No rigid bodies.
- **The verbs a kid knows keep their names.** `move_actor` gains a `dz` and
  slides in a 3D world; `touching` tests 3D boxes; `remove_actor` and
  `actors(tag)` are unchanged; `on_floor`, `jump` and a follow camera are new.
  An Actors program written for 2D reads the same in 3D.
- **`draw_scene()` draws the world** through layer 2: the level, every actor's
  model or cut-out, from the world's camera. A Blocks cart never hands the
  engine geometry.
- **What runs per frame is C.** Moving, sliding, gravity, touch detection and
  drawing. Scripts receive the events and decide what they mean.

### 3.4 The data

All text, diffable, beside today's cart files. Names are placeholders: each
format is a spec decision and permanent (§9).

| file | what | Godot's |
|---|---|---|
| a model per file | voxels or faces (§9), in the palette, textured from the sheet | a mesh resource |
| tile shapes | tile id → cube, ramp, floor, or a model | a `MeshLibrary` |
| kinds | model, body, box, gravity | a saved scene used as a prefab |
| scene rows (`scenes/<name>.moyscene`) | gain `z`, a turn and a kind | the scene file |

### 3.5 The editors

- **The Model panel** (new). It shares the Sprites panel's layout: tools in a
  column, the model's view in the middle, its own sheet strip below for
  textures (as the Map keeps its own, Studio S11). It fits the T-Deck's
  320×222, because no panel may need more (Studio S5). **Bake to sprites**
  renders a model from chosen angles into sheet tiles for 2D carts: the first
  step `moybyte_console_plan_2026-07.md` §10.2 decided, kept here, and useful
  on a board that denies the 3D tier.
- **The Scene panel's 3D view.** Placement stays top-down, which works with a
  trackball and on touch, with a height field in the props row. A 3D preview
  sits beside it where the pane has room.
- **The inspector rows** for a kind: model, body, box, gravity.
- **A Blocks 3D category**: follow camera, turn, move forward, jump, on floor.
  The Actors category is reused as is.

The Studio stays a Python app (`docs/studio_2026-09.md` §9). Its 3D views draw
through the engine against a canvas handle, the shape the kernel gives app
drawing (`docs/native_kernel_2026-09.md` §2.1).

## 4. Speed

**The thesis: on these boards 3D is slow when per-frame loops run in script,
not because a renderer is not Jet.**

- **Native C, not the sandbox.** Jet's teapot (1,560 faces, SOURCE:
  `ports/jet/teapot.moy/teapot.obj`) renders on the T-Deck, one core,
  320×240, half width, interlaced, in 15.7 ms Flat and 22.1 ms Phong natively,
  against 29.7 and 38.1 ms as the wasm cart (MEASURED, #158, 2026-09-29). The
  console's renderer is native, so it competes with the first pair.
- **Two cores** bought native Jet 1.48–1.69× (MEASURED, #158, 2026-09-29),
  which is why the pass is deferred.
- **Fill.** The S3 fills 74 ns a pixel on wide spans and about 120 on narrow
  ones (MEASURED, #167, 2026-07-28). One 320×240 layer is 76,800 pixels: 5.7 to
  9.2 ms; at twice that for overdraw, 11 to 18 ms on one core (ESTIMATED from
  2D spans, not a 3D raster). The depth buffer's early reject and the lanes
  cut into it; half width halves it.
- **Crossings are not the cost.** A C verb called from Lua costs 1.65 µs on the
  T-Deck (MEASURED, #66, 2026-09-02): a hundred objects is 0.17 ms.
- **Script loops are the cost.** The 160-ray raycaster's frame took 45.5 ms on
  the S3, and its ray march alone measured 30 ms in Python and 15.8 ms in Lua,
  while the native fill was about a millisecond of the P4's frame (MEASURED,
  #66, 2026-07-28). Layer 3 exists so a Blocks game runs no such loop.
- **Collision is cheap when it is C.** Against the level, an actor reads the
  few cells under its box; against an actor, a box test is six comparisons.
  Nobody has measured collision here. #85 and #109 describe the 2D world's
  limit only in words, tens of actors fine and two hundred moving ones not,
  and that limit is a Python loop over every actor.

**PREDICTED: a scene of a few hundred triangles, a full screen of fill and a
few dozen actors holds 30 fps on the Guition S3 at half width, and more on the
P4s.** Phase 0 settles it (§8).

## 5. Memory

- **What the tier holds:** the depth buffer (320 × 240 × 2 = 150 KB, half that
  at half width), the frame list, each loaded model, the prepared level (faces
  only between solid and empty cells), and the world's actor table. Only the
  depth buffer is large.
- **It is cart memory.** It comes from the cart-available PSRAM the kernel's
  sprint 0 defines (`docs/native_kernel_2026-09.md` §6), and a cart that does
  not fit gets the fit notice, as a compiled cart does. A Lua cart running with
  the Python VM stopped (sprint 4) is what frees that room on the S3s.
- **Internal SRAM.** Native Jet keeps its hot buffers in internal SRAM (#227).
  The kernel's rule is PSRAM unless latency-bound, gated on internal free and
  low-water with WiFi and BLE up (`docs/native_kernel_2026-09.md` §4.6). A band
  buffer in internal SRAM is a latency-bound case to argue with a measurement,
  per board, under that gate.
- **Flash.** The renderer and the world are native text in every image, and
  again inside the web bundle that every image carries (kernel §5, item 4).
  Every phase gates on the per-board headroom floor sprint 0 sets.

## 7. Relation to the kernel transition

The kernel's non-goals include **any change to the cart API**
(`docs/native_kernel_2026-09.md` §9), and its sprints move the very things this
engine plugs into. So the work follows it. What each phase waits on:

| phase (§8) | waits on | because |
|---|---|---|
| 0 — the prototype | nothing the kernel moves | a native bench outside the firmware; scheduled after the transition by plan, earlier only by the owner's call |
| 1 — the spec | the transition (no cart API change during it) | §9 of the kernel doc |
| 2 — libmoy and the tiers | sprint 3 (the glass: canvas ownership, present) and sprint 4 (the cart path: loop, moycore's glue) | the pass renders into a canvas the kernel owns, from a loop the kernel drives |
| 2 — the lanes | the kernel taking the lanes over from `native/moy_wasm` | `par` and the renderer share them; today they live in the compiled tier's engine |
| 3 — the world | sprint 4's ruling on the scene and actor verbs | they are Python trampolines today (kernel §2.3); the 3D world takes the same native home and handle shape the 2D world gets |
| 4 — the editors | sprint 5 (canvas handles for apps), sprint 6 (the native toolkit), and the Studio's own order of work | the 3D views draw through a handle; the panels are toolkit kinds |

What the kernel gives this engine: PSRAM for carts (the VM stopped), one native
loop on every tier, handles, a recovery floor for a native crash, and one
toolkit for the editors' chrome.

## 9. Decision points, all the owner's

1. **Colour.** Palette ramps with dithered Gouraud (proposed: `pal()`, fades
   and #44's indexed canvas hold; the look is a dithered PS1) or a direct-colour
   3D surface (the teapot's look; reopens #44 and the console plan's §10.1).
2. **Depth.** A depth buffer (proposed, if phase 0 shows it fits the floor
   board) or a back-to-front sort that costs no memory and gets some overlaps
   wrong. Either way it is one rule for every host.
3. **Modelling.** Voxels (proposed: the sprite editor with a layer slider,
   usable on a T-Deck, and the console plan's own direction) or picoCAD-style
   faces, which need a pointer. Importers for both either way.
4. **Physics depth.** Boxes, the grid, gravity and on-floor (proposed), or
   slopes and capsules too.
5. **Layer 3's home.** moybyte first and promoted later (proposed), or moy-spec
   from the start.
6. **Phase 0's timing.** After the transition (the plan), or earlier, since it
   touches nothing the kernel moves.
7. **Every board, or the P4s first.** Decided from phase 0's numbers.

## 10. What can kill it

- **The floor board.** If phase 0 misses the owner's bar on the Guition S3,
  the tier is the P4s and the browser, the S3 boards deny it, and bake to
  sprites is what they get.
- **Memory.** The depth buffer and the world not fitting the cart-available
  PSRAM on the S3s, even with the VM stopped.
- **Flash headroom** on the P4 images, where it is tightest.
- **The editor.** A Model panel that cannot be made usable at 320×222 with a
  trackball. Then 3D authoring is a desk feature, which Studio S5 forbids
  without a decision.
- **Spec permanence.** A format that turns out wrong after carts use it.

## 11. Non-goals

- Jet's API, materials, lights or Phong shading in the spec.
- Rigid bodies, joints, a transform hierarchy deeper than one attachment, an
  animation system, skeletal meshes, shaders, multiple lights, shadows,
  terrain sculpting.
- Loading glTF or OBJ on a console: one format of our own, with importers.
- A new invalidation mechanism, or caching any part of a 3D frame.
- Changing the 2D verbs, the 2D actor world, or anything a 2D cart sees.
