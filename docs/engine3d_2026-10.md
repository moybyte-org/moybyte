## 0. The thesis

**What makes a 3D editor easy is its loop: model a thing, place it on a map,
give it behaviour.** The Blocks tier offers that loop in 2D: the Scene panel
places actors, the actor world moves and removes them, `draw_scene()` draws
them, and the Actors blocks compile onto those calls (`docs/moy_cart_api.md`,
"The actor world"). This doc adds the same loop in three dimensions: a Jet-like
renderer under a stripped-down Unity, with the blocks a kid already knows.

**It is a second engine, and is planned as one** (2026-10-04). Godot is the
model for living with two: separate 2D and 3D node families and physics
servers over one shared core. Here the shared core is the console (§1).

**The cart keeps the loop.** #44 declined an engine that owns the loop, and #85
chose data-only scenes over a native entity loop for that reason (#85 §5 and
its decision log). The 3D world here is the route #85 itself named for later:
native bulk verbs over a native actor table, which the block compiler emits
into the loop it already generates. What it does reopen is #85's "per-entity
work in C, deferred by design", for the 3D world only; that is §9's first
decision.

**Jet is not the console's engine.** The Jet carts stay compiled carts that
carry their own renderer (`ports/jet/README.md`), the console's route to Phong
shading and direct colour, and #227's case for native speed. The console's
raster may adapt Jet's integer span loops (§3.1); Jet's API, materials and
lights stay out of the spec.

**PICO-8-style 3D stays possible and is not the answer.** `tri`, `tline` and
`sspr` (SPEC.md §6.1, §7.1) let a code cart write its own renderer, as picoCAD
does. It is hard to write, and its per-frame loops run in script (§4).

**Blocks compiles to Python, and stays Python.** Blocks→Lua is declined
(`docs/moycore_direction.md` §3), and the compiled helpers mutate actor rows and
use float trig (SOURCE: `runtime/blocks.py`). So a Blocks 3D game runs with the
Python VM up, wherever the kernel can stop it for a Lua cart. Every budget
below is costed for that case (§4, §5).

The 2D actor world stays as it is: Python for Python carts
(`runtime/widgets.py`), a Lua mirror at zero upcalls a frame for Lua carts
(`runtime/lua_ext.py`). Nothing a 2D cart sees changes (§11).

## 2. Decisions this doc rests on

The design conversation of 2026-10-04 set the first two; the rest are this
doc's proposals, open to §9.

- **A stripped-down Unity, Blocks-first.** Kinds instead of prefabs (a kind is
  a tag, as in Blocks' per-kind scripts, `docs/studio_2026-09.md` §5.5), a flat
  list of actors, one camera, one sun.
- **Built after the kernel transition** (§7).
- **Immediate API, deferred execution, retained data.** A cart says each frame
  what to draw. The calls inside a 3D pass record into a frame list that the
  pass's end renders, because banding the raster across cores needs the frame's
  triangles first. Models, the prepared level and the world's actors are kept
  between frames. A software renderer re-transforms every vertex and redraws
  every pixel each frame whatever the API, so a retained scene saves nothing.
- **Three layers** (§3): a raster; pass verbs for code carts, Raylib-shaped;
  a world for Blocks, Godot-shaped, as bulk verbs the cart's loop calls.
- **Whole-number maths in all three layers.** Conformance holds every host to
  identical pixels, and netplay sends inputs only. Netplay already found what
  float width does across chips (`docs/netplay_v1.md` §5).
- **One call per object, never per triangle.** Geometry lives in assets
  addressed by name, as `map()` addresses the tilemap (SPEC.md §6.1: batching
  is the host's duty).
- **No new invalidation mechanism.** A pass redraws its viewport every frame;
  `docs/surface_model_v1.md` §8 stays closed.
- **One renderer for the game and the editor**, so what a kid places is what
  Play shows.
- **An optional extension, declared.** The 3D chapter is optional in the spec,
  as the WebAssembly binding is (SPEC.md §16). A cart declares it in its
  manifest; a host without it refuses at launch with a notice (SPEC.md §3.1),
  never at the first 3D call, and stays conforming.
- **Allocate at launch, never grow.** The tier sizes its buffers from caps the
  cart declares, and the fit notice judges them at launch (§5).

## 3. The shape

### 3.1 Layer 1 — the raster (C, libmoy)

- **Into the console's canvas.** On the boards it holds RGB565 words, with the
  palette folded into one store table (`store[i] = wire[spal[pal[i]]]`,
  SOURCE: `native/moy_gfx/libmoy/moy_canvas.c`). A pass renders into the canvas
  current when it began, inside the clip rect current then: its viewport.
- **Colour order.** A shaded pixel is `wire[spal[ramp[pal[base]][step]]]`: the
  draw palette recolours the base colour, the ramp shades it, the screen
  palette and the wire follow. Each recorded call carries the `pal` and `palt`
  current when it was called, so one model in a pass can be recoloured. Per
  face this is a short table of the ramp's steps, looked up once a pixel.
- **Shading by palette ramps.** Each colour has a ramp of darker and lighter
  indices, a table with a MOY64 default that a cart may replace. Flat shading
  picks a step per face; Gouraud interpolates the step and dithers between
  steps with a screen-anchored 4×4 matrix, as `fillp` is anchored; fog walks
  the ramp towards a fog colour. (Proposal: colour is §9's second decision.)
- **Textures from the sprite sheet**, affine, addressed in sheet pixels as
  `sspr` addresses them. A sprite actor draws as a camera-facing cut-out.
- **Jet's span loops, adapted.** Jet's triangle and texture span code is
  integer (SOURCE: `ports/jet/jet/src/TriangleSpans.hpp`,
  `ports/jet/jet/src/TextureSpans.hpp`), but its per-triangle setup takes float
  reciprocals for speed on the LX7 (SOURCE: `ports/jet/jet/src/Renderer.cpp`,
  the edge and UV setup). The adaptation replaces those with fixed point and
  int64 intermediates, at a cost phase 0 measures; it is C99, palette-shaded,
  under Jet's MIT notice. Holding IEEE single precision bit-identical across
  the four tiers (no contraction, no fast-math) is a lever phase 0 may try,
  accepted only through the four-tier gate (§8).
- **A 16-bit depth buffer**, split per band (§5). The depth test and the tie
  rule are part of the spec, and opaque objects draw front to back in a sorted
  order the spec fixes, ties broken by call order, so early rejection works
  and pixels stay exact.
- **Half width is a cart's choice** (Jet's cheaper mode), never a board's,
  because a board-chosen mode changes pixels. Interlacing, Jet's cheapest, is
  not offered: it leaves the other field's rows on the canvas between frames.
- **Bands across cores.** The pass's end transforms and culls on the cart's
  core, then rasterizes horizontal bands on the lanes the board gives, each
  band into its own rows and its own slice of the depth buffer. Bands match a
  single pass byte for byte, as the Jet carts' do (`tests/test_jet_cart.py`).
  A board with no lanes renders the bands in order, to the same pixels. The
  lanes are a new seam (§7).

### 3.2 Layer 2 — the pass verbs (immediate, Raylib-shaped)

Names are illustrative; the spec settles them. "The 3D verbs" stays the name
of `tri`, `trib`, `sspr` and `tline` until phase 2 renames that section.

```lua
function _draw()
  cls(1)
  begin3d(px, py - 24, 16,  px, py, 4) -- eye, target: the pass begins
  map3d()                              -- the tilemap through its tile shapes
  model("ship", px, py, pz, turn)      -- an asset by name, one call
  bill(12, cx, cy, cz)                 -- sheet tile 12 as a cut-out
  end3d()                              -- the frame list renders here
  print("score "..score, 4, 4, 7)      -- the HUD, in the 2D verbs
end
```

- **World units are the 2D world's.** A map cell is 8 units, `x` and `y` lie on
  the map's plane as a 2D scene's rows do, `z` is height. A scene authored in 2D
  places its actors at the same spots in 3D.
- **`ray(...)` here tests the level only**: the first solid cell or tile shape
  along a ray. Rays that hit actors are the world's (§3.3).
- **Numbers at the boundary.** A verb takes plain numbers and converts each to
  fixed point by one rule the spec states. `tline` asks for 16.16 integers; a
  kid's verb must not. Angles are integers in a fixed number of steps a turn,
  over a lookup table.
- **The pass rule.** Inside an open pass:
  - a 2D draw verb or a pixel read is refused with a message naming the rule;
  - `pal` and `palt` may change, and bind per recorded call;
  - a layer swap (`make_layer`'s canvas) is refused;
  - a pass still open at the end of `_draw` is ended by the console;
  - an error drops the pass with its frame.
- **The prepared level follows the map.** `mset` marks its cell, and the next
  pass re-prepares that cell's faces and its neighbours' before drawing.

### 3.3 Layer 3 — the world (Godot-shaped, the cart's loop)

- **The world is selected by the manifest.** A cart that declares the 3D world
  gets `actors`, `touching`, `move_actor` and `remove_actor` bound to it; a
  cart that does not is a 2D cart, unchanged. Today those names are fixed by
  the Lua prelude (`NOT_REGISTRABLE`, SOURCE: `runtime/lua_ext.py`); the
  binding chooses by the declaration.
- **Actors live in a native table**, each named by a handle (index and
  generation, `docs/native_kernel_2026-09.md` §4.3). A removed actor's handle
  is a no-op wherever it is passed, as removing in 2D is harmless today; a
  handle from another run is refused (proposal, §9). How rows appear to Python
  and Lua, read from the table without a crossing per field and iterated
  without a list built per call, is phase 1's first question.
- **Kinds are the prefabs.** A kind names its model or sprite, its body, its
  box (the model's bounds unless set), and whether gravity applies.
- **Three bodies.** Static: the level's solid cells. Character: moves by
  sliding along walls and floors and knows whether it stands on one. Area: a
  trigger. No rigid bodies.
- **Bulk verbs, called from the cart's loop.** `step_world()` moves every body
  by its velocity, applies gravity and resolves slides; `touches(kind, kind)`
  returns this frame's contacts. The block compiler emits them into the
  `_update` it generates, so a Blocks program's per-frame Python is a loop over
  contacts (usually none) and the player's input, not over every actor. A code
  cart calls them itself. This is #85 §5's "native bulk verb" swap, made for
  3D.
- **The verbs a kid knows keep their names.** `move_actor` gains a `dz` and
  slides; `touching` tests 3D boxes; `remove_actor` and `actors(tag)` are
  unchanged; turn, move forward, jump and on-floor are new C verbs over integer
  angles, replacing the float trig the 2D helpers use.
- **`draw_scene()` draws the world** through layer 2: the level, every actor's
  model or cut-out, from the world's camera. A Blocks cart hands the engine no
  geometry.
- **Determinism is specified, not hoped for.** The spec fixes the slide axis
  order, the actor update order (handle order), the order freed handle slots
  are reused, int64 intermediates for products and squared lengths (a 16.16
  square overflows int32 past 181 units), and a speed cap or substeps so a body
  cannot cross a cell in one step.

### 3.4 The data

All text, diffable, beside today's cart files. Names are placeholders: each
format is a spec decision and permanent.

| file | what | Godot's |
|---|---|---|
| a model per file | voxels or faces (§9), in the palette, textured from the sheet | a mesh resource |
| tile shapes | tile id → cube, ramp, floor, or a model | a `MeshLibrary` |
| kinds | per tag: model, body, box, gravity | a saved scene used as a prefab |
| scene rows (`scenes/<name>.moyscene`) | optional `z` and `turn`, absent from every 2D scene, so a 2D cart's rows are unchanged; read strictly, under the no-migrations rule (CLAUDE.md, 2026-09-07) | the scene file |

### 3.5 The editors

- **The Model panel** (new) shares the Sprites panel's layout: tools in a
  column, the model's view, its own sheet strip for textures (Studio S11). At
  the T-Deck's 320×222 (Studio S5) it shows one view at a time: a voxel slice
  with a layer slider, or the 3D preview, toggled. Voxel grids are capped,
  meshed at load and flat-shaded.
- **Bake to sprites** renders a model from chosen angles into sheet tiles for
  any 2D cart: the first step `moybyte_console_plan_2026-07.md` §10.2 decided.
  It needs layer 1 where the baking happens, not on the board that plays the
  result: in the Studio on a board that keeps the raster, in the browser
  Studio, or in moy-spec's CLI.
- **The Scene panel's 3D view.** Placement stays top-down, which works with a
  trackball and on touch, with a height field in the props row. The fullscreen
  tier never splits (Studio §7), so on a T-Deck or Guition S3 the 3D preview is
  a toggle; on the P4 desk it sits beside placement.
- **The props row** gains model, body, box and gravity for a kind. It is the
  row the Scene panel has, not the custom-field inspector Studio §11 cut.
- **The floor board's verdict.** The Studio shows whether the cart's scene fits
  the floor board's budget (§4), so a cart authored on a P4 at full width does
  not ship a scene the S3s cannot hold.
- **A Blocks 3D category**: follow camera, turn, move forward, jump, on floor,
  and "when kind touches kind" over `touches`.

The Studio stays a Python app (`docs/studio_2026-09.md` §9). Its 3D views draw
through the engine against a canvas handle (`docs/native_kernel_2026-09.md`
§2.1), with the app's memory, not a cart's (§5).

## 4. Speed

**On the S3 boards a 3D frame is bound by fill and by the fixed frame; on every
board it is slow when per-frame loops run in script.** The design answers the
second; the first sets a scene budget.

The floor board's frame, terms that may overlap (Jet's render clears its own
buffers):

| term | figure | source |
|---|---|---|
| raster, teapot (1,560 faces) at half width, progressive, one core, Flat / Gouraud | 24.2 / 28.3 ms on the T-Deck, headless | MEASURED, #158, 2026-09-29 (native rung f) |
| what lanes bought that render on the Guition S3 | 1.26–1.38× (ESP 88: 1.08–1.29×; the setup stays serial) | MEASURED, #158, 2026-09-29 (`par`) |
| the shell, per drawn frame, Guition S3 | about 6 ms (diag on; the kernel changes it) | MEASURED, #66 body, 2026-09-11 |
| `cls`, Guition S3 | 3.1 ms | MEASURED, #66 body, per-verb table |
| depth clear at half width | about half a `cls` (76,800 B against 153,600) | ESTIMATED |
| the panel's band pump on core 0, Guition S3 | 7.3 ms a frame, competing with the lanes | MEASURED, #66 body, Guition S3 section |
| the Blocks program's Python | not measured for 3D | phase 0 |

**ESTIMATED:** 24.2 ms ÷ 1.26–1.38 is 17.5–19.2 ms; with the shell, `cls` and
the depth clear, 28–30 ms before the Blocks logic. A teapot-scale scene at half
width is at the edge of 30 fps on the Guition S3 with today's shell.

**What the S3 evidence says.** The raycaster's S3 frame spent 5.7 ms on its
background and 3.6 ms on its walls, and #66 concluded "on the S3, paint fewer
pixels" (MEASURED, #167 and #66, 2026-07-28). Half width cut Jet's native Flat
render by 19%, not 50% (30.0 → 24.2 ms, #158, 2026-09-29), because the canvas
stays 320 wide in PSRAM. A 3D pixel costs more than a rect's: a depth read
and write, interpolation, a ramp lookup and a dither; `fillp`'s per-pixel
branch alone costs the S3s 34–35% (#66 body, 2026-09-03).

**What the design does about it.**
- **One call per object.** A C verb called from Lua costs about a microsecond
  (MEASURED, #66, 2026-09-09); Blocks pays Python's call cost, per contact and
  per input, not per actor.
- **Script loops leave the frame.** The 160-ray raycaster's march measured
  30 ms in Python and 15.8 ms in Lua (#66, 2026-07-28); `step_world()` and
  `touches` are what keep a Blocks game out of that.
- **A scene budget.** Covered pixels and triangles per pass are what the S3
  pays for. A viewport smaller than the screen (HUD bars, a framed window) is
  the cheapest lever, and the Studio's verdict (§3.5) holds a cart to it.

**PREDICTED:** a scene budget exists, in triangles and covered pixels, at
which a Blocks 3D game holds 30 fps on the Guition S3 at half width; phase 0
finds it, or shows the bar must be lower. The P4s are not assumed faster: their
cost outside the render is larger (ESP 88: 25–30 ms a frame; the Waveshare's
PPA scale about 4.7 ms; #158, 2026-09-29 and 2026-10-01), and a frame drawn
into the canvas does not take the compiled carts' zero-copy path.

## 5. Memory

- **Two cases.** A Lua cart may run with the Python VM stopped (kernel sprint
  4); a Blocks or Python cart never does (§1). The S3 budget is judged for the
  second.
- **Every buffer is sized at launch from declared caps** and never grows.
  Jet's own queues keep the capacity of the busiest frame (`ports/jet/README.md`,
  "Memory"), and the S3s fail on fragmentation, not totals (#158,
  2026-10-01), so the tier asks once and the fit notice judges it then.
- **ESTIMATED, the items and their largest block:**

| item | size | largest block |
|---|---|---|
| depth buffer | 320 × 240 × 2 = 153,600 B; half width 76,800 B | one band's rows: a quarter at four bands |
| frame list | about 40 B a transformed triangle × the cart's cap (1,024 → 40 KB) | the list |
| models | about 6 B a vertex and 10 B a face; a voxel model meshes to its surface, under the grid's cap | the largest model |
| prepared level | faces between solid and empty cells, under a cap on the map's size | the level |
| world | about 64 B an actor × the cart's cap (256 → 16 KB) | the table |

- **Internal SRAM.** Native Jet keeps hot buffers there (#227); the T-Deck's
  low-water with radios up is a few KB (kernel §4.6), so no band buffer goes
  there on the T-Deck, and elsewhere only under the kernel's gate.
- **The editor's memory is the app's.** The Studio's 3D views hold their own
  depth buffer and frame list from the app's share, costed in phase 5.
- **Flash.** The raster, the pass verbs and the world are native text in every
  image that takes them, and again in the web bundle every image carries
  (kernel §5, item 4). The build prints each image's headroom; the P4 images
  have the least (#158). Every phase gates on the per-board floor kernel sprint
  0 sets.

## 7. Relation to the kernel transition

**The work starts after the transition ends** (sprint 7; 2026-10-04). The
table says what each phase builds on, so a phase that could move earlier is
visible; moving one is the owner's call.

| phase (§8) | builds on |
|---|---|

| 1 — spec | nothing in the kernel; moy-spec's own schedule |
| 2 — libmoy, tiers, lanes | sprint 3 (canvas ownership, present), sprint 4 (the cart path, moycore's glue), sprint 0's headroom floors |

**The lanes are a new item no sprint holds.** Today they exist only inside a
wasm session (SOURCE: `native/moy_wasm/README.md`; the seam is
`native/moycore/libmoy/moy_wasm.h`'s `lane_go`/`lane_wait`), and an interpreted
or a Lua or Python session has none. Phase 2 lifts that seam into libmoy's
raster interface for every runtime, with the kernel's cart path as its moybyte
owner.

What the kernel gives the engine: PSRAM for Lua carts, one native loop on
every tier, handle tables, a recovery floor for a native crash, and one
toolkit for the editors' chrome.

## 9. Decision points, all the owner's

1. **The 3D world in C.** Taking #85 §5's deferred row (per-entity work in C)
   for the 3D world, with the cart keeping the loop (proposed), or a 3D world
   in Python like the 2D one, inside the S3 budget §4 shows.
2. **Colour.** Palette ramps with dithered Gouraud (proposed: `pal()`, fades
   and #44's indexed canvas hold; the look is a dithered PS1), or a
   direct-colour surface (the teapot's look; reopens #44 and the console plan's
   §10.1).
3. **Depth.** A banded depth buffer (proposed, if phase 0 shows it fits), or a
   back-to-front sort that costs no memory and gets some overlaps wrong. One
   rule for every host either way.
4. **Modelling.** Voxels (proposed: a slice editor works with a trackball, and
   it is the console plan's direction) or picoCAD-style faces, which need a
   pointer. Importers for both.
5. **Physics depth.** Boxes, the grid, gravity and on-floor (proposed), or
   slopes and capsules too.
6. **A removed actor's handle**: a no-op (proposed, as in 2D) or a loud error.
7. **The bar.** The drawn rate a Blocks 3D game must hold on the Guition S3;
   phase 0 sizes the scene budget against it.
8. **Where 3D is authored.** At T-Deck size (proposed, Studio S5), or on the
   desk only, as #228 put it.
9. **Phase 0's timing**: after the transition (the plan), or earlier.
10. **Every board, or the P4s first**: decided from phase 0's numbers.

## 10. What can kill it

- **The floor board.** No scene budget worth having holds the bar on the
  Guition S3. Then the S3 boards deny the tier, and bake to sprites is what
  they get.
- **Memory with the VM up.** A Blocks 3D game's buffers do not fit beside the
  Python heap on the S3s.
- **The lanes.** The band pump leaves core 0 too little for the bands to pay.
- **Flash headroom** on the P4 images.
- **The editor.** A Model panel unusable at 320×222 with a trackball. Then 3D
  authoring is a desk feature, which Studio S5 forbids without a decision.
- **Determinism's price.** Fixed-point setup slower than Jet's floats by more
  than the budget allows.
- **Spec permanence.** A format that turns out wrong after carts use it.

## 11. Non-goals

- Jet's API, materials, lights or Phong shading in the spec.
- Rigid bodies, joints, a transform hierarchy deeper than one attachment, an
  animation system, skeletal meshes, shaders, multiple lights, shadows,
  terrain sculpting.
- Loading glTF or OBJ on a console: one format of our own, with importers.
- A new invalidation mechanism, or caching any part of a 3D frame.
- Changing the 2D verbs, the 2D actor world, or anything a 2D cart sees.
- Blocks compiling to Lua (declined, `docs/moycore_direction.md` §3).
