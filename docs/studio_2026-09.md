## 0. The thesis

**The Studio is today's Editor with its tabs turned into panels you can place.**
It is still one app on one project. On the windowed tier the tab ladder becomes
panes: five workspaces each place several panels, the running game in one of
them, and their dividers move. Each panel is today's T-Deck editor, upgraded
and given more room when its pane has it. On the fullscreen tier nothing
splits: the seven-tab ladder stays under one bar, one panel fills the screen,
and Play runs the game fullscreen as it does today.

**The target is a middle ground** between PICO-8 and a JetBrains IDE. PICO-8's
editors are the floor: the sprite and map panels keep its layout, keys and
tools. The code panel gains the most, because that is where people leave
PICO-8 for VS Code (pico8-ls: completion, signatures, go to definition). What a
full IDE adds beyond that (debugger, search everywhere, inspectors, onion skin,
auto-tiling) waits (§11, §12).

## 2. What exists today

The Editor is one app, `runtime/editor_app.py`, opened on a project. Its bar
row holds PROJECTS, the tab ladder (Config → Blocks → Code → Sprites → Map →
Scene → Music), UNDO, REDO and PLAY (`docs/shell_ux_v1.md` §6). On the
fullscreen tier that row is the OS bar's lent left zone (§5 there); on the
windowed tier it is the window's own first row, under the title strip the WM
draws for every window (`runtime/wm_windowed.py`). Each tab is its own surface module
(`cards_layer`, `block_editor_ui`, `code_layer`, `paint_layer`,
`map_editor_ui`, `scene_editor_ui`, `music_editor_ui`) with its own Layout
class over `runtime/layout_base.py`, which already takes a width, a height, a
font scale and a chrome scale, and lays the T-Deck's 320×240 out through the
same formulas as every canvas (theming phase 3 step 4).

On a big enough screen the Blocks tab already draws a Scene pane beside its
blocks. On the windowed tier, PLAY opens a separate playtest window at 1× of
the cart canvas, parked bottom-right (#178), and a running cart composites
integer-scaled in its window. On the fullscreen tier the game runs
fullscreen and exit returns to the Editor on the tab you left. The Code tab
holds one of the cart's scripts at a time, switched by a FILE chip (#89); the
Config tab's ADVANCED row lists the project's files and holds + NEW SCRIPT, the
one door that adds a script. The Files app routes any file to the editor for
its kind (`runtime/files_app.py`).

## 3. The window and its one row

On the windowed tier (host, the Waveshare P4, the Guition P4) the Studio is a
window like Calc or Paint. Restored, the WM draws its title strip and the
Studio's one row sits under it; maximised, the window is full screen and the
row is the top edge, with the WM's minimise, restore and close at its right
(S3). The row holds the cart's name (the project menu: switch project, cart
info), the workspaces, undo, redo and Play
(`docs/media/look_2026-10/EDITOR_LAYOUT.md`). Nothing else is Studio chrome.

## 4. Panes

### 4.1 Workspaces and dividers

Each workspace places its panels; the user moves its dividers, and nothing
else (S4). Picking a file in Files opens it in the workspace for its kind, or
focuses it where it already is (S7). The dividers' rules (whole-zoom content,
the minimums of §4.2, a drag that redraws only the two neighbouring panes on
release and never commits or restarts) are
`docs/media/look_2026-10/MAXIMISE_VARIANTS.md`'s Resize.

### 4.2 Minimum sizes: the T-Deck is the ceiling

A panel's minimum is its content, under its pane's header. Every panel with a
fixed minimum is today's T-Deck editor, so it fits the T-Deck unchanged.

| panel | minimum | notes |
|---|---|---|
| Run | 320×240 | the game at 1× |
| Sprites, Sound | 320×222 | |
| Map, Scene | 320×222 | Map with its own sheet strip (S11) |
| Code, Settings, Files, Blocks | none | they scroll when smaller |

A bigger pane only gives a panel more room: more canvas, more code columns,
more map. Two panels side by side need 640 plus borders, so on the 7" screen
three fit across and two rows fit down; under Run there is less than 222 left,
so only a scrolling panel fits there, and the fixed-size panels go beside Run
(Layout B: Sprites, Map, then Run over Code). The Studio window's own minimum is
its layout's combined minimum, and a resize stops there (S7).

### 4.3 Buttons in a small pane

At the T-Deck size a panel draws exactly as on the T-Deck, at chrome scale 1.
Once a pane has room for the panel's layout at the board's own chrome scale,
the panel switches to it; where that point falls is each panel's own Layout's
answer, not one ratio for all. On P4 glass a pane at its
minimum therefore has tap targets below #203's `MIN_TAP_MM`; the owner accepted
that because the big boards are developed on with a pointer (S6). A touch drag
stops before a pane reaches that scale until the P4 boards take a mouse.

That leans on a pointer the P4 boards do not take yet: the kernel's BLE central
(`native/moy_input/moy_hid.c`) parses keyboards, and the mouse is #26's open leg (with #83's USB host as the
other candidate). Host and the browser have one today.

### 4.4 One file, one place

A file is open in one pane at a time, so an edit never has to reach two views of
the same file, and there is one Run. Opening a file that is already open moves
focus to it. The workspace and its dividers are saved on the board, per
project and per screen size, and restored when the project opens. It never travels with a
shared cart: the next board may have a different screen, and a layout made for
the 10.1" does not fit the 7" (S7).

## 5. The panels in the first version

Nine panels, each a tab of today's Editor or a view of the project folder:

| panel | today | first version adds |
|---|---|---|
| Run | the playtest window | docked in a pane (§6) |
| Code | the Code tab | completion, signatures, value picking, go to definition (§5.1) |
| Sprites | the sprite painter | PICO-8's set (§5.2) |
| Map | the map editor | PICO-8's set, one-screen frame (§5.3) |
| Scene | the scene placement editor | the Map's zoom and frame, actors over the real map (§5.4) |
| Blocks | the Blocks tab | its Scene pane becomes the Scene panel; graduation greys it (§5.5) |
| Sound | the Music tab | restyled only |
| Settings | the Config tab | restyled only; it scrolls |
| Files | the ADVANCED row | a panel of its own (§5.6) |

### 5.1 Code

- **Completion and signatures** from the cart API. The names come from
  `runtime/cart_verbs.py`; the signatures and one-line docs come from the verb
  table in moy-spec's SPEC.md, so Python and Lua show the same text.
- **Value picking.** Inside a call whose argument names an asset, the signature
  popup lists the cart's own values: `sfx(` lists the sounds by number and
  name, each with a play button; `spr(` shows the sheet to pick from.
- **Go to definition** for the cart's own functions, across its scripts.
- **One tab per script.** Each script in the cart's load order is a file in
  Files and opens as its own tab; the FILE chip goes.
- Everything the tab has today stays: the tool palette, selection and
  clipboard, find, the gutter, indent and outdent, crash-to-code.

Code colours are theme roles (§8).

### 5.2 Sprites

PICO-8's editor, at the T-Deck size: the canvas, the tool column (pencil,
fill, line, rectangle, circle, select, stamp, shift, flip H and V, rotate,
clear), the first 16 colours with the rest of MOY64 behind one button, the 8
flag toggles, sprite size, and the sheet always visible along the bottom with
its page buttons. Keys as PICO-8: Q and W for the previous and next sprite, H,
V and R, 1–4 for zoom, and holding a pixel picks its colour. The undo,
transforms and bucket the tab has today stay.

### 5.3 Map

PICO-8's map tools on the same sheet strip and the same keys as Sprites, plus a
dashed one-screen frame and the zoom ladder with today's overview rung (#215).
The strip is the Map's own at its minimum, and folds into the Sheet pane at the
desk's scale (S11).

### 5.4 Scene

Today's scene editor (#85): tap to place or select, drag to move or pan, snap,
tag and flip, front and back, per-gesture undo, and a live sync into the
scene on every gesture. It gains the Map's zoom levels and one-screen frame,
and draws the actors over the real map.

### 5.5 Blocks, and graduation beside Code

Blocks keeps its per-object scripts (Stage and one per actor kind, #85/#93).
The Scene pane is a panel placed like any other, and the pairing holds across
the two panels: selecting an actor in Scene opens that actor's script, and
picking a script selects its actor (`_sync_target_from_scene` and
`_select_sprite` in `runtime/block_editor_ui.py`).

Graduation stays the one-way door of `docs/shell_ux_v1.md` §8, and so does its
mechanism: the manifest's `moybyte.graduated` flag, set by the commit whose code no
longer round-trips, carried by the journal's `grad` rider so that undoing past
that commit un-graduates (`runtime/project.py`, `runtime/moy_journal.py`). What
changes is how it shows. With Blocks and Code side by side, Code carries no
warning; typing in Code is allowed. At the commit that graduates, the Blocks
pane greys out where it stands and reads "you've leveled up to code". An undo
past that commit brings it back.

### 5.6 Files

The project's folder, in the ladder's gentlest-first order: Settings, the
scripts, sprites, map, the scenes, sounds, then the cover and cart info. Each
entry opens its panel. An entry with no panel takes the door it takes today:
the cover opens in Paint (the Files router's picture door) and cart info opens
the CART INFO dialog. **+ new file** at the bottom replaces the ADVANCED row's
+ NEW SCRIPT as the one door that adds a script, offered where a second script
would run (`moy_carts.multi_script`). On the fullscreen tier Files is the bar
itself (§7).

## 6. Run

- **The Run pane is the playtest window, docked.** The Studio lends the pane's
  rectangle; the WM places the Player's window there without a frame. The
  Player is unchanged: Play is still `commit(); run(current)`
  (`docs/shell_ux_v1.md` §2), and one cart runs at a time.
- **Play starts** the game with the freshest files; **Restart** and **Stop**
  take its place while it runs. The Run slot cannot be closed, so Stop stays.
- **Play selects** the workspace's Run slot or Game tab (S12). It never falls
  back to a floating playtest window.
- **Sprites, sounds and flags are live; map, scene and code wait** (S13). A
  sprite, sound or flag edit reaches the running game at once; a game that
  reads its map or scene once at start (Sky Run does) cannot show such an edit
  live, so those and code wait for the next Play, with a dot on Restart. Nothing
  restarts a running game on its own: a restart per stroke would throw away
  the player's place for every brush mark.
- Run draws at 1× and grows in whole steps as its pane does, the way a cart
  composites in its window today.

## 7. The fullscreen tier (T-Deck, Guition S3)

One panel fills the screen and nothing splits. One bar carries the seven
tabs and Play (S8; its layout is `docs/media/look_2026-10/EDITOR_LAYOUT.md`'s
handheld). Play runs the game fullscreen and exit returns to the file you were
on, as today. On the Guition S3's 480×320 the same rule holds: two panels
never fit at their minimums, so its Studio is this one.

## 8. Relation to theming

The Studio is drawn in D1 and restyles with every theme, because it is drawn
from the toolkit's parts. How each piece maps onto `docs/theming_2026-09.md`:

- **The window frame is WM chrome** (`window`, `window.title`,
  `window.button.*`), so frame styles (§4.5 there) apply to the Studio as to
  every window (S3).
- **New parts, named early.** The Studio's chrome adds kinds the toolkit does
  not have yet: a pane and its header, a divider, and the completion popup
  (`docs/media/look_2026-10/GAPS.md` 31 lists them all). They are added to
  `ui.DEFAULT_SPECS` before theming's phase 1 freezes format 1, so they are in
  the derived part list (§4.3 there) instead of arriving as renames.
- **Content is exempt** (§4.3 there): the sprite canvas, the sheet, the map and
  scene views and block colours. A theme restyles the frames around them,
  never their pixels. Code syntax colours are theme roles, each held to 4.5:1
  on the code surface (decided 2026-10-15, `docs/look_2026-10.md`).
- **Fonts.** Code is the `mono` role. `CodeLayout`'s grid reads its line
  metrics (theming §4.7): a row is petme128's line and the code lead, or a
  version 2 face's glyph box, and the caret, a selection and the error
  marks span that box (`CodeLayout.text_h`).
- **Timing.** The Studio moves pixels on purpose, so it follows theming's rule
  (§8 there): it starts after kernel sprint 6, whose gate held the goldens. The T-Deck's Editor bar
  took the Studio mockup's narrow form with theming phase 3 step 4 (one icon a
  tab, then UNDO, REDO and PLAY); the one bar of the look's step 30 has its
  own named re-baseline.

## 9. Relation to the native kernel

- **The Studio stays Python.** It is "the Editor and its tabs" in the apps row of
  `docs/native_kernel_2026-09.md` §2.2, and the panes, docking and layout are the
  app's own policy. Nothing here moves below the app verb table.
- **The Run pane is a WM feature.** A window docked into a rectangle another app
  lends is new policy in `runtime/wm_windowed.py`, which stays Python (the
  kernel doc's §10 question 8: sprint 7 does not run).
- **The cart path is untouched.** The Player docked in a pane is the same
  Player; sprint 4's gate (a cart runs launch to exit with no Python upcalls)
  holds, and "one VM, one active cart" stands.
- **Parts are toolkit kinds**, so sprint 6's native toolkit draws the Studio's
  chrome with everything else's (§8).

## 10. Order of work

Each step ships alone, deletes what it replaces and passes
`tools/preflight.sh`. The Editor's goldens re-baseline once per step that moves
pixels, naming what moved.

1. **Panels take a rectangle.** Each tab's Layout lays out against a pane's
   width and height instead of the whole content area, and picks its chrome
   scale by room (§4.3). On the fullscreen tier nothing moves.
2. **Files and one tab per file** on the windowed tier; the FILE chip and the
   ADVANCED row's file list go.
3. **Panes:** the workspaces, their dividers, the minimums, the saved layout,
   and the new toolkit parts (§8).
4. **The Run pane** in the WM (§9).
5. **Panel upgrades:** Code (§5.1), then Sprites, Map, Scene and Blocks.
6. **The T-Deck bar**, with theming phase 2b (§8).

Steps 1 to 5 run on the host and the P4 boards first; the pointer (§4.3, #26)
gates calling any of it done on P4 glass.

## 11. Cut from the first version

Drawn in the "everything" set and cut on 2026-09-29, so they are not added
piecemeal without a decision:

- **Debugging:** watch variables, pause and step, the frame timeline (they
  return as the Debug panel, §12).
- **Editor extras:** an inspector with custom fields, onion skin, a minimap,
  brushes, auto-tiling.
- **Code navigation:** search everywhere, "used by", named sprites and flags.
- **Code decorations:** sprite thumbnails and value hints in the margin.
- **Panels:** history, problems, structure, a status bar.
- **Other:** slow-frame warnings, a beginner "try this next" list, "run on
  T-Deck", and a separate Simple/Full mode. There is one layout for everyone;
  the gentlest-first order survives as the order of Files.

## 12. Later

- **Debug:** the cart's variables live, a console, pause and step one frame; no
  breakpoints. It scrolls like Code. The console is written by a new cart verb,
  `log()`, because a cart's `print()` draws on its screen. That verb is a
  moy-spec addition first (the verb table is a public spec).
- **Restart on a map, scene or code edit** as a setting, if the first version
  shows people want it (S13).
