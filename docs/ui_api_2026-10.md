# The public UI API (2026-10-15)

**What this is.** The verbs every app and cart draws its interface with —
Python apps, Lua carts and compiled (wasm) apps alike — and their semantics.
Step 11a of `docs/history/look_2026-10.md` built its core, and the screen steps
after it added the rest (§1a). The look they draw is
`docs/media/look_2026-10/DESIGN.md`'s, the theme model `THEMES.md`'s beside
it; the engine beneath is `native/moy_ui` (`docs/kernel_toolkit_2026-10.md`).

## Decisions (owner, 2026-10-15)

- **The design system is a public UI API** for user apps in all three
  runtimes, not the shell's private styling. The shell's own apps draw
  through it and nothing else, held by a ratchet test (§7).
- **Dear ImGui's model, microui's calls, our names.** Immediate mode, ids,
  and keyboard navigation the engine owns, resolved over the previous
  frame's rects (ImGui); flat calls that take values and answer one
  (microui); the design system's words — `normal`, `primary`, `tonal`,
  `danger`, `toggle`, `current`, `focus` — which are Material's and HTML's.
  No library is adopted; LVGL stays in `docs/surface_model_v1.md` §8.
- **Themed by default, overridable, like CSS** ("allow apps to do as they
  please with focus, color, layout — a balance that's good enough"): colour
  comes from the kind unless a call overrides it (§3); rows stack
  automatically unless `ui.at` places a call; the engine moves and marks
  focus unless an app takes it over (§4). The shell's apps keep every
  default; user apps are free.
- **Moybyte's own, not moy-spec core** (owner, 2026-10-15): the API is the
  vendor extension `moybyte.ui`, which SPEC.md §10 lets a cart use when the
  host has it. Game carts stay portable; an app cart is a Moybyte app. A
  core proposal is written only if another host ever wants it (§9).
- **Built as we go** (owner, 2026-10-15): step 11a builds a small core,
  enough for Settings and Calc (§1). Each later screen step adds the
  widgets it needs to the public API, never as private calls, with its rows
  in §1's table, reviewed against the theme like any part; §1a says what
  each step added.
- **Blocks, composed** (owner, 2026-10-29; the plan that moved the
  surfaces, #243, is `docs/history/ui_blocks_2026-10.md`): every surface and
  every new app is built from the engine's blocks in `native/moy_ui/`,
  which each face calls (§1), and scrolls on the one scroller. A screen
  that needs something new composes it from the verbs, or the gap is fixed
  in a block; no verb is named after the screen that first wanted it.
- **Carried in C** (2026-10-30, the `moy_prof` capture in #66): most of an
  immediate-mode pass is the app's Python, not the engine's layout, so a
  row that did not change is carried by the engine with no app Python run
  for it (a table of parts, §2). A carry in Python roughly broke even with
  calling only the rows that show, and bought nothing. The other lever is
  Python per verb call, so a block allocates nothing on a moving frame (§7).

**The survey** (`docs/media/ui_api_2026-10/survey.md`) compares thirteen
APIs and sketches three shapes as a cart. Only Dear ImGui, LVGL and egui
navigate by keyboard (LVGL is in the graveyard, egui is Rust); the small C
ones have no focus at all; none knows semantic kinds or a current mark; and
our audience, PICO-8 and TIC-80 makers, knows no UI API, only the web's and
the phone's words. So the shape is copied and the names are ours.

## 1. The verbs

```lua
function _draw()
  ui.page("Settings")
  ui.hints({"change", "Change"})
  ui.group("Sound")
  sound = ui.toggle("Sound", sound)
  vol   = ui.slider("Volume", vol, 0, 10)
  ui.group()
  cur   = ui.list("Theme", themes, cur)
  if ui.button("Save", "primary") then save() end
  if ui.button("Forget", "normal", {fill = "danger"}) then forget() end
end
```

Python makes the same calls, `o` a dict. `o`, the override table (§3), is
optional everywhere.

`kind` is one of the five names; an unknown one draws as `normal`. `cur`
counts the language's way (from 1 in Lua, from 0 in Python and wasm); 0 in
Lua and -1 elsewhere is no current row. The wasm imports are the `ui`
role's rows in `native/os_calls.json`, every compiled app's with no
grant, marshalled by moy-spec SPEC.md §16.4: text is a pointer and length,
`items` NUL-separated, a boolean an `i32`, `kind` its index among the five
names in the order above, several results written at `out` (a pointer and
length), `o` an override block's pointer and length (length 0: none),
`colours` 0xRRGGBB values as little-endian words, a group's caption of
length 0 its end (a scroll region's id and a dialog's title the same), a
table's columns and cells each ending in a NUL (the cells row by row) and its
two answers written at `out`, a field's text edited in place at `buf` (its
length the room) and answered as the new length plus 0x10000 the frame Enter
is pressed, a dialog's answer from 0 and -1 for none, a popover's id of
length 0 its end and its answer 1 or 0, a menu's `items` and `icons`
NUL-separated and its answer from 0, -1 for none, a grid's id of length 0 its end, a card's five answers written at `out`, a bar's `tools` NUL-separated, bit i of `off` its tool i at half strength and bit 31 the app's way back, its answer from 0, -2 the way back and -1 none, and
`ui_focus` with an id of length 0 reads instead of moving, answering the
focused id's length (0: none), and `ui_text_view` takes its lines
NUL-separated, its options as seven little-endian words (rows, wrap,
syntax, follow, gutter, the caret's line and column; moy_ui_api.h's
`MOY_UI_TXO_*`, the syntax as its index among `plain`, `python`, `lua`,
`json`, `sgr`, `markdown`) and writes its two answers at `out`. A scroll region, a
text view, a dialog or a popover begun inside two open ones (moy_ui_api.h's

its wasm import answers -5 (moy_ui.h's `-MOY_UI_DEEP`), a value none of the
four answers otherwise. `ui.empty` is every face's: an empty page's

**A text area: `ui.text_view`** (docs/history/scroll_and_text_2026-10.md §5, P4)
draws `lines` -- a list of strings, a table from 1 in Lua -- in rows of the
theme's `mono` face, in `ui.at`'s rect or stacked `o.rows` rows tall (the
rest of the page where it names none). It is a scroll region of its own: a
drag scrolls it by pixels and its release coasts, the wheel steps it. Its
options: `wrap` (a line longer than the view breaks after its last space
that fits, else at the view's width; otherwise it is cut), `syntax` (`sgr`,
the default: a terminal's `ESC [ n m` colours, which take no column --
30-37 and 90-97 the theme's text, danger, string, number, keyword, builtin,
value and comment inks, 2 the dim ink, 0 and 39 back to the text's;
`plain`; `python`, `lua` and `json`, the Code tab's highlighting;
`markdown`, a note's source in the same tones: its marks in the comment's,
a heading's words in the number's, a task's open box in the keyword's and
a ticked one in the string's, its words dim, a `[[link]]`'s name in the
builtin's), `follow`
(a view starts at its foot, and at its foot glides to the new foot when
lines are added: a log, a chat, a terminal), `gutter` (line numbers) and
`caret` (a line and column, each from 1 in Lua: an input line's). The
Python face's own, an editor's (the Code tab's): `sel`, `err`, `find`,
`left`, `mark`, `lines_gen`, `top`, `font`, `paper` and `into` (runtime/toolkit/ui.py's `text_view`
says each); a compiled app's options are the seven words before them. Its colours are the theme's: the
`surface` under it, the code roles (`code_text` .. `code_builtin`) for its
tones, so a theme restyles it as it does the Code tab. A frame draws only
its rows that changed and moves the rest (its rows' gens, as the Code

the first line shown and the rows shown. The record of what it drew is
kept by its id, four text areas across every context (the least recently

**A chat's bubble: `ui.bubble`** (the Moy Mesh design, 2026-11-10) is a

## 2. Semantics

- **Ids.** A widget's id is its label, or `o.id` where two share a label; a
  part names its own, and a page is its title, or `o.id` where two pages
  share one. The engine keeps focus, a
  page's scroll, a list's row and scroll and a slider's drag by id from
  frame to frame, and drops an id's state the first frame it is not drawn.
  A duplicate id in one frame is no stop, and the Python face logs it once.
- **The engine's state** is a context per running app: the Python face's
  is bytes its host keeps (`ui_draw.ui_context`), begun each frame by the
  host before the app's update (`ui_draw.ui_frame`); a Lua cart's and a
  compiled app's is the run's one, reset when a run opens and begun by the
  first verb of each tick over the run's snapshot, the input its `btnp`
  reads. An app's own memory holds none of it.
- **One focus.** One stop holds focus per screen; in a windowed host, in
  the focused window, and a window behind draws none. On a page's first
  frame it is the first stop drawn; `ui.focus(id)` moves it, and focus on
  an id that stops being drawn passes to the nearest stop.
- **Navigation** resolves once per frame, before its first ui call, over
  the stops the previous frame recorded: up and down to the nearest stop
  above or below, left and right to the nearest beside (the least gap along
  the arrow, then across it), Tab in call order, wrapping. Tab is the typed
  key 9; the input carries no shift with it, so there is no Shift-Tab. A
  focused slider, cycle, seg, tab row or swatch picker keeps left and right
  (a cycle wraps, the others stop at their ends), a list keeps up and down until its
  first or last row. The page scrolls to keep focus, or the list row it
  moved to, in view (focus on its first stop shows it from its top, the
  caption above included). A pointer drag's direction is decided once, when
  it first passes 4 pixels (at the font scale), as a phone's is: a mostly
  vertical one scrolls the page from whatever row it went down on, a
  slider's and a stepper's included, and is no tap; a mostly horizontal one
  on a slider drags its knob, and on a cycle, seg, tab row or swatch picker
  taps where it is released.
- **Motion.** A page, a `ui.scroll` region and a placed table's rows each
  scroll on the one scroll model (`moy_ui_scroll_t`,
  `docs/theme_and_shell_2026-11.md` §9.1): a drag let go at speed coasts on
  and comes to rest, dead at either end; a press on a coasting page stops
  it and taps nothing; the scroll that keeps focus in view, and a wheel
  notch, glide there eased, a step moving exactly one step. The clock is
  the host's tick, injected (`ui_draw.frame_dt`, the run's snapshot time
  for a Lua or compiled app): with none, a glide lands at once and a
  release flings nothing.
- **Activation** is `a` or Enter (`run`) on the focused stop, or a tap or
  click released inside the stop it went down on, which focuses it as well.
  A button or a link answers true that frame, a toggle flips, a list makes
  the focused row `cur` (the tapped row, for a tap), which then wears the
  current mark; a cycle, a seg, a tab row and a swatch picker take their
  next option, or for a tap the one tapped (a cycle, whose options are not
  shown, its next); a tap on a slider takes the value under it.
- **Back is the host's.** The ui never reads `b`. The host's back -- Esc,
  B, the T-Deck's K, the bar's chevron, a desk window's -- steps out of the
  app's own views first (`moy_ui_api_back`, `Player.back`, on every tier):
  a popover the last frame drew is dismissed, as Esc and a press outside
  it are; else, where the last frame lent `ui.bar`'s `back`, its next
  `ui.bar` answers its way back (`ui.UP`; Lua -1, a compiled app -2) and
  the host shows the chevron meanwhile. With neither open the chevron
  leaves the app, and a cart sees `b` and Esc through `btnp` and `keyp`
  (`docs/app_api_v1.md` section 4).
- **`ui.keys_taken()`** tells a cart with its own input beside a menu
  whether to act on this frame's `btnp`: true when an arrow, `a`, Enter or
  Tab was pressed while a stop the engine navigates holds focus.
- **Settled.** A frame that owes no frame after it is settled
  (`ui_draw.ui_frame` answers it): what its input moved -- the focus, a
  page's scroll, a step of its motion -- the engine applied before the
  pass, so the pass draws it (`api_moved`); an activation, a typed key, a
  press or its release, a value a key stepped, a reveal the pass set, or a
  layout found stale owes the next (`api_owes`), and a page drawn again
  then draws the same pixels. A page still moving on its own is
  `api_moving`, which a host's frame gate reads as animation.
- **Shift frames** (docs/history/scroll_and_text_2026-10.md §3.3, the contract in
  docs/surface_model_v1.md §14.7). A page, a `ui.scroll` region, a placed
  table or a card given a `gen` (§3) says what the app draws there is a
  function of it;
  where every page and picture in the region a frame scrolls carries one,
  the host moves the last frame's pixels of the region and the pass draws
  only its floor -- the band the move exposed, the rows whose marks moved,
  the fades -- every verb still laying out, taking focus and answering.
  The app moves the gen when anything it draws there changes; one with no
  gen, or that places a stop in the region with `ui.at`, draws whole. A
  card or part the floor does not reach answers a rect of no size, so the
  app draws nothing into it, and one it reaches is drawn through
  `ui.card_clip(r)`, which cuts the app's clip (an `array("i")` of four,
  in place) to the floor's rect the picture lies in. A placed table is the
  region its rows scroll in: its floor is whole rows where the app draws
  pictures on them (`ui.table_rows`), so the app passes each row's picture
  rect through `ui.card_clip` after the table and draws only where it
  answers a rect. `ui.band()` is the floor's bounding rect in
  the page's coordinates (y from its rows' top; what shows of the page on
  a whole frame), and an app that loops over many cards skips those it
  lies outside of with `ui.keep(id, h)`, which carries the stop forward as
  the last frame drew it (a card of the open grid, else a row `h` high) --
  but never a card whose picture moved, which it draws. A key typed into a
  field draws the field's row alone, its text and caret, and a field whose
  text the app changed draws its row again. A note an app draws through
  its editor handle (`ed.draw`) on a page under a gen draws the rows that
  changed alone, the page's floor those rows: stops `ui.at` placed on such
  a page are no bar, since nothing moves (docs/history/scroll_and_text_2026-10.md
  §5). The Python face's; a Lua or compiled app passes no gen and draws
  whole.
- **Budgets** (`native/moy_ui/moy_ui_api.h`, configuration): a frame
  records `MOY_UI_API_STOPS` (40) stops, its pages' and regions' among
  them; one past them is drawn but takes no focus or input, and the Python
  face says so once a frame (`moy_ui_api_lost`). A list or a table is one
  stop whatever its rows, and a table of parts one for its rows plus the
  stops drawn in the parts that show, so a long list is one `ui.list` or
  `ui.table`, not a stop a row. The engine keeps the state of
  `MOY_UI_API_KEEP` (16) ids, a shift frame's floor holds
  `MOY_UI_API_FLOOR` (24) rects, and nests open `MOY_UI_API_NEST` (2) deep
  (§1). A budget is raised by counting the stop record's bytes first.
- **Drawn on change.** A page is drawn when something changed, never on a
  clock: a shipped app when its host owes a frame (`ui_host.AppHost`), and a
  Python app cart (`"type": "app"`, its frame begun by the Player) while a
  key, a button, the wheel or the pointer is in play, while the frame it
  drew last was not settled and the one after it, while the engine has a
  part in motion (`api_owes`: a toast; `api_moving`: a page's coast or
  glide) and while an editor handle it opened
  changed or owes its idle save (`Player.animates`). Still, it draws
  nothing, its `_update` with it, and its window keeps the last frame. An
  app cart whose manifest's `moybyte` object says `"animates": true` draws
  every frame (a clock, a meter, anything that moves on its own), and so
  does one that lists `audio` in its permissions, the frame being where the
  host and the browser pull its sound.

## 4. Taking focus over

`nav = false` on a page: the engine never moves focus inside it; the arrows
and `a` are the cart's (`ui.keys_taken()` answers false) and the cart moves
focus with `ui.focus`. On a part: focus arrives by the engine's navigation
and then stays, the keys the cart's — a swatch grid, a game board — until
the cart calls `ui.focus` elsewhere, and a press held on it stays its own
through a drag, which moves no page (`ui.part_at`, §5).

`mark = false`: the engine draws no focus mark, and the cart draws its own
look from `ui.part`'s `state`. Both keys work on any stop.

## 5. `ui.part`

`ui.part(id, w, h, o)` reserves a stop for content only the cart can draw:
a colour swatch, a cover, Calc's display. The engine lays it out (a row, or
`ui.at`'s rect), draws its fill and the theme's marks — focus, and current
when `o.current` — and answers `x, y, w, h, state`; the cart then draws into
that rect with its ordinary verbs. `state` is bits: FOCUS 1, ACTIVATED 2
(this frame), PRESSED 4, HOVER 8 (`ui.FOCUS` and its siblings in Python).
Its fill is the theme's display inset: the `lcd` role, ringed by the
look's `lcd_border` or bevelled by its `lcd_bevel`, its corners the key
radius up to 8 pixels on the handheld and 10 on the desk (square without a
depth); a disabled part is no stop. A part may read `theme()`'s roles to
match its surroundings, never write them; a Python app measures the text it
draws there with `ui.text_size`, and `ui.has_symbols` says whether the
font has `− × ÷ ← →`. `ui.face(name, text)` has its prints draw in the
theme's face for type role `name` (Calc's result is `result`) where the
theme installs one that draws every character of `text`, answering
whether it did, and `ui.face()` puts the print font back: the theme names
the face, the app only the role. A button's label is in the face its
kind's `font` leaf names (`buttons[kind].font`, `app_buttons[app]` for a
shell app), where one is installed and covers the label.

`ui.part_at()` answers where the pointer is inside the part answered last
this frame, from the part's top-left: where the tap that activated it was
released (its `state` ACTIVATED by the pointer), else where the pointer is
while it presses or hovers the part; None otherwise (a key activated it).
A press held on a part stays the part's through a drag past the slop
where no page lies under it to drag, or where its `nav` is off (§4): it is
PRESSED, and `part_at` follows the pointer, while the pointer stays on it.
A part that is a grid of cells (Paint's sprite picker, the desk Editor's
Sheet, whose held slide picks each tile it passes) reads its cell from it,
so no app turns a glass pixel into a cell of its own.

## 5a. `ui.split`

`ui.split(id, dir, sizes, o, out)` cuts `ui.at`'s rect (else the page's,
from its next row down) into one pane a size of `sizes`, along `dir` (`"x"`
left to right, `"y"` top to bottom), `o.gap` pixels apart, the last pane
taking what is left. It writes each pane's `x, y, w, h` into `out`, then
four words: the divider held or let go this frame (from 0, -1 none; Lua
from 1, 0 none), where its drag takes its gap (an x, or a y), the side it
stopped at (-1 none, 0 the pane before it at its minimum, 1 the pane
after) and its bits (`ui.LIVE` 1: the drag has taken, `ui.LET_GO` 2: let
go this frame). With neither `o.focus` nor `o.drag` it is the rect algebra
and draws nothing.

- **Focus.** `o.focus` is the focused pane (-1 none; Lua from 1). The
  split answers it as moved: to the pane a press goes down in, and, as the
  focus moves between groups, to the pane the focused stop lies in on the
  frame the keys move it there. Without `o.focus` it answers -1. The panes
  a pass's splits cut stay the context's record until its next pass: a
  host asks it for the frame that draws the focused pane alone
  (`AppHost.split_frame`) and for the pane a directional move lands in
  (`AppHost.split_toward`), both below. A pane a later split of the same
  pass cuts again is a node of the record, not a pane; the Editor desk
  gives each split the child the keys reach (a prompt's pane, else the
  focused one), and a pane grown or alone over the area is a split of one.
- **Divider.** With `o.drag` each gap is a divider the engine keeps by
  `id`: a press on it (`o.hit`, its `(across, along)` box centred on the
  gap, the gap's where absent) holds it, a drag past `o.slop` pixels moves
  its line (`o.line` across, the `value` token), and the release writes the
  two sizes beside it back into `sizes`, neither under its minimum
  (`o.mins`). Until the release the panes stay where they were. Its handle
  is a pill in the `border` token, `o.handle` `(across, along)`, the gap
  and six gaps where absent. A host that routes its own presses asks
  `AppHost.split_at(x, y)` whether a press lies on a divider its last frame
  drew, and gives that press to the frame.

**The split frame.** A pane's content lives in a context of its own (each
Editor tab's `AppHost`), and one context's plan cannot see another's, so
the frame that draws the focused pane alone is decided from the record
before any pass begins: `AppHost.split_frame(gen, known, top, lag, out)`
(`moy_ui_api_split_frame`). It answers ALONE, with the pane's rect below
`top` (the header the context's own pass draws), where the host holds no
input for the context, nothing is owed, no page moves, the last pass drew
no popover and held no divider, `gen` is the last frame's and `known`
(the WM's word) says the target holds the page as the last frame left it;
what the WM paints over the page is the WM's to keep in step. It answers
LAGS where the target lags (`lag`) outside that rect, the frame drawing
whole and changing the rect alone, and WHOLE otherwise. The app's part is
data: `gen` is what it draws outside the pane (the desk's `_surround`), or
None where that changes on its own (a playtest, an animation, a loupe).
The pane's own context then plans what changed in it, its page's shift
and rows frames or its dialog's rows (`Hold.ok`), reading the WM's word
the desk relays round the pane's draw (`AppHost.window`, over
`ui_draw.window_frame`); the change the WM takes is the pane's rect, or the
dialog's floor (`AppHost.floor_box`).

**Directional moves.** `AppHost.split_toward(x, y, dx, dy, out)` answers the
recorded pane that lies (dx, dy) from the one holding (x, y): of the panes
whose centre lies that way the nearest along it, a pane off to the side
counting twice its distance across. The desk's Select and d-pad move the
keys there.

A compiled app's `ui_split` takes `sizes` and `mins` as little-endian words
(length 0: no minimums) and its options as moy_ui_api.h's `MOY_UI_SPO_*`
words (flags `MOY_UI_SPLIT_*`, gap, focused pane, slop, hit, handle, line;
0 each one's default), writes `sizes` back where a divider is let go after
a drag, and answers -0x100 less a `MOY_UI_*` code where it fails.

## 6. Theming stays the engine's

The theme supplies the row heights and type per size class, each kind's
look (`buttons[kind]`, `app_buttons`) and the `focus` and `current`
properties, so a new theme restyles every app that kept its defaults with
no change to the app. A Lua or compiled cart's buttons take the same leaves
(shape, radius, depth, colours) as a Python cart's: a game's canvas has
MOY64 only, so a leaf's colour is its nearest MOY64 index, the rule a
Python cart's page takes inside the cart boundary (`moy_ui_pidx`), and the
three runtimes draw one button. A responsive app's page draws outside the
boundary on every tier, in the theme's own colours and faces
(`docs/app_api_v1.md` section 3).

## 7. The shell is strict

The shell's apps — Settings, Appearance, Files, Calc, the editors and the
system carts' code — call only the verbs, with no colour key and no `nav`
or `mark`, so their look is the theme's entirely. They lay out with
`ui.page`'s rows, or with `ui.at` over rects cut from the content rect
`ui.page` answers (the rect algebra stays in `runtime/toolkit/ui.py`), into the
frame their host side begins (`ui_host.AppHost`, an app's `ctx.ui` when its
class sets `UI = True`). The engine
layer under the verbs — the rect-taking widgets, the marks
(`focus`, `current`) — is `runtime/toolkit/ui_draw.py`, which the chrome (bars, window frames,
the home, the window managers) keeps; `runtime/toolkit/ui.py` is the verbs.

The ratchet, `tests/test_ui_public.py`, scans the shell's app modules and
system carts for the engine layer (`ui_draw`) and for the colour keys, `nav`
and `mark` (`id`, `current`, `disabled`, `steps`, `hint`, `wash`, `lead` and `gen` pass). It pins the list of apps not yet moved,
which can only shrink: each screen step that restyles an app (19–24) took it off, and
seven modules stay on it, the editors that steps 23 and 24 restyled in place (§1a)
and Paint's layer. No
system cart is on it since Notes moved (step 31), and an app cart's
namespace carries `ui` alone (`runtime/shell/system_api.py`).

The ratchet is also what holds a composition to the public verbs: a
module off its list names no `ui_draw`. A composition that replaces a
verb draws that verb's goldens byte for byte and keeps its input semantics, and a verb that leaves takes its
callers with it in the same commit, with no alias (there are no user apps
to keep working). The blocks have their own nets:

- `tests/test_ui_public.py`'s fixture page, drawn by the three faces to
  the same pixels, and its pins of the stop budget (§2) and the split
  frame (§5a);
- `tests/test_ui_nest.py`: a nest past `MOY_UI_API_NEST` raises in Python
  and Lua and answers `-MOY_UI_DEEP` in wasm (§1);
- `tests/test_frame_alloc.py`: a block's moving frames allocate nothing
  past their answer -- the Blocks outline's table of parts walked and
  swiped, a row of parts dragged, flung and snapped, a split's divider

and the drag over buffers in the app's memory) went in one commit, with no
compatibility rows: there are no users. The engine keeps focus, the
previous frame's stops and each id's state per running app (§2), so an
app's memory holds no ui buffers. The fixture
`tests/fixtures/wasm/app_ui.moy` imports every row, and
`tests/test_roles.py` holds that and the table, the adapter and
`docs/app_api_v1.md` together; a step that adds a widget adds its row, and
the fixture imports it.

A Lua cart reaches `ui` as the vendor extension `moybyte.ui` and may use
it opportunistically (`if ui then`, SPEC.md §10): every Lua run on a host
with the toolkit has the table, its theme the console's live one; a
compiled app imports the rows from module `"moybyte.app"`, as it does every
role's.

A native app (a manifest of type `app` whose cart carries modules,
`native/moy_elf/README.md`) or a WASI app (`"wasi": true`,
`runtime/run/wasi_run.py`) calls the same rows under the same names and
signatures from `sdk/include/moybyte/ui.h`, answered inline by a copy of
the toolkit its module links (`sdk/README.md`): the copy's RUN face, the
compiled run's, drawing on a canvas of the app's own, its theme the
console's block pulled where its generation moved (`moy_ui.h`'s
`moy_ui_theme_pull`, the OS rows `moy_ui_pull` and `moy_ui_font_pull`),
its input the frame message's words, its screen RGB565 handed over with
`moy_present`. A responsive one's `_layout` (`docs/app_api_v1.md` §3) is
the copy's to call, when the message's layout words move. `tests/test_ui_linked.py` holds both to a Python app's
pixels, a typed field's included.

## 9. moy-spec

moy-spec gets no proposal (owner, 2026-10-15). Were another host to want
the API, `proposals/ui.md` would carry the verbs as they then stand, the
semantics (§2) and the override keys (§3), with kinds and marks named and
not drawn, a reference look in palette indices in libmoy, and conformance
that tests behaviour under scripted input and never a pixel.
