# The public UI API (2026-10-15)

**What this is.** The verbs every app and cart draws its interface with —
Python apps, Lua carts and compiled (wasm) apps alike — and their semantics.
Step 11a of `docs/look_2026-10.md` built its core, and the screen steps
after it added the rest (§1a). The look they draw is
`docs/media/look_2026-10/DESIGN.md`'s, the theme model `THEMES.md`'s beside
it; the engine beneath is `native/moy_ui` (`docs/kernel_toolkit_2026-10.md`).

## Decisions (owner, 2026-10-15)

- **The design system is a public UI API** for user apps in all three
  runtimes, not the shell's private styling. The shell's own apps draw
  through it and nothing else, held by a ratchet test (§7).
- **Dear ImGui's model, microui's calls, our names.** Immediate mode, ids,
  and keyboard navigation the engine owns, resolved over the previous
  frame's rects (ImGui); flat calls that take values and answer one
  (microui); the design system's words — `normal`, `primary`, `tonal`,
  `danger`, `toggle`, `current`, `focus` — which are Material's and HTML's.
  No library is adopted; LVGL stays in `docs/surface_model_v1.md` §8.
- **Themed by default, overridable, like CSS** ("allow apps to do as they
  please with focus, color, layout — a balance that's good enough"): colour
  comes from the kind unless a call overrides it (§3); rows stack
  automatically unless `ui.at` places a call; the engine moves and marks
  focus unless an app takes it over (§4). The shell's apps keep every
  default; user apps are free.
- **Moybyte's own, not moy-spec core** (owner, 2026-10-15): the API is the
  vendor extension `moybyte.ui`, which SPEC.md §10 lets a cart use when the
  host has it. Game carts stay portable; an app cart is a Moybyte app. A
  core proposal is written only if another host ever wants it (§9).
- **Built as we go** (owner, 2026-10-15): step 11a builds a small core,
  enough for Settings and Calc (§1). Each later screen step adds the
  widgets it needs to the public API, never as private calls, with its rows
  in §1's table, reviewed against the theme like any part; §1a says what
  each step added.

**The survey** (`docs/media/ui_api_2026-10/survey.md`) compares thirteen
APIs and sketches three shapes as a cart. Only Dear ImGui, LVGL and egui
navigate by keyboard (LVGL is in the graveyard, egui is Rust); the small C
ones have no focus at all; none knows semantic kinds or a current mark; and
our audience, PICO-8 and TIC-80 makers, knows no UI API, only the web's and
the phone's words. So the shape is copied and the names are ours.

## 1. The verbs

```lua
function _draw()
  ui.page("Settings")
  ui.hints({"change", "Change"})
  ui.group("Sound")
  sound = ui.toggle("Sound", sound)
  vol   = ui.slider("Volume", vol, 0, 10)
  ui.group()
  cur   = ui.list("Theme", themes, cur)
  if ui.button("Save", "primary") then save() end
  if ui.button("Forget", "normal", {fill = "danger"}) then forget() end
end
```

Python makes the same calls, `o` a dict. `o`, the override table (§3), is
optional everywhere.

`kind` is one of the five names; an unknown one draws as `normal`. `cur`
counts the language's way (from 1 in Lua, from 0 in Python and wasm); 0 in
Lua and -1 elsewhere is no current row. The wasm imports are the `ui`
role's rows in `native/moy_app/roles.json`, every compiled app's with no
grant, marshalled by moy-spec SPEC.md §16.4: text is a pointer and length,
`items` NUL-separated, a boolean an `i32`, `kind` its index among the five
names in the order above, several results written at `out` (a pointer and
length), `o` an override block's pointer and length (length 0: none),
`colours` 0xRRGGBB values as little-endian words, a group's caption of
length 0 its end (a scroll region's id and a dialog's title the same), a
table's columns and cells each ending in a NUL (the cells row by row) and its
two answers written at `out`, a field's text edited in place at `buf` (its
length the room) and answered as the new length plus 0x10000 the frame Enter
is pressed, a dialog's answer from 0 and -1 for none, a popover's id of
length 0 its end and its answer 1 or 0, a menu's `items` and `icons`
NUL-separated and its answer from 0, -1 for none, a grid's id of length 0 its end, a card's five answers written at `out`, and
`ui_focus` with an id of length 0 reads instead of moving, answering the
focused id's length (0: none). The faces are `runtime/ui.py` (Python),
`native/moycore/moycore_ui.h` (Lua) and `native/moy_ui/moy_ui_wasm.h` (the
rows), all over `native/moy_ui/moy_ui_api.h`; `tests/test_ui_public.py`
holds one fixture page drawn by each to the same pixels.

## 2. Semantics

- **Ids.** A widget's id is its label, or `o.id` where two share a label; a
  part names its own, and a page is its title. The engine keeps focus, a
  page's scroll, a list's row and scroll and a slider's drag by id from
  frame to frame, and drops an id's state the first frame it is not drawn.
  A duplicate id in one frame is no stop, and the Python face logs it once.
- **The engine's state** is a context per running app: the Python face's
  is bytes its host keeps (`ui_draw.ui_context`), begun each frame by the
  host before the app's update (`ui_draw.ui_frame`); a Lua cart's and a
  compiled app's is the run's one, reset when a run opens and begun by the
  first verb of each tick over the run's snapshot, the input its `btnp`
  reads. An app's own memory holds none of it.
- **One focus.** One stop holds focus per screen; in a windowed host, in
  the focused window, and a window behind draws none. On a page's first
  frame it is the first stop drawn; `ui.focus(id)` moves it, and focus on
  an id that stops being drawn passes to the nearest stop.
- **Navigation** resolves once per frame, before its first ui call, over
  the stops the previous frame recorded: up and down to the nearest stop
  above or below, left and right to the nearest beside (the least gap along
  the arrow, then across it), Tab in call order, wrapping. Tab is the typed
  key 9; the input carries no shift with it, so there is no Shift-Tab. A
  focused slider, cycle, seg, tab row or swatch picker keeps left and right
  (a cycle wraps, the others stop at their ends), a list keeps up and down until its
  first or last row. The page scrolls to keep focus, or the list row it
  moved to, in view (focus on its first stop shows it from its top, the
  caption above included). A pointer drag's direction is decided once, when
  it first passes 4 pixels (at the font scale), as a phone's is: a mostly
  vertical one scrolls the page from whatever row it went down on, a
  slider's and a stepper's included, and is no tap; a mostly horizontal one
  on a slider drags its knob, and on a cycle, seg, tab row or swatch picker
  taps where it is released.
- **Activation** is `a` or Enter (`run`) on the focused stop, or a tap or
  click released inside the stop it went down on, which focuses it as well.
  A button or a link answers true that frame, a toggle flips, a list makes
  the focused row `cur` (the tapped row, for a tap), which then wears the
  current mark; a cycle, a seg, a tab row and a swatch picker take their
  next option, or for a tap the one tapped (a cycle, whose options are not
  shown, its next); a tap on a slider takes the value under it.
- **`b` and back are the host's.** The ui never reads them: back leaves the
  page under the host's bar contract (`docs/app_api_v1.md`), and a cart
  still sees `b` through `btnp`.
- **`ui.keys_taken()`** tells a cart with its own input beside a menu
  whether to act on this frame's `btnp`: true when an arrow, `a`, Enter or
  Tab was pressed while a stop the engine navigates holds focus.
- **Settled.** A frame whose input moved no focus, activated nothing,
  pressed nothing and scrolled nothing is settled (`ui_draw.ui_frame`
  answers it), and a page drawn again draws the same pixels.
- **Layout.** `ui.page` fills the app's surface with the page's ground and
  its title (under a theme with a depth the `panel` colour, or the window's
  body as its frame paints it where the host begins the page in a window --
  `ui_draw.ui_frame`'s `window`, a run's snapshot slot `SNAP_WINDOW` -- and
  the title as a heading, else the panel and its title strip) and stacks the rows from the top of the content rect it
  answers, full width, at the row height for the size class
  (`native/moy_ui/style.json`'s `row` metrics `stack` and `stack_desk`: 20 on the handheld, 28 on
  the desk, as DESIGN.md's sizes; the host names the class) and clipped to
  it. A cart's surface is its canvas, the host's strip over its top as over
  the rest of it (`docs/app_api_v1.md`'s bar contract); a shipped app's is
  the rect its host begins the frame with. A label and an info are rows
  with no stop; a link, a cycle, a seg, a swatch picker, a toggle (its
  On/Off word and switch) and a slider (its number and track, which a
  pointer drags over, or with `steps` its segments alone) are rows with their value at the right
  (`docs/media/look_2026-10/DESIGN.md`, Components); a list is its label's row, then a row per item: every item where
  it stacks (the page scrolls), its own scroll inside `ui.at`'s rect.
  `ui.icon(name)` puts an icon before the next row's label (a label, info,
  link, cycle, seg, swatch picker, toggle, slider or progress), or on the
  next button, before its label or alone where it has none: the theme's
  icon set's slot of that name (`runtime/iconsets.py`, step 16's sets), else
  the glyph table's glyph (`lock`, `key`), in the label's ink; a cart's
  canvas takes the glyph, as its text takes petme128. `ui.progress(label, v,
  hi)` is a row with no stop showing `v` of `hi` done as a bar in `value` and
  its percent, the slider's track without a knob, `v` clamped to 0..`hi`.
  `ui.table(label, columns, rows, cur)` is a list in columns: its caption,
  a header row where any column is named, then a row per item, `cur` the
  current one (it wears the current mark and follows focus as a list's
  row does); an empty first header makes column 0 the picture column, its
  cells icon names. The columns after the first text column take their
  widest cell, right-aligned, and it takes the rest, cut with an ellipsis
  where the font has one;
  where it would show fewer than eleven characters the columns between it
  and the last drop, then the last. Enter on the current row, or a tap on
  it when it is already current, opens it (the second answer); stacked,
  its rows scroll with the page, and in `ui.at`'s rect they scroll in it.
  `ui.scroll(id)` begins a scroll region in `ui.at`'s rect (else the
  page's room below its rows), whose stacked rows scroll in it by the keys
  that move focus and by a drag, until `ui.scroll()`. `ui.field(label,
  text, max)` is a row with a text field at its right (in a group, the
  row's value as a slider's track is, that wide, its label where the other
  rows' are; elsewhere from its label to the row's end): while it holds
  focus the typed keys go into it (each press once, `a` a letter like any
  other, Backspace taking the last character), at most `max` bytes, and
  Enter is its second answer. `ui.dialog(title, buttons, kind)` begins a
  modal card centred on the surface, its `buttons` at its foot (the last of
  `kind`, the others normal), its body the rows stacked until
  `ui.dialog()`; while it is drawn no stop under it takes input, focus
  opens on its body's first stop, else its first button, and goes back
  where it was when the dialog is no longer drawn.
  `ui.popover(id, w)` begins a card hung under `ui.at`'s rect (else under
  the stop that holds focus as it opens, else centred on the surface), left-aligned with it and kept on
  the surface, above it where there is no room below; `w` wide (0: the
  rect's width), as tall as its body, the rows stacked until
  `ui.popover()`. While it is drawn nothing outside it takes input, focus
  opens on its first stop and goes back as a dialog's does; a press outside
  the card, or Esc (the typed key 27), dismisses it: it answers false that
  frame, its body still drawn, and the app stops drawing it.
  `ui.tabs(label, items, cur)` is a row of tabs from the left, the label
  its id (it draws none), `items[cur]` wearing the current mark.
  `ui.grid(id, w, h)` begins a grid of cards whose pictures are `w` × `h`,
  as many columns as the row holds, centred, its rows stacking on the page
  (or from `ui.at`'s rect's top left) until `ui.grid()`; in a group it lies
  on the page's ground between the caption and the group's rows.
  `ui.card(title, sub)` is the open grid's next card: a stop whose
  picture's rect it answers, as `ui.part` does, with its title and, where
  the card's foot holds it, `sub` centred under it; the current mark (`o`'s
  `current`) covers the card, the focus mark is the theme's on a card (a
  lifted card's picture grows, and the rect it answers with it). The app
  draws the picture there with its ordinary verbs before its next ui call,
  which cuts the picture's corners to the card radius and rings it; a card
  scrolled out of view answers a rect of no size.
  `ui.at(x, y, w, h)` places the next call exactly and leaves the row
  cursor alone, so placed and stacked calls mix freely; before a `ui.page`
  it places the page, and a frame may hold several (a sidebar and a body,
  one focus across both). A `w` or `h` of 0 in `ui.part` is the row's.
- **Groups and hints.** `ui.group(caption)` stacks its caption, then the
  rows stacked after it sit on its card, one under the next with a rule
  between them (on the desk, rules alone), until the next `ui.group` or
  `ui.group()`, which draws the card's foot; a page ends an open group with
  a square foot. `ui.hints(items)`, called after `ui.page` and before its
  rows, draws keycap hints — `items` alternate an action or keys and what
  it does — in a band at the page's foot, which its rows then stop above;
  after `ui.at` they take that rect instead, and in a dialog's or a
  popover's body they stack under its rows, a rule between.
- **Hints name actions; the engine draws the keys of the input in use**
  (owner call 2026-10-18). The actions are `confirm`, `back`, `change`
  (left and right), `tabs` (the previous and the next) and `menu` (the
  console's key), and each input has its keys for them:

  | action | desk keyboard | T-Deck | gamepad |
  |---|---|---|---|
  | `confirm` | ↵ | ↵ | A |
  | `back` | Esc | K | B |
  | `change` | ← → | ← → | ← → |
  | `tabs` | Q E | Q E | L R |
  | `menu` | Super | Mic | Start |

  Touch alone shows no keycaps: no hint draws and `ui.hints` takes no band,
  so the rows reach the foot. Keys spelled out still draw as written
  (space-separated; `enter`, `left`, `right`, `up` and `down` are signs),
  and `enter`, `Esc`, `left right` and `Q E` name their actions. A
  one-glyph cap is square. The input in use is the LAST one used, as a PC
  game swaps its keyboard and pad prompts: the input table names the
  source that brought news (`moy_input_news`), and the console
  (`Workstation.use_inputs`) maps it through the inputs its board declares
  — the T-Deck its keyboard, a BLE keyboard and touch; the touch boards
  touch and a BLE keyboard; the host its keyboard, its mouse being no
  finger. A board that declares none draws the desk keyboard's keys.
- **Menus.** `ui.menu(label, items, icons)` stacks its caption (`label`, as
  a group's; empty, none, and then a rule where rows sit above it), then a
  row per item, each a stop whose id is its text, with the icon named at
  its place in `icons` (as `ui.icon` names one; an empty name, none) before
  its label; the focused item wears the focus mark, and an activated one is
  the answer that frame. After `ui.at` the rows lie from its rect's top
  left, across its width. A menu is a card's rows: in a popover it is the
  system menu (hung under the Moy button) or the pause menu (a popover with
  nothing to hang from -- no `ui.at` rect, no stop holding focus as it
  opens -- is centred on the surface).

## 3. Overrides

| key | value | does |
|---|---|---|
| `fill`, `ink`, `border` | a role name, or a colour `0xRRGGBB` | replaces the kind's colour: a role (`"danger"`, `"value"`) still follows the theme and its mode; a raw colour is the app's own, and the readability check does not vouch for it |
| `id` | text | the id, where the label is not unique |
| `current` | true | the current mark, on a button or a part |
| `disabled` | true | dimmed, no stop, never activates |
| `nav` | false | the engine stops moving focus here (§4) |
| `mark` | false | the engine draws no focus mark here (§4) |
| `steps` | true | a slider draws a segment per step from `lo` to `hi`, the ones up to `v` filled, and no number |

No key reaches a shape, a radius, a font, a metric or a mark's style. An
override colour is RGB, as a theme's is; the draw verbs' palette indices
(`& 63`) are a separate space. In wasm the block is nine words in the
order above, -1 for absent: a role written as `0x1000000` plus its index in
the token row (`native/moy_ui/style.json`'s `tokens`), the id's word its
length in bytes with its text after the nine words, a flag 0 or 1
(`native/moy_ui/moy_ui_api.h`).

## 4. Taking focus over

`nav = false` on a page: the engine never moves focus inside it; the arrows
and `a` are the cart's (`ui.keys_taken()` answers false) and the cart moves
focus with `ui.focus`. On a part: focus arrives by the engine's navigation
and then stays, the keys the cart's — a swatch grid, a game board — until
the cart calls `ui.focus` elsewhere.

`mark = false`: the engine draws no focus mark, and the cart draws its own
look from `ui.part`'s `state`. Both keys work on any stop.

## 5. `ui.part`

`ui.part(id, w, h, o)` reserves a stop for content only the cart can draw:
a colour swatch, a cover, Calc's display. The engine lays it out (a row, or
`ui.at`'s rect), draws its fill and the theme's marks — focus, and current
when `o.current` — and answers `x, y, w, h, state`; the cart then draws into
that rect with its ordinary verbs. `state` is bits: FOCUS 1, ACTIVATED 2
(this frame), PRESSED 4, HOVER 8 (`ui.FOCUS` and its siblings in Python).
Its fill is the theme's display inset: the `lcd` role, ringed by the
look's `lcd_border` or bevelled by its `lcd_bevel`, its corners the key
radius up to 8 pixels on the handheld and 10 on the desk (square without a
depth); a disabled part is no stop. A part may read `theme()`'s roles to
match its surroundings, never write them; a Python app measures the text it
draws there with `ui.text_size`, and `ui.has_symbols` says whether the
font has `− × ÷ ← →`. `ui.face(name, text)` has its prints draw in the
theme's face for type role `name` (Calc's result is `result`) where the
theme installs one that draws every character of `text`, answering
whether it did, and `ui.face()` puts the print font back: the theme names
the face, the app only the role. A button's label is in the face its
kind's `font` leaf names (`buttons[kind].font`, `app_buttons[app]` for a
shell app), where one is installed and covers the label.

## 6. Theming stays the engine's

The theme supplies the row heights and type per size class, each kind's
look (`buttons[kind]`, `app_buttons`) and the `focus` and `current`
properties, so a new theme restyles every app that kept its defaults with
no change to the app. A Lua or compiled cart's buttons take the same leaves
(shape, radius, depth, colours) as a Python cart's: its canvas has MOY64
only, so a leaf's colour is its nearest MOY64 index, the rule a Python
cart's page takes inside the cart boundary (`moy_ui_pidx`), and the three
runtimes draw one button.

## 7. The shell is strict

The shell's apps — Settings, Appearance, Files, Calc, the editors and the
system carts' code — call only the verbs, with no colour key and no `nav`
or `mark`, so their look is the theme's entirely. They lay out with
`ui.page`'s rows, or with `ui.at` over rects cut from the content rect
`ui.page` answers (the rect algebra stays in `runtime/ui.py`), into the
frame their host side begins (`ui_draw.AppHost`, an app's `ctx.ui` when its
class sets `UI = True`). The engine
layer under the verbs — today's rect-taking widgets, `Hits`, the marks
(`focus`, `current`) — moves to `runtime/ui_draw.py`, which the chrome (bars, window frames,
the home, the window managers) keeps; `runtime/ui.py` becomes the verbs.

The ratchet, `tests/test_ui_public.py`, scans the shell's app modules and
system carts for the engine layer (`ui_draw`) and for the colour keys, `nav`
and `mark` (`id`, `current`, `disabled` and `steps` pass). It pins the list of apps not yet moved,
which can only shrink: each screen step that restyles an app (19–24) takes it off, but
the editors, which steps 23 and 24 restyled in place (§1a), and step 27 holds it empty. While a system cart is on that list, an app cart's
namespace carries `ui_draw` beside `ui` (`runtime/system_api.py`).

## 8. The wasm rows

The `ui` rows are §1's twenty-eight; the nine before them (the kind and glyph
lookups, the rect-taking button, label and list, the hit buffer, its pump
and the drag over buffers in the app's memory) went in one commit, with no
compatibility rows: there are no users. The engine keeps focus, the
previous frame's stops and each id's state per running app (§2), so an
app's memory holds no ui buffers. The fixture
`tests/fixtures/wasm/app_ui.moy` imports every row, and
`tests/test_roles.py` holds that and the table, the adapter and
`docs/app_api_v1.md` together; a step that adds a widget adds its row, and
the fixture imports it.

A Lua cart reaches `ui` as the vendor extension `moybyte.ui` and may use
it opportunistically (`if ui then`, SPEC.md §10): every Lua run on a host
with the toolkit has the table, its theme the console's live one; a
compiled app imports the rows from module `"moybyte.app"`, as it does every
role's.

## 9. moy-spec

moy-spec gets no proposal (owner, 2026-10-15). Were another host to want
the API, `proposals/ui.md` would carry the verbs as they then stand, the
semantics (§2) and the override keys (§3), with kinds and marks named and
not drawn, a reference look in palette indices in libmoy, and conformance
that tests behaviour under scripted input and never a pixel.
