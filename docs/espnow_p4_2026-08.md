# ESP-NOW on the P4: the hosted-shim track (started 2026-08-24)

`docs/espnow_multiplayer_2026-08.md` settled that the P4 cannot join a link
today ("The P4 cannot join": the flag flip dies at link, ESP-Hosted's RPC has
no ESP-NOW, upstream esp-hosted-mcu#19 is open and unshipped). Multiplayer is
a core pillar, so this doc is the WORKING PLAN for the one viable path that
section named: ESP-Hosted >= 2.8.1 custom RPC + a C6-side shim. Everything
below is either measured on this desk or read out of the exact component
revisions named; when a phase lands, its facts move to the authority docs and
this file records the verdicts.

## The shape (decided)

**Host: implement the 17 missing symbols, keep everything above them.**
`MICROPY_PY_ESPNOW (1)` fails at link with exactly these undefined:
`esp_now_{init,deinit,send,add_peer,mod_peer,del_peer,get_peer,fetch_peer,
get_peer_num,is_peer_exist,set_pmk,get_version,register_recv_cb,
unregister_recv_cb,register_send_cb,unregister_send_cb}` +
`esp_wifi_config_espnow_rate`. A board-local component (`esp_now_hosted`,
beside `moy_ble_hid` in the P4 tree) provides them as thin wrappers over the
hosted custom-RPC seam, so:

- MicroPython's own `modespnow.c` compiles and runs UNCHANGED -- its rxbuf
  ring, its Python API, its semantics are upstream's problem, not ours;
- `device/moy_espnow.py` runs UNCHANGED -- it imports `espnow`, configures
  `rxbuf` (a host-side ring, no RPC involved) and `rate` (one RPC), and drains
  `irecv(0)` per frame exactly as on the S3s;
- the S3 boards notice nothing: the radio waveform is genuine ESP-NOW out of
  the C6 (v2-capable; v2<->v1 interop holds at <=250 B payloads and ours are
  ~16-60 B).

**Slave: the stock esp-hosted-mcu slave + one shim file.** The slave keeps its
app_main; our shim registers custom-RPC handlers that forward to the REAL
`esp_now_*` on the C6 and pumps two event streams back. No fork of the RPC
protocol, no protobuf edit -- the custom seam is upstream's own, shipped and
documented since 2.8.1.

## The custom-RPC seam (verified present in 2.12.12, both halves)

    esp_err_t esp_hosted_send_custom_data(uint32_t msg_id, const uint8_t*, size_t);
    esp_err_t esp_hosted_register_custom_callback(uint32_t msg_id,
        void (*cb)(uint32_t, const uint8_t*, size_t, void*), void *ctx);

Symmetric on host (`host/esp_hosted_misc.h`) and slave
(`slave/main/esp_hosted_peer_data.h`); payload cap 8166 B (ESP-NOW's own cap
is 250, so one message per frame, never fragmentation). Also present and
relevant: `esp_hosted_get_coprocessor_fwversion` (ask the C6 what it runs)
and the STREAMED slave OTA -- `esp_hosted_slave_ota_{begin,write,end,activate}`
-- which is the same feed-it-chunks shape as `moy_ota`, meaning the C6 gets
updated FROM THE P4 over SDIO with no URL and no extra wires.

## Message protocol (FROZEN v1, 2026-08-24 -- espnow_shim_proto.h is the body)

EXACTLY ONE hosted msg id per direction (H2S/S2H), verbs multiplexed in an
envelope byte: the seam's handler table is
CONFIG_ESP_HOSTED_MAX_CUSTOM_MSG_HANDLERS deep and DEFAULTS TO 3 per
processor, so a one-id-per-verb design would have silently needed a slave
Kconfig bump -- a half-set of the exact kind this repo keeps finding. One
handler slot per side, forever.

    host -> slave:  INIT  DEINIT  PING  SEND{dst_valid,mac[6],len,payload}
                    ADD_PEER{mac,channel,ifidx,encrypt,lmk} (UPSERT)
                    DEL_PEER{mac}  SET_RATE{ifidx,rate}  SET_PMK{pmk[16]}
    slave -> host:  ACK{verb,err}  RECV{src,dst,rssi(i8),len,payload}
                    SEND_STATUS{mac,status}

INIT/DEINIT/PING always ACK (they are the handshakes -- a missing ACK is how
a stock slave says "no shim"); every other verb ACKs only on FAILURE, and an
ACK(SEND, err) synthesizes a FAILED send callback on the host so modespnow's
sync accounting never hangs on a slave-side error.

Send-status is forwarded HONESTLY (per-send, from the C6's real send cb) so
`send(sync=True)` keeps its meaning -- even though moy_espnow never trusts it
("the ack lies" is a radio fact the shim must not launder further). RECV
carries rssi because `modespnow`'s recv info wants an `rx_ctrl`; the shim
fabricates the minimal struct around it.

Channel: same policy as the S3s today (no explicit channel; two unconnected
consoles both sit on the default). The pre-existing open question -- a console
CONNECTED to an AP rides that AP's channel and a lone unconnected peer will
not hear it -- is unchanged by this design and stays an S3-parity question,
not a shim question.

## Phase ledger

**A. Host feasibility -- DONE 2026-08-24, ALL GREEN INCLUDING ON GLASS:**

- MicroPython pins `esp_hosted: "2.7.0"` exactly (`main/idf_component.yml`);
  `esp_wifi_remote` 0.15.2 constrains only `>=0.0.6`, so 2.12.12 is
  manifest-legal. Bumped in the build tree, lock + managed copy dropped,
  component manager fetched 2.12.12, **the image builds clean** and the
  archive carries every symbol named above.
- **First on-glass verdict: 2.12's transport mempool cannot allocate at boot
  on this board** -- `E HS_MP: mempool create failed: no mem`, then the SDIO
  driver reads no registers and the board crash-loops (~30 s period, display
  up each time). The fix candidate is upstream's own and names this exact
  target: `ESP_HOSTED_MEMPOOL_PREFER_SPIRAM` (2.12.8, "preserves scarce
  internal RAM on targets where GDMA can reach PSRAM through cache (e.g.
  ESP32-P4)"). The tracker's EHM-250 warns that knob breaks DMA alignment at
  a 128 B L2 line; **this board's line is 64 B** (generated sdkconfig), so
  the warning's trigger is absent. **The knob fixed it**: clean boot, first
  frame in 206 ms, zero HS_MP/SDIO errors across capture.
- **The 2.12.12 host TALKS TO THE FACTORY SLAVE.** Measured 2026-08-24, same
  AP as every number this week: wifi autoconnects, the webhost serves, and
  the raw-socket RX bench lands 4 MB at 2.87-2.98 MB/s warm against 2.7.0's
  3.18-3.24 -- parity within AP variance. BLE (NimBLE over hosted VHCI, the
  keyboard's stack) comes up and scans with no error. So the host bump ships
  ALONE and the board stays whole; the C6 reflash is a prerequisite only for
  the espnow half, exactly the risk split Phase D wants. Still unread: the
  factory slave's version string (`esp_hosted_get_coprocessor_fwversion` has
  no Python surface yet; the shim component will expose it, and Phase D's
  updater wants it printed before and after).
- **Landed on dev the same day**: build.sh step 2c' bumps the manifest
  (marker-guarded, drops the stale per-target lockfile so the component
  manager re-resolves) and the board fragment carries
  `CONFIG_ESP_HOSTED_MEMPOOL_PREFER_SPIRAM=y` with the crash-loop prose.

**B. C6 slave build -- DONE 2026-08-24, no hardware touched:**
`c6_slave/build.sh` stages the slave project OUT OF THE SAME managed-component
checkout the host builds against (version match by construction, not by
discipline -- it refuses to run before `make firmware-build-p4` has fetched
the component), copies in `slave_espnow_shim.c` + the one-body protocol
header, patches the two stock files marker-guarded (CMakeLists source list;
the app_main example-init tail), and builds esp32c6/SDIO on the same IDF
checkout every moybyte esp32 build uses. Output:
`dist/p4/c6_network_adapter.bin` (1,207,264 B, hosted 2.12.12, five moyc6_*
symbols confirmed in the ELF).

**C. Host shim -- DONE the same day, proven on glass against the FACTORY
slave:** `native/moy_c6/modmoy_c6.c` implements the seventeen symbols;
`MICROPY_PY_ESPNOW (1)` is ON and the stock modespnow.c compiles unchanged
(image +30 KB, 400 KB ota-slot headroom). On the desk, with the stock C6:
`import espnow` -> module exists (two days after the linker said never);
`moy_c6.ping()` -> False (the honest capability probe); `moy_c6.fwversion()`
-> None (the factory slave does not answer the version RPC -- consistent with
the community enabler's report); `ESPNow().active(True)` -> OSError raised
cleanly, desk still running. The soft-fail contract holds end to end. The
`moy_c6` module also carries the streamed slave-OTA verbs
(`ota_begin/ota_write/ota_end/ota_activate`) -- Phase D's updater, drivable
from MicroPython over the ordinary serial machinery.

**D. DONE 2026-08-24, owner-consented, and the radio is ON THE AIR.** The
streamed OTA ran end to end -- twice, because iteration turned out cheap
(~40 s: HTTP fetch to the P4's VFS at wifi speed after an ARP warm, sha-check,
1500-byte `ota_write` chunks over SDIO, activate): the C6 now answers
`fwversion() -> "2.12.12"` and `ping() -> True`. THE CROSS-ARCHITECTURE
PROOF, both directions: the P4's `ESPNow().recv()` catches the T-Deck's live
discovery beacons (`b'\x01\x01\x00tdeck|tdeck|'` from its exact MAC -- the
REAL moy_espnow wire bytes, so Phase E's console integration speaks a proven
protocol), and a P4 broadcast increments the T-Deck link's rx counter. WiFi
through the new slave is intact (autoconnect + webhost + the 2.9 MB/s bench).

Learned on the way, each now encoded where it bites:
- `ota_write` chunks are 1500 B (the RPC's own example size; 4096 fails EIO).
- The OTA image self-hosts: HTTP GET from this machine works after an
  ARP-warm (host talks to the board first; the repeater AP drops the board's
  cold ARP who-has, which also explains every EHOSTUNREACH in the benches).
- espnow on this board needs `WLAN(0).active(True)` FIRST -- the C6's radio
  starts with the host's wifi, so `active(True)` before it fails EPERM. The
  S3s' own module already lives by this rule; moy_espnow.start() holds.
- The factory slave image was NOT preserved (its bytes may survive in the
  C6's inactive OTA slot, but nothing reads them back). Recovery from a bad
  slave is a re-OTA of our own build, or the UART header.

**D-tail: BLE against the 2.12 slave -- FIXED the same day, and the bug was
ours all along.** The hunt's shape is worth keeping because every wrong turn
was a plausible verdict:

- Espressif's own bleprph VHCI example, built for this exact host+slave pair,
  WORKED -- which exonerated the slave and hosted, and left "something in
  MicroPython's arrangement".
- A host built without any of the espnow additions still died: espnow
  exonerated. HCI debug logging off (upstream's p4_wifi_common ships it ON;
  ruled out, kept off anyway): still died. NimBLE host task moved to core 1:
  still died.
- The crash dump finally said it plainly: core 1 spinning forever on a
  spinlock INSIDE `ble_freertos_ev_buf` -- NimBLE's static npl event arena --
  while core 0 sat in the idle loop. Nobody held that lock; its MEMORY WAS
  CORRUPT. And the corruption's source was the pattern nobody had questioned:
  every manual `active(True)` was a SECOND attempt, because the boot-time
  keyboard start always ran (and failed) first. First attempt: clean HCI
  timeout. Every retry: panic over the state the failed attempt's cleanup left
  behind (nimble deinit racing a transport that keeps delivering -- a real
  upstream bug in its own right, but only reachable through a failed first
  activation).
- WHY the first attempt failed is the actual root cause, and it is the #212
  contract plus one boot-order fact: hosted >= ~2.8 slaves do not self-init
  the BT controller, and at boot the keyboard driver runs BEFORE any network
  use -- so the hosted transport was not up, `bt_up()`'s controller RPCs
  failed silently, the controller never started, and NimBLE timed out against
  dead HCI. The factory slave self-initialised its controller, which is why
  those images worked for weeks and why the regression tracked the slave swap.

The fix is three lines and it is the working example's own preamble:
`moy_c6.bt_up()` = `esp_hosted_connect_to_slave()` (idempotent transport
bring-up) + `bt_controller_init()` + `bt_controller_enable()`, called by
`ble_keyboard.start()` before `active(True)`. On glass: the BOOT-TIME first
activation now succeeds -- "Moybyte BLE keyboard: scanning" -- and one image
runs WLAN + BLE + ESP-NOW through the one C6 simultaneously (bt scanning,
ping() True, wifi up, and `recv()` catching the T-Deck's beacons, in one
session). The npl-corruption-on-failed-activation remains a latent upstream
issue our path no longer reaches; if a first activation ever fails again, do
not retry in-process -- reboot, and re-read this entry.

**E. On-glass lockstep parity -- DONE 2026-08-24, with one cross-architecture
desync found and killed.** `moy_espnow.py` staged (board.toml group),
`moy_runtime` wires link + per-frame poll exactly as the S3s (the service
parity + lifecycle ratchets verify both). The match: both consoles `run
brick siege`, discovery in ~1 s, the P4 hosts (lower MAC), 28.6 ticks/s over
a 60 s hold with 5.7-6.9% stalls (vs the S3 pair's 3.0% -- acceptable, not
yet tuned), frame gap <= 5, neither side waiting.

THE DESYNC, owner-felt on first play ("inputs work, the game isn't in
sync"): tanks identical on both screens, enemies on completely different
paths. The frame-aligned world-checksum probe (an `_update` wrapper keyed by
lockstep frame -- wrap `ws.player._update`, NOT the ns entry, which the
Player captured by reference at start) measured 0/1105 frames agreeing, and
one dump line told the whole story: the same accumulator prints
`0.21666668` on the T-Deck and `0.216666668` on the P4. The S3s run REPR_C
(30-bit truncated floats, #66); the P4 ran REPR_A boxed 32-bit singles --
identical math at different precisions, and chaos amplifies the tail
difference into flipped branch decisions within seconds. **FLOAT WIDTH IS
PART OF THE LOCKSTEP CONTRACT**: the P4 takes `moybyte_patch_repr_c`
(build.sh 2e, where the week-old DECLINED entry records its own reversal),
and after the flip the same probe reads **1106/1106 frames bit-identical**.
The paired perf A/B (same tree, same flash cycle): Sky Run 58.0 -> 56.5,
Sakura 51.0 -> 51.5 -- ~1.5 fps on one cart, noise on the other.
(Separately noticed, NOT this track's: today's roster numbers sit ~4 fps
under #58's post-#159 table on BOTH arms -- the week's hosted-2.12/mempool
changes or measurement conditions; re-sweep under #58's procedure before
optimizing anything.)

Bench discipline learned twice today: the CH343 open GLITCH-REBOOTS the P4,
so a measurement that spans a match must hold ONE serial handle for its
whole life -- a reopen mid-experiment silently kills the match it measures.

## Standing decisions for this track

- The hosted bump ships AHEAD of the shim -- reversed from this doc's first
  draft, on the Phase A measurement: the 2.12.12 host is at wifi/BLE parity
  against the factory slave, so the bump costs nothing a kid can see and
  splits the risk -- every later phase changes exactly one thing at a time.
- `main/idf_component.yml` is MicroPython's file; the bump lands as a
  marker-guarded edit in the P4's build.sh patch ladder (step 2c'), like
  every other upstream-file change.
- Nothing in `runtime/` or `device/` changes for any of this. The protocol,
  netplay, discovery and the carts are DONE and S3-proven; this track is
  transport plumbing underneath an unchanged `espnow` module surface.
