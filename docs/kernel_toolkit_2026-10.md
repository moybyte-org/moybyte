# The toolkit, data-driven — sprint 6's design (2026-10)

**What this is.** What sprint 6 of `docs/native_kernel_2026-09.md` (#224) is to
build, set down ahead of the code: the widget toolkit's bodies in C, with
everything a restyle, a translation or a re-layout touches held as data; one
text path for every app runtime; the end of `surface.glyph`; compiled apps in a
window; the crossing, the pass order, the gate and the budget. Status and the
sprint's measurements are #224's; frame numbers are #66's.

**The scope (owner, 2026-10-10; the plan's §10 question 8).** Sprint 6 runs
data-driven: themes, strings and layout are data over C widget primitives, so
most UI changes stay data edits. Sprint 7 does not run: the window managers, the
bar, the desk and the rest of `runtime/console.py` stay Python, and nothing here
assumes they cross. A windowed compiled app (a window's surface, its size and
its focus) is this sprint's (`docs/kernel_appabi_2026-10.md` §12 answer 8).

**What it stands on.** Sprint 3's glass: the canvas rows and the draw gates
that check them (`native/moy_glass/moy_canvas.h`). Sprint 4's chrome as display
lists (`native/moy_play/moy_chrome.h`). Sprint 5's app ABI: the role table
(`native/moy_app/roles.json`), the live token table and its generation, the
per-grant surface row, the `moybyte.app` import extension and the adapter's hop
and seqlock (`docs/kernel_appabi_2026-10.md` §2, §4).

**Nothing moves a pixel.** This sprint has no deliberate re-baseline. A step
whose crossing moves one golden hash does not land.

## 1. The toolkit today

SOURCE, `runtime/ui.py`. Immediate mode over the canvas verbs, no retained
tree. Style is already data: `DEFAULT_SPECS` (kind × state → a `(field, ink,
edge)` triple of token specs) and `DEFAULT_METRICS` (kind → a tuple of pads,
edge rings, boxes, alignment), flattened per theme into shared tuples behind a
four-entry identity ring; `runtime/skin.py` holds the skins as deltas over both.
Geometry is pure and separate from drawing. The six-state ladder resolves in
`widget_state`; `Hits` is the pointer pump for bounded widget sets and
`ScrollRegion` the one scroll model.

What is not data yet: the widget bodies (each a Python function issuing three
to eight canvas calls), the glyph vocabulary and its raster (twice: Python's
`chrome._blit_glyph` and moy_chrome's C, fed by a push of the Python table at
start), the scaled-text helper that draws a glyph pixel per `rect`, word wrap
(twice: `ui.wrap_words` and moy_chrome's `panel_lines`), every string, and
every layout.

Why the bodies cross is #66's (the P4 editor attribution): chrome surfaces are
dispatch-bound, Python plus the MicroPython-to-C transition per canvas call,
and on the S3s each extra Python layer per call is the cost. A widget drawn by
one C call in place of several Python canvas calls removes that share. Why they
cross now is the plan's §4.5: one implementation for every app runtime, so a
Python app and a wasm app draw the same button through the same code.

## 2. What makes it data-driven

### 2.1 The four tables

| data | its source | read by | changes it |
|---|---|---|---|
| **theme tokens** | `runtime/chrome.py`'s `THEMES` and `THEME_LIGHT`, flattened by the look into native/moy_app's live token table (sprint 5) | the C style resolution, every app's `theme` reads | a theme edit; theming's packages later (`docs/theming_2026-09.md` §3) |
| **style** | `+native/moy_ui/style.json`: the kinds, the states, each `(field, ink, edge)` spec, each kind's metric tuple with its slot names, the skins as deltas, the glyph vocabulary | `+native/moy_ui/moy_ui_tables.c`, generated by `+tools/gen_ui_tables.py` and checked by a test, so the default style costs no RAM and no boot parse | a style edit |
| **layout** | a layout spec: a short array of nodes (§2.3), as JSON beside the surface that owns it | `moy_ui_layout`, at relayout only, never per frame | a layout edit |
| **strings** | `+native/moy_ui/strings/en.json`, one entry per string id, English complete | the C table generated with the style (§2.4) | a string edit; a language pack later |

A data edit regenerates the C table on the next build (the host's at first use,
as `runtime/native_build.py` does) and touches no C and no Python logic. It
still needs a firmware build to reach a board: what it saves is the C edit, its
review and its risk, not the flash.

**The style file is the part list theming phase 1 freezes**
(`docs/theming_2026-09.md` §4.3): parts and states as nested objects, every
kind the toolkit resolves, plus the quirks of `NON_DATA_QUIRKS`, each recorded
against the kind it belongs to. A theme package, when theming's loader lands,
installs a delta over it through the same entry a skin uses.

### 2.2 Which edits stay data, which need C

| a change | the edit |
|---|---|
| which token a widget state paints; a skin; a theme's colours | data (style; tokens) |
| a pad, an edge weight, a strip height, a label alignment | data (metrics); a size change moves goldens, a deliberate act as today |
| a new kind that reuses a primitive's shape: a toggle, the Studio's pane tab, a quiet or a danger row | data (style) |
| a glyph's pixels; a new glyph | data (style's glyph vocabulary) |
| a string; a language | data (strings) |
| the layout of a surface that takes a spec (§2.3) | data (layout) |
| an app's own screen: its Layout class, its `_base` branch, which widget it draws where | Python (apps stay Python, plan §3) |
| the bar, the desk, window chrome, the WMs' caches | Python (sprint 7 does not run); the in-cart chrome stays moy_chrome's C |
| a new primitive shape (a splitter's grip, a drop zone's dash), a new state, a new metric slot, a quirk, the hover and press rules, scroll physics, the text lane, a font format, theming's surface painter | C |

### 2.3 Layout as data

A **layout spec** is an array of nodes evaluated against `(w, h, fs, cs)` into
an array of boxes, one per SLOT node, in spec order:

| node | carries |
|---|---|
| `col`, `row` | a direction, a gap, its children |
| `inset` | four sides |
| `size` (on any child) | `px`, `fs` cells, `cs` cells, a fraction of what is left, or `rest` |
| `scroll` | a view slot whose content extent the caller sets per frame |
| `slot` | a named box the caller draws into |

The unit set is the one the shipped layouts already compute in (`8 * fs`, `18 *
cs`, `(h - top) // row_h`), so a spec reproduces today's arithmetic instead of
approximating it. `moy_ui_layout(spec, n, w, h, fs, cs, out, cap)` returns the
slot count; the Python face caches the boxes on the Layout object, which keeps
the rule that layouts are built at init and relayout only (`runtime/layout_base.py`).

The rect algebra (`inset`, `cut_*`, `hsplit`, `vsplit`) crosses with it: the
evaluator is made of it, and a wasm app needs it by import.

**What takes a spec.** `runtime/app_shell.py`'s `ListShellLayout` (Files,
Storybook and the list apps built on it) and the compiled apps (§6). The
frozen `_base` layouts (`chrome.Layout`, `CodeLayout`, the editors') do not:
they are the 320×240 parity contract, owned by apps and the WMs, and theming
phase 2b retires them. Question 4 (§13) is the owner's.

### 2.4 Strings as data: the localization hook (#135)

A string id is a dotted name (`chrome.stuck`, `fit.needs_free`); the table maps
it to UTF-8 text. C reads `moy_ui_str(id) -> span`; the Python face reads
`ui.s(id)` at layout or at draw (one interned dict get); a compiled app reads
`ui_str(id, buf)`. A formatted string keeps its arguments' order and count in
the table's text (`%s` as moy_chrome writes them today), and a language pack
whose entry carries different conversions than English's is refused for that
id, which then reads English: a pack is untrusted data, as a theme is
(`docs/theming_2026-09.md` §7).

Sprint 6 builds the table, English, and the strings drawn in C: moy_chrome's
(the stuck and fit texts, the panel titles, the menu rows) and the recovery
screen's (`native/moy_kernel/moy_recovery.c`). Those are the strings whose
change is a C edit today. The Python surfaces' strings move under a ratchet as
later edits (question 2). No language row lands in Settings until a second
language exists.

Glyph coverage, #135's other half, is font data: the text call takes UTF-8 and
a font handle (§4), and a font that covers Cyrillic is a data file in theming
phase 4's font format, not a toolkit edit (question 3).

### 2.5 The absorbed issues

Of the plan's §6.2 row for sprints 6–7, what lands in the toolkit: #135's string
hook (§2.4); #177's pump, which crosses whole (§3.4), while extending hover to
the desk icons, the window strip and the taskbar is WM work and stays with the
WMs; #146's press cue, already the `pressed` state's data. The rest of that row
(#140's charm items, #132, #129, the Studio's docking) lands in apps and WMs,
not here. The Studio's new parts are kinds in the style file; one whose shape no
primitive draws adds a primitive when the Studio lands, which by its §8 is not
during this sprint.

## 3. The C primitives

### 3.1 The module

`+native/moy_ui/`: the style resolution, the primitives, the hit pump, the
scroll model, the layout evaluator and the string table. Three bindings, the
moy_app pattern: a MicroPython usermod (`+native/moy_ui/modmoy_ui.c`) on the
boards and in the browser, a ctypes binding on the host
(`+tools/moy_ui_binding.py`), and the `ui` rows of the role table for wasm
(§3.5). The Zero denies it in its board.toml: it runs no apps.

**The sink.** A primitive draws through a sink, never a canvas object:

    typedef struct {
        uint8_t kind;      // ROW: a CANVAS row; RUN: a compiled run's libmoy canvas
        uint8_t fs;        // the font scale: the row's FONT_SCALE, or the grant's surface row
        uint8_t look;      // which flattened style table: the shell's or the run's
        void *dst;         // moy_canvas_row_t * or moy_canvas *
    } moy_ui_sink_t;

The ROW sink draws into a canvas row of sprint 3's glass, named by its CANVAS
handle and checked like any handle, through the kernels the canvas verbs end in
(`native/moy_gfx/moy_gfx_kernels.h`). Around each op it does what the draw
gates do: camera, clip and palette from the row; the row's fill and text
counters, so `gate_counts` holds; the flush pump at the gates' cadence on a
board that has one. The host's canvases are rows too
(`native/moy_glass/moy_glass_host.c`), so the sink is one body on every tier.
The Python face flushes a pending sprite batch before the call, as the canvas's
`print` does (the #63 order rule). The RUN sink calls libmoy's verbs on the
run's console, the ones a compiled cart's own draws end in. Both end in the
same kernels, so one body draws the same pixels into either.

**The look.** The style table resolved against one token row: per kind and
state, three palette indices, `-1` for "paint nothing". It is rebuilt lazily per
kind when the skin's generation or the token row's generation moves, as
`_flatten_kind` does today. There are two: the shell's, read on the VM's task,
and a compiled run's, read on its session thread under sprint 5's seqlock; so
no flatten is shared between threads. A theme dict the Python side passes that
is not the live theme (Appearance's per-card previews, an empty `{}`) is packed
into a token row in the four-entry ring the Python face keeps, as today's
`_FLAT_RING` does, and flattened there.

### 3.2 Call shapes

Every primitive takes a sink, a box, a kind id and a state, then its content.
Text is a UTF-8 span; a glyph is a glyph id or `-1`; a colour override is three
`int16` with `-2` meaning "from the style". A primitive returns what its caller
needs back (a drawn width, an art box, a slot count) or an error.

    typedef struct { int16_t x, y, w, h; } moy_ui_box_t;
    typedef struct { const uint8_t *p; uint16_t n; } moy_ui_span_t;

    int  moy_ui_kind(const char *name, size_t n);    // a kind's id, or -1; relayout time
    int  moy_ui_glyph_id(const char *name, size_t n);
    void moy_ui_colors(const moy_ui_sink_t *s, int kind, int state, int16_t out[3]);
    const int16_t *moy_ui_metrics(int kind);

    int moy_ui_button(moy_ui_sink_t *s, moy_ui_box_t b, int kind, int state,
                      moy_ui_span_t label, int glyph, const moy_ui_icon_t *icon);
    int moy_ui_row(moy_ui_sink_t *s, moy_ui_box_t b, int kind, int state,
                   const moy_ui_row_t *r);          // label, value, glyph, pads, text_dy, scale, edge, overrides
    int moy_ui_cell(moy_ui_sink_t *s, moy_ui_box_t b, int kind, int state,
                    const moy_ui_cell_t *c, moy_ui_box_t *art);

Errors are `MOY_UI_OK`, `MOY_UI_BAD` (an unknown kind, glyph or state, a span
over its bound) and `MOY_UI_STALE` (a sink whose canvas row is gone: the gate's
own check). An icon image crosses as the `spr` gate's own arguments (its pixel
buffer, size and palette), never as an object.

Every `//` of the Python bodies is a floor division in C (`moy_ui_fdiv`): C's
`/` truncates toward zero, and the bodies divide negative differences whenever
a label is taller than its box.

### 3.3 The primitives

| primitive | C | Python face (signature unchanged) | wasm import (`moybyte.app`) |
|---|---|---|---|
| button | `moy_ui_button` | `ui.button(cv, th, rect, label, kind, on, icon_img, glyph, glyph_draw, disabled, state)` | `ui_button(x, y, w, h, kind, state, label, len, glyph)` |
| chip, toggle (a kind of chip) | `moy_ui_chip` | `ui.chip(...)` | `ui_chip(...)` |
| label | `moy_ui_label`: text in a box with a kind's ink, alignment, clip; returns the width | `ui.label(cv, th, rect, text, kind, align, scale)` | `ui_label(...)` |
| row | `moy_ui_row` | `ui.row(...)` | `ui_row(x, y, w, h, kind, state, label, len, value, vlen, glyph)` |
| scroll list | `moy_ui_list`: the visible rows, the selection and the bar over a scroll state | `ui.list(...)` | `ui_list(x, y, w, h, scroll, items, len, n, row_h, sel)` |
| cell | `moy_ui_cell`, returns the art box | `ui.cell(...)` | `ui_cell(..., art_out)` |
| tab row | `moy_ui_tabs`, returns the tab boxes | `ui.tab_row(...)`, `ui.tab_row_rects(...)` | `ui_tabs(...)` |
| status row, panel, toolbar, focus ring, dialog | one function each | unchanged | one import each |
| text field | `moy_ui_field`: the text, the hint, the caret | `ui.text_field(...)` | `ui_field(...)` |
| scrollbar | `moy_ui_scrollbar` over a scroll state | `ScrollRegion.draw_bar` | drawn by `ui_list`, or `ui_scrollbar` |
| glyph | `moy_ui_glyph` (§5) | `ui.glyph(cv, kind, rect, c, scale)` | `ui_glyph(...)` |
| the game-canvas family | `moy_ui_game_btn`, `_game_icon_btn`, `_mini_btn` | unchanged | not imported: cart verbs draw a cart's buttons |
| rect algebra, layout | `moy_ui_inset` and its siblings; `moy_ui_layout` | `ui.inset(...)` and its siblings | `ui_layout(spec, len, w, h, out, cap)` |

**How Python drives one.** `runtime/ui.py` stays the module every shipped app
and every app cart imports (`docs/app_api_v1.md`'s `ui`), with today's
signatures. Each function is a thin face: it turns keywords into the C entry's
positional ints, maps the kind name to its id (interned at first use), and makes
one call with the canvas's CANVAS handle. What stays Python because it is a
Python seam: a `glyph_draw` callable
(`code_layer`'s chip face), which the face calls after the C call drew the
field and the edge; the `th` ring; the `(verb, arg)` ids of §3.4. Text editing
stays the app's (`runtime/editors_base.py`); the field primitive only draws.

**How wasm drives one.** The `ui` rows are C-served and ungated, as the theme's
reads are; they draw into the run's canvas with the RUN sink on the session
thread, with no hop, and leave the VM-free verdict unchanged. An app reads its
kind and glyph ids once (`ui_kind`, `ui_glyph_id`) and the state constants from
the author's header the table generates.

### 3.4 Interaction state: caller-owned buffers, not handles

`Hits` and `ScrollRegion` are state a surface owns for its life. Their rules
(the six-state pump, the press edge, leave, fling, clamp) cross to C as pure
functions over a state buffer **the caller owns**: a `bytearray` inside the
Python object, or a span of the compiled app's linear memory. The kernel holds
nothing between calls, so there is no table, no lifetime and no leak across a
VM stop: the plan's §4.3 rule (no runtime's object held beyond a call) holds
with no handle at all.

- **Hits.** Ids are `int32`. A compiled app chooses its own; the Python face
  interns `(verb, arg)` to an id per `Hits` instance, and keeps `hover` and
  `pressed` as the `(verb, arg)` values `state_of` compares, so they persist
  across a `clear` as today. A buffer holds a fixed number of rects, chosen at
  construction; one add past it answers FULL, and `HITS_DEBUG` raises on it.
  The grid rule stands: `cell` registers nothing.
- **ScrollRegion and DragTap.** The offset, extent, drag and fling are the
  buffer's; `blit_shift` and `note_painted`, which copy canvas pixels, stay in
  the Python face, because the retained shift is a Python surface's.

### 3.5 The role table's `ui` rows

The `ui` rows join `native/moy_app/roles.json` as a role of their own: server
`c`, grant `always` (every app's, as `theme()` is), with wasm types. So the
author's header, `docs/app_api_v1.md`'s table, the adapter's registration and
`tests/test_roles.py`'s ratchets cover them with no new mechanism; a cart that
declares no `moybyte.app` extension imports only from `"moy"`, as now.

## 4. One text path

**What it is.** `moy_text` in `native/moy_gfx` (beside `mg_text`, which it
replaces as the entry):

    int moy_text(sink, uint32_t font, const uint8_t *s, size_t n, int x, int y,
                 int ink, int scale, int align, int maxw);   // the drawn width
    int moy_text_width(uint32_t font, const uint8_t *s, size_t n, int scale);
    int moy_text_wrap(uint32_t font, const uint8_t *s, size_t n, int cols,
                      moy_ui_span_t *lines, int cap);

Every UI text reaches it: the system canvases' `print`, every primitive's
label, the scaled display type (`chrome._print_scaled`), `chrome._text_w`, word
wrap (`ui.wrap_words` and moy_chrome's `panel_lines` become one), the recovery
screen and the kernel's own frames, and a compiled app's `ui_label`. It takes
`align` and `maxw` and returns the width, so fit-and-truncate is one call.

**What does not.** A cart's `print` stays libmoy's `moy_print` at 8 px on every
cart runtime (moy-spec's SPEC.md §6), byte-identical, Lua's C API included.

**The lane choice stays inside it.** Petme128 at scale 1 goes to libmoy's lane
and every other scale to `mg_text_raw`, which is how `mg_text` chooses today
and what the S3 A/B in `native/moy_gfx/moy_gfx_kernels.c`'s header settled. A
second font goes to its own lane in theming phase 4, gated on its own S3 A/B
(`docs/theming_2026-09.md` §4.7).

**The font is a handle-shaped `uint32`.** Sprint 6 has one font, petme128, id
0. Theming phase 4 adds rows of a FONT kind behind the same argument, so the
call does not change when Tiny5 lands. Text is UTF-8; petme128 draws the bytes
it draws today, and a font's codepoint ranges are its data.

## 5. `surface.glyph`'s fate

It leaves the role table. It was a Python-only row only because the glyph
raster was a Workstation method; once the raster is a toolkit primitive it is
drawing, not a role.

- The vocabulary (`chrome._GLYPHS`) moves into the style file; the generated
  table holds each glyph's span pack per scale, as `_glyph_pack` builds today.
- One raster, `moy_ui_glyph`, serves the toolkit, moy_chrome's GLYPH op and
  `ws._glyph`. `moy_chrome_glyph_put` and the start-time push of the Python
  table are deleted, so the two copies cannot drift.
- `runtime/shell_servers.py`'s `SurfaceServer` is deleted. Callers that passed
  `glyph_draw=self._surf.glyph` pass only `glyph=`; Appearance's direct call
  becomes `ui.glyph`. `glyph_draw` stays a keyword for a custom face.
- A compiled app draws one with `ui_glyph`.

## 6. Windowed compiled apps

**What it is.** A compiled app whose manifest asks for a window
(`"moybyte": {"type": "app", "runtime": "wasm", "window": {"min": [w, h]}}`)
runs as a registered Layer rather than cart-shaped. The window managers stay
Python, so the window is the WM's like any other; what is new is a Layer that
draws by running a compiled module, `+runtime/wasm_window.py`.

**The surface.** The WM's window buffer is a canvas row; the Layer points the
run's libmoy canvas at that row's pixels, and the grant's surface row
(sprint 5's, written by `_LayoutCtx.install` and the fullscreen relayout) names
it with its size, scales, origin and windowed flag. On the fullscreen tiers the
same Layer fills the screen below the bar.

**The frame.** The Layer's `draw` asks the kernel for one frame of the run: the
module's `_update` and `_draw` exports, on its session thread, into the window's
canvas. The app's lifecycle is the cart's exports with no new ones: `_init` at
open, a frame per painted frame, and the run ends when the window closes. There
is no close veto: an app saves through `prefs` and `files` as it goes.

**Size and relayout.** A resize rewrites the surface row, and the app reads
`surface.size()` in its frame and re-evaluates its layout spec when the size
moved. Polling one C row per frame costs a read under the seqlock.

**Focus and input.** The WM routes as it does for every window. The focused
window's Layer writes the pointer, in window coordinates, and the typed keys
into the run's input snapshot (`native/moycore/moycore_run.h`'s slots); an
unfocused window's snapshot holds no input. Focus is one more field of the
surface row, `surface.focused()`, written by the WM's focus change, so the app
draws its focused and unfocused looks from it. There is no event queue: the
snapshot already carries the press edge per tick.

**Damage.** The window's content follows `docs/surface_model_v1.md` §14.1 like
any other: a frame with no input and no `damage.again()` is a static frame the
content freeze may skip, so an animating app asks for its next frame with
`damage.again()`, the Class B signal. One mechanism, no new invalidation.

**One run at a time.** `native/moy_wasm/` runs one module at a time. While a
compiled app's window is open, launching a compiled cart, or a second compiled
app, is refused with a notice naming the open one (question 5).

**The VM.** A windowed app needs the Python WM, so it keeps the VM; the
cart-shaped form keeps its sprint 5 verdict.

## 7. The pixel goldens

The host already draws with the boards' raster: `runtime/host_canvas.py` runs
`device/device_canvas.py` over the C kernels through ctypes. So a crossing can
drift pixels only through transcription — arithmetic, order, truncation — and
the nets are aimed at exactly that.

- **The order of ops is the body's order**: field, edge rings, icon or glyph,
  value, label, then the hit registration.
- **Arithmetic is Python's**: floor division (§3.2), the same clamps, and
  truncation counted in glyphs.
- **Counted ops are the same ops**: a surface's `gate_counts` (fills, texts)
  match before and after, so `tests/test_top_bar.py`'s budgets hold unchanged.
- **The nets.** `tests/test_shell_goldens.py` on all six rows (the T-Deck rows
  included, though they reach few widgets); `tests/test_ui_states.py`'s widget
  matrix, extended in step 1 to every primitive and kind, both skins, fs 1 to 3,
  and boxes smaller than their label; `tests/test_skin.py`; the settings pixel
  test. On glass, a widget sheet hashed on each board against the host's hash.
- **No deliberate re-baseline lands in this sprint.** No pixel-moving theming
  phase and no Studio step overlaps it (`docs/theming_2026-09.md` §8).

## 11. The budget

**Image.** The T-Deck is the tightest console image, and its headroom at
sprint 5's end is #224's. The floor is 512 KiB (the plan's §6.1). ESTIMATED:
sprint 5's steps grew the image about 10 KB each (#224); ten C-adding steps at
that rate are about 100 KB, less the frozen bytecode the deleted Python held.
**The sprint's budget is 96 KiB net on the T-Deck** (configuration), which keeps
most of the headroom over the floor for theming phases 3 and 4 and what follows
them. Each step records its image delta in #224; a step over 24 KiB is split or
explained before it lands, and the generated tables are `const` so they cost
flash, not RAM.

**Memory.** The style table, the glyph packs and the strings are `const` in
flash. The looks and the ring live in PSRAM by the plan's §4.6 rule; the hit
and scroll state is the caller's. No internal SRAM is added, and the gate's
meter checks it.

## 12. Risks

- **A widget whose cost was its Python frame, not its ops**, gains less than
  expected: the face is still one Python frame per widget. The A/B decides, and
  a hot surface may call the C entries directly.
- **Tests that read a fake canvas's calls** (a recording stub that asserts
  `rect` arguments) stop seeing a widget's ops. They move to pixels or
  `gate_counts`, in the step that crosses the widget.
- **Canvases that are not rows.** A widget drawn on one has no sink. Step 1's
  ratchet lists every canvas class a widget is handed; any that is not a canvas
  row becomes one or stops taking widgets.
- **Scaled display type.** `_print_scaled` paints a glyph pixel as a block per
  `rect`; `mg_text_raw` at the same scale is expected to paint the same blocks.
  If a golden says otherwise, step 3 keeps a block lane inside `moy_text`
  rather than move a pixel.
- **Theming lands beside this.** Its phases 1 and 2a move no pixels and could
  overlap; its phases 3 and 4 must not (question 1).
- **The one-run rule** may surprise on the desk; the notice names what is open.

## 13. Owner questions

1. **Theming's loader.** Recommendation: theming phases 1 and 2a run after this
   sprint, written in C against the toolkit, with no Python reference built

   apps only, and no Python layout takes a spec this sprint.

   window and a compiled cart exclude each other, with a notice. A second
   concurrent run is engine work for a case no one has asked for.
6. **Windowed input by polling.** Recommendation: the run's snapshot plus the
   `size` and `focused` rows, no event queue and no close veto. This reverses
   the sentence in `docs/kernel_appabi_2026-10.md` §4.1 that promised exports
